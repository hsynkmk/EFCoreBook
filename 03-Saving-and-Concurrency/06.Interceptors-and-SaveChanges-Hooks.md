# Interceptors & SaveChanges Hooks

## 🧠 Intuition

Many cross-cutting concerns repeat across every save: audit timestamps, soft-delete, the outbox
pattern, command logging, tenant scoping, performance instrumentation. Putting that code in every
service is duplication; putting it in `OverrideSaveChangesAsync` is fine for a single context but
brittle. **Interceptors** are EF's official extensibility seams — small classes you register
in DI that EF calls at well-defined moments (before command execution, after save, on
transaction commit, etc.).

> 💡 **Interceptors are how senior teams stay DRY in EF.** Anything that should happen on every
> save / command / connection is a candidate.

## 📐 The interceptor types

| Interface | Hooked into |
|-----------|-------------|
| `ISaveChangesInterceptor` | `SavingChanges`, `SavedChanges`, `SaveChangesFailed` |
| `IDbCommandInterceptor` | About to execute / executed / error on any command |
| `IDbConnectionInterceptor` | Connection opening, opened, closed |
| `IDbTransactionInterceptor` | Begin / commit / rollback |
| `IMaterializationInterceptor` | After entities are materialized from query results |

You register them on the context:

```csharp
opt.UseSqlServer(cs).AddInterceptors(new AuditingSaveChangesInterceptor());
```

…or via DI:

```csharp
builder.Services.AddSingleton<AuditingSaveChangesInterceptor>();
builder.Services.AddDbContext<BloggingContext>((sp, opt) =>
    opt.UseSqlServer(cs)
       .AddInterceptors(sp.GetRequiredService<AuditingSaveChangesInterceptor>()));
```

## 💻 Auditing interceptor (the canonical example)

```csharp
public class AuditingSaveChangesInterceptor : SaveChangesInterceptor {
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var ctx = eventData.Context!;
        var now = DateTime.UtcNow;
        foreach (var entry in ctx.ChangeTracker.Entries<IAuditable>()) {
            if (entry.State == EntityState.Added)    entry.Entity.CreatedUtc = now;
            if (entry.State is EntityState.Added or EntityState.Modified) entry.Entity.UpdatedUtc = now;
        }
        return ValueTask.FromResult(result);
    }
}

public interface IAuditable { DateTime CreatedUtc { get; set; } DateTime UpdatedUtc { get; set; } }
```

Every entity implementing `IAuditable` gets timestamps automatically, with zero per-service code.

## 💻 Soft-delete interceptor

```csharp
public class SoftDeleteInterceptor : SaveChangesInterceptor {
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        foreach (var entry in eventData.Context!.ChangeTracker.Entries<ISoftDeletable>()) {
            if (entry.State == EntityState.Deleted) {
                entry.State = EntityState.Modified;     // convert DELETE to UPDATE
                entry.Entity.IsDeleted = true;
            }
        }
        return ValueTask.FromResult(result);
    }
}
public interface ISoftDeletable { bool IsDeleted { get; set; } }
```

Pair with a `HasQueryFilter(b => !b.IsDeleted)` on entities (see
[Global & Named Filters](../01-Modeling-Data/08.Global-and-Named-Query-Filters.md)) and you have
real, system-wide soft delete.

## 💻 Outbox pattern interceptor (the "events on save" pattern)

```csharp
public class OutboxInterceptor : SaveChangesInterceptor {
    public override async ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var ctx = eventData.Context!;
        var aggregateChanges = ctx.ChangeTracker.Entries<IHasDomainEvents>()
            .SelectMany(e => e.Entity.DequeueEvents())
            .ToList();
        foreach (var evt in aggregateChanges)
            ctx.Add(new OutboxMessage(evt.GetType().FullName!, JsonSerializer.Serialize(evt)));
        return result;
    }
}
```

Every aggregate's domain events end up in an `OutboxMessage` table inside the **same transaction**
as the business change. A background dispatcher picks them up and publishes — guaranteed
at-least-once delivery without a distributed transaction.

## 💻 Command interceptor for performance logging

```csharp
public class SlowQueryInterceptor : DbCommandInterceptor {
    private const int ThresholdMs = 200;
    private readonly ILogger<SlowQueryInterceptor> _logger;
    public SlowQueryInterceptor(ILogger<SlowQueryInterceptor> logger) => _logger = logger;

    public override async ValueTask<DbDataReader> ReaderExecutedAsync(
        DbCommand command, CommandExecutedEventData eventData, DbDataReader result, CancellationToken ct = default)
    {
        if (eventData.Duration.TotalMilliseconds > ThresholdMs)
            _logger.LogWarning("Slow query ({Ms}ms): {Sql}", eventData.Duration.TotalMilliseconds, command.CommandText);
        return result;
    }
}
```

Surface slow queries automatically. Combine with `TagWith` for instant identification.

## ⚖️ Trade-offs

**Pros:** centralized cross-cutting logic; testable; composable (register many); reusable across
contexts.
**Cons:** invisible from a casual read of a save operation — readers must know interceptors exist;
order can matter if interceptors interact; **`ExecuteUpdate` / `ExecuteDelete` bypass
SaveChanges interceptors** (use a command interceptor for them).

## 🚫 Common mistakes

```csharp
// ❌ Storing per-request state in a singleton interceptor field
public class TenantInterceptor : SaveChangesInterceptor { private int _tenantId; ... }   // shared across requests!
// ✅ inject IHttpContextAccessor or a scoped service to read the tenant on each call

// ❌ Relying on a SaveChanges interceptor to audit ExecuteUpdate/ExecuteDelete
// ✅ those bypass the change tracker — set audit columns in the SetProperty list, or use a command interceptor

// ❌ Throwing from an interceptor without restoring state
// ✅ make interceptors idempotent and safe to retry
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- Interceptor APIs are stable from EF 5+; new interfaces have been added gradually.
- **EF 10** simplified emitted SQL parameter names — interceptor-captured commands are now far
  more readable in logs.

## 🌍 Real-world production tips

- One interceptor per concern — auditing, soft-delete, outbox, slow-query — all small classes.
- Register interceptors via **DI** so they can depend on `ILogger`, `IHttpContextAccessor`, etc.
- For multi-context apps, share interceptors across contexts where the concern is the same.
- Test interceptors with **integration tests** (real save, real assertions on rows / outbox).

## 🎯 Practice (with full solutions)

### 1. System-wide audit — `Medium`
**Task:** Every entity implementing `IAuditable` should auto-set `CreatedUtc` / `UpdatedUtc`.
**Solution:** the `AuditingSaveChangesInterceptor` above; register via DI; mark relevant entities
with `IAuditable`. Done.
**Why it's better:** zero per-service code; consistent across every save in every context.

### 2. Soft delete from a single interceptor — `Medium`
**Task:** `Remove(blog)` should produce an `UPDATE` (set `IsDeleted = true`) instead of a `DELETE`.
**Solution:** the `SoftDeleteInterceptor` above. Adopt the `ISoftDeletable` interface on
soft-delete-able entities. Add the query filter. Done.
**Why it's better:** services keep calling `ctx.Remove`/`SaveChangesAsync` as usual; the
interceptor invisibly converts deletions to soft updates.

## ✅ Key Takeaways

- **Interceptors** are EF's official cross-cutting extensibility seam — `SaveChanges`, command,
  connection, transaction, materialization hooks.
- Use them for **auditing, soft delete, outbox, slow-query logging, multitenancy**.
- Register via **DI** so they can depend on scoped services.
- Remember: `ExecuteUpdate` / `ExecuteDelete` **bypass `SaveChanges` interceptors**.
