# Cascade Delete (and Soft Delete)

## 🧠 Intuition

Delete a `Blog` and its `Posts` are now orphans. You have two choices: **delete them too**
(cascade) or **prevent the deletion** until you clean them up (restrict). EF lets you configure
this per relationship. For audit-sensitive domains, you often want neither — you want **soft
delete**: keep the row, just mark it `IsDeleted = true`.

> 💡 EF infers cascade behavior from the relationship's nullability. Required FK → `Cascade`.
> Optional FK → `ClientSetNull`. Read these defaults; they're a common source of "wait, EF deleted
> what?".

## 📐 The behaviors

| `DeleteBehavior` | What the DB does | What EF does to tracked dependents |
|------------------|-----------------|------------------------------------|
| `Cascade` | Delete dependents automatically | Same; loaded ones are deleted too |
| `Restrict` | Block the delete if dependents exist | Throws an exception |
| `SetNull` | Sets the FK to NULL (requires nullable FK) | Sets loaded dependents' FK to null |
| `ClientSetNull` (default for **optional**) | Nothing (no DB action) | EF sets loaded dependents' FK to null |
| `ClientCascade` | Nothing | EF deletes loaded dependents |
| `NoAction` | Errors at DB level on violation | Nothing |

EF's defaults:
- **Required** relationship (`int BlogId`) → `Cascade`.
- **Optional** relationship (`int? BlogId`) → `ClientSetNull`.

## 💻 Configuring it

```csharp
modelBuilder.Entity<Blog>()
    .HasMany(b => b.Posts)
    .WithOne(p => p.Blog)
    .HasForeignKey(p => p.BlogId)
    .OnDelete(DeleteBehavior.Cascade);

modelBuilder.Entity<User>()
    .HasMany<Post>().WithOne(p => p.Editor)
    .HasForeignKey(p => p.EditorId)
    .OnDelete(DeleteBehavior.SetNull);   // requires int? EditorId
```

## 🚫 The multiple-cascade-paths trap (SQL Server)

SQL Server rejects multiple cascade paths to the same dependent row — for example, deleting a
`User` that's referenced from two relationships on `Post` (`AuthorId` and `EditorId`) both with
`Cascade`. You'll see:

```
Introducing FOREIGN KEY constraint 'FK_Posts_Users_EditorId' on table 'Posts' may cause cycles or multiple cascade paths.
```

**Fix:** make one path `Restrict`, `NoAction`, or `SetNull`.

## 💻 Soft delete — the preferred pattern in many apps

```csharp
public class Blog {
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public bool IsDeleted { get; set; }
}

modelBuilder.Entity<Blog>()
    .HasQueryFilter(b => !b.IsDeleted);   // queries hide soft-deleted rows automatically

// "Delete" via:
blog.IsDeleted = true;
await ctx.SaveChangesAsync();
```

Pair with a **filtered index** on `IsDeleted = 0` (see [Indexes & Constraints](../01-Modeling-Data/07.Indexes-and-Constraints.md))
and, on EF 10, **named query filters** so admins can bypass just the soft-delete filter
([Global & Named Query Filters](../01-Modeling-Data/08.Global-and-Named-Query-Filters.md)).

You can also wire soft delete via a **`SaveChanges` interceptor**: intercept `EntityState.Deleted`
on flagged types and convert to `Modified` + `IsDeleted = true`. See
[Interceptors](06.Interceptors-and-SaveChanges-Hooks.md).

## ⚖️ Cascade vs Restrict vs Soft Delete

| | Cascade | Restrict | Soft delete |
|--|---------|----------|-------------|
| Data preserved? | No | No (must clean dependents first) | **Yes** |
| Audit / undo? | No | No | **Yes** |
| Storage cost | None | None | Grows forever (prune) |
| FK enforcement | DB | DB | App (query filter) |
| Best for | Aggregate ownership (delete blog → delete its posts) | "I want to be told if dependents exist" | Anything user-facing where "deleted" is reversible |

## 🚫 Common mistakes

```csharp
// ❌ Forgetting to switch to Restrict on a multi-path cascade → migration fails
// ✅ explicitly pick a behavior

// ❌ Soft delete without a query filter → deleted rows leak everywhere
// ✅ HasQueryFilter on every soft-deleted entity

// ❌ Soft delete + no retention policy → table grows forever
// ✅ background job to hard-delete after N days, or move to an archive table
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 10 named query filters** dramatically improve the soft-delete experience: you can
  selectively bypass only the soft-delete filter (`IgnoreQueryFilters(["SoftDelete"])`) without
  also disabling tenant scoping.

## 🌍 Real-world production tips

- For most user data, **soft delete + named filters + filtered index** is the senior default.
- Cascade is fine for aggregates you genuinely own (a `Blog` owns its `Posts`).
- For multi-tenant systems, hard-delete with retention via a background process is much cleaner
  than ever-growing soft-deleted rows.
- Document the delete strategy per entity — surprise cascades are no fun on day 90 of an outage.

## 🎯 Practice (with full solutions)

### 1. Soft delete with a clean admin path — `Medium` (EF 10)
**Task:** Soft-delete `Blog`. Regular queries hide deleted; admin can see them but tenant scoping
still applies.
**Solution:**
```csharp
modelBuilder.Entity<Blog>()
    .HasQueryFilter("SoftDelete", b => !b.IsDeleted)
    .HasQueryFilter("Tenant", b => b.TenantId == _tenant.Current);

modelBuilder.Entity<Blog>()
    .HasIndex(b => b.Title)
    .HasFilter("[IsDeleted] = 0");

// admin
var deleted = await ctx.Blogs.IgnoreQueryFilters(["SoftDelete"]).ToListAsync();
```
**Why it's better:** tenant rule is never accidentally bypassed; index is small; admins get what
they need with one named override.

### 2. Resolve multiple cascade paths — `Easy`
**Task:** `Post` has `AuthorId` (required) and `EditorId` (optional), both pointing at `User`.
Migration errors on cascade paths.
**Solution:**
```csharp
modelBuilder.Entity<Post>()
    .HasOne(p => p.Author).WithMany().HasForeignKey(p => p.AuthorId)
    .OnDelete(DeleteBehavior.Restrict);   // can't delete a User who authored posts

modelBuilder.Entity<Post>()
    .HasOne(p => p.Editor).WithMany().HasForeignKey(p => p.EditorId)
    .OnDelete(DeleteBehavior.SetNull);    // editor goes → posts' Editor null
```
**Why it's better:** the two paths now have distinct behaviors that match business intent.

## ✅ Key Takeaways

- EF infers cascade by relationship requiredness; **read the default** before relying on it.
- SQL Server **rejects multiple cascade paths** to the same row — pick one path to `Restrict` /
  `SetNull` / `NoAction`.
- **Soft delete** with a global / named query filter is the senior default for user data.
- Pair soft delete with **filtered indexes** and a **retention/archive plan**.
