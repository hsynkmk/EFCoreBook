# Change Tracking

## 🧠 Intuition

When EF returns a tracked entity from a query, it stashes a **snapshot** of the original values
on the side. When you call `SaveChangesAsync()`, EF compares the current entity to that snapshot
and decides what SQL to emit. That's how `blog.Views++` becomes a one-column `UPDATE [Views] = ...`
instead of a full row write — and how related-graph mutations (add a post to a blog, set a
navigation) translate to correct INSERT/UPDATE/DELETE order automatically.

> 💡 **Mental model:** the change tracker is a *diff* between the entity you got and the entity
> you have now. `SaveChangesAsync` is "apply the diff, in order, transactionally."

## 📐 Entity states

| State | When it happens |
|-------|-----------------|
| `Detached` | Entity isn't tracked (created with `new`, queried with `AsNoTracking`, or removed from the change tracker) |
| `Added` | `ctx.Set<T>().Add(entity)` |
| `Unchanged` | Just queried (tracked), no mutations |
| `Modified` | A property of a tracked entity was changed |
| `Deleted` | `ctx.Set<T>().Remove(entity)` |

`SaveChangesAsync` issues `INSERT` for `Added`, `UPDATE` for `Modified`, and `DELETE` for `Deleted`
entities — in the right order based on relationships, inside one transaction.

## 💻 Reading and changing state

```csharp
var blog = await ctx.Blogs.FirstAsync(b => b.Id == 42);

var entry = ctx.Entry(blog);
Console.WriteLine(entry.State);                                  // Unchanged

blog.Views++;
Console.WriteLine(entry.State);                                  // Modified

Console.WriteLine(entry.Property(b => b.Views).OriginalValue);   // the snapshot value
Console.WriteLine(entry.Property(b => b.Views).CurrentValue);    // the new value

await ctx.SaveChangesAsync();
Console.WriteLine(entry.State);                                  // back to Unchanged
```

## 💻 Detaching, attaching, updating

```csharp
// Got an entity from somewhere else (an API call, a cache); now I want to save changes
ctx.Attach(blog);                          // tracked as Unchanged
ctx.Entry(blog).State = EntityState.Modified;   // mark all properties as modified
await ctx.SaveChangesAsync();

// Shorter: ctx.Update(blog) — attaches AND marks Modified
ctx.Update(blog);
await ctx.SaveChangesAsync();
```

> ⚠️ `Update(entity)` marks **every property** as modified — so the `UPDATE` writes every column.
> For a partial update without loading the entity, prefer **`ExecuteUpdateAsync`**
> (see [Bulk Operations](05.Bulk-Operations.md)).

## 💻 Disabling auto-detect for hot paths

Every read of `ChangeTracker.Entries()` and most query/save operations call `DetectChanges` which
scans tracked entities. For very large bulk inserts, you can turn this off:

```csharp
ctx.ChangeTracker.AutoDetectChangesEnabled = false;
try {
    foreach (var batch in items.Chunk(1000)) {
        ctx.Items.AddRange(batch);
        await ctx.SaveChangesAsync();
    }
} finally {
    ctx.ChangeTracker.AutoDetectChangesEnabled = true;   // ALWAYS restore
}
```

> ⚠️ Forget to restore and the rest of your code stops noticing changes. Wrap in `try/finally`.

## ⚖️ Trade-offs

**Pros:** writes only changed columns; correct insert/update/delete ordering with related graphs;
relationship fix-up automatic.
**Cons:** snapshot memory per tracked entity; CPU on `DetectChanges`; tracked entities live as
long as the context. For read-only paths and bulk writes, opt out.

## 🚫 Common mistakes

```csharp
// ❌ Forgetting that AsNoTracking entities won't save
var blog = await ctx.Blogs.AsNoTracking().FirstAsync(b => b.Id == id);
blog.Views++; await ctx.SaveChangesAsync();   // no UPDATE — entity isn't tracked

// ❌ Update(entity) when you wanted a partial update
ctx.Update(blog);   // writes every column — including ones the client never touched
// ✅ load + mutate + save, OR ExecuteUpdateAsync for partial server-side updates

// ❌ Long-lived DbContext accumulates tracked entities
// ✅ scoped (one per request); clear with ctx.ChangeTracker.Clear() if you must reuse
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** `Update` and `Attach` semantics stable; primary constructors compatible.
- **EF 9:** small `DetectChanges` perf improvements; better diagnostics.
- **EF 10:** no major behavior changes; pairs with **EF 10 ExecuteUpdate non-expression lambdas**
  for cleaner partial-update code paths.

## 🌍 Real-world production tips

- **Read-side: `AsNoTracking()` everywhere.** Write-side: tracked, mutate, save.
- For **API-driven updates** (client posts a DTO), the safe pattern is **load entity → apply
  changed fields → save**, not `Update` over a deserialized DTO.
- For very large inserts, **`AutoDetectChangesEnabled = false`** is fine but disciplined.
- Use **`ctx.ChangeTracker.DebugView.LongView`** when investigating "why did SaveChanges do X?".

## 🎯 Practice (with full solutions)

### 1. Make the right `SaveChanges` happen — `Easy`
**Smelly code:**
```csharp
var blog = await ctx.Blogs.AsNoTracking().FirstAsync(b => b.Id == id);
blog.Title = newTitle;
await ctx.SaveChangesAsync();   // silently does nothing
```
**Solution:**
```csharp
// Either drop AsNoTracking when you intend to write:
var blog = await ctx.Blogs.FirstAsync(b => b.Id == id);
blog.Title = newTitle;
await ctx.SaveChangesAsync();

// Or, if you got the entity from elsewhere:
ctx.Attach(blog);
ctx.Entry(blog).Property(b => b.Title).IsModified = true;   // only the field that changed
await ctx.SaveChangesAsync();
```
**Why it's better:** the second variant produces an `UPDATE` that touches only `[Title]` — perfect
for partial saves.

### 2. Partial server-side update — `Medium`
**Task:** Bump views by 1 for every blog whose tenant matches, without loading any entity.
**Solution:**
```csharp
await ctx.Blogs
    .Where(b => b.TenantId == tenantId)
    .ExecuteUpdateAsync(s => s.SetProperty(b => b.Views, b => b.Views + 1));
```
**Why it's better:** zero tracked entities, one round-trip, one SQL statement. The change tracker
isn't involved at all (see [Bulk Operations](05.Bulk-Operations.md)).

## ✅ Key Takeaways

- The **change tracker** keeps snapshots so `SaveChangesAsync` emits only the necessary SQL.
- Entity states: **Detached, Added, Unchanged, Modified, Deleted**.
- `Update(entity)` writes every column — use partial techniques for surgical changes.
- For huge inserts, consider toggling `AutoDetectChangesEnabled`; always restore it.
- Read-only → `AsNoTracking`; partial server-side write → `ExecuteUpdateAsync`.

**Self-check:**
1. What's the snapshot and why does it matter?
2. Why does `AsNoTracking + mutate + SaveChanges` silently do nothing?
3. When would you use `ExecuteUpdateAsync` instead of mutating a tracked entity?
