# Concurrency Handling

## 🧠 Intuition

Two users edit the same blog at the same time. Alice changes the title; Bob, who loaded the
blog a minute earlier, saves a different title. Without protection, **last write wins** — Alice's
edit silently vanishes. **Optimistic concurrency** assumes conflicts are rare: each write asserts
"the row hasn't changed since I read it"; if it has, EF throws a `DbUpdateConcurrencyException`
you can handle deliberately.

> 💡 **The pattern:** detect the conflict, decide policy (last-write-wins, first-write-wins,
> merge, ask the user), retry if appropriate. EF gives you the detection; you choose the resolution.

## 💻 The simplest mechanism — `RowVersion`

```csharp
public class Blog {
    public int Id { get; set; }
    public string Title { get; set; } = "";
    [Timestamp]                                       // EF: this is the concurrency token
    public byte[] RowVersion { get; set; } = null!;
}
```

Equivalent Fluent:
```csharp
modelBuilder.Entity<Blog>().Property(b => b.RowVersion).IsRowVersion();
```

**⚡ Generated SQL** on save:
```sql
UPDATE [Blogs] SET [Title] = @p0
OUTPUT INSERTED.[RowVersion]
WHERE [Id] = @p1 AND [RowVersion] = @p2;   -- the original RowVersion EF saw

-- if 0 rows are affected, EF throws DbUpdateConcurrencyException
```

SQL Server's `rowversion` (a.k.a. `timestamp`) auto-increments on every UPDATE. EF compares the
stored version against the one it read; mismatch → conflict.

## 💻 The other mechanism — a concurrency token on a regular column

```csharp
public class Order {
    public int Id { get; set; }
    public string Status { get; set; } = "";
    [ConcurrencyCheck] public int Version { get; set; }   // you manage Version yourself
}
```

You bump `Version` on every save. Works on any provider; less automatic than `RowVersion`.

## 💻 Handling the exception

```csharp
try {
    await ctx.SaveChangesAsync();
} catch (DbUpdateConcurrencyException ex) {
    foreach (var entry in ex.Entries) {
        var dbValues = await entry.GetDatabaseValuesAsync();
        if (dbValues == null) {
            // The row was deleted by someone else.
        } else {
            // Decide policy:
            //   - "client wins": entry.OriginalValues.SetValues(dbValues); await ctx.SaveChangesAsync();
            //   - "store wins": entry.CurrentValues.SetValues(dbValues);  // discard local changes
            //   - "merge": let the user resolve field-by-field
        }
    }
}
```

`OriginalValues` is what we read; `CurrentValues` is what we tried to save; `dbValues` is what's
*currently* in the database. You compare and decide.

## ⚖️ Resolution strategies

| Strategy | When to use |
|----------|-------------|
| **Client wins** | The user explicitly chose to overwrite (with confirmation) |
| **Store wins** | Local changes were probably stale; refresh and abandon |
| **Merge** | Mature UI that highlights conflicts field-by-field |
| **Retry** | The conflict is on a counter / aggregate — re-read, re-apply, save |

## 🚫 Common mistakes

```csharp
// ❌ No concurrency token + heavy update traffic = silent lost writes
// ✅ Always add a concurrency token on rows that multiple users update

// ❌ Catching DbUpdateConcurrencyException and just retrying blindly forever
// ✅ Bounded retries with backoff; surface unresolvable conflicts to the user

// ❌ Concurrency token on a column the database also auto-updates (e.g. a trigger)
// → EF's expected value diverges from the DB's value; conflicts on every save
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- Stable across EF 8/9/10. `[Timestamp]` / `IsRowVersion()` work on SQL Server out of the box.
- **PostgreSQL** uses `xmin` (a system column) for the same purpose: `Property(b => b.Version).IsRowVersion()`
  with the Npgsql provider maps to `xmin`.

## 🌍 Real-world production tips

- **Add a `RowVersion`** on any entity that's edited by multiple users or that participates in
  optimistic workflows.
- For **counters / inventories**, prefer an atomic `ExecuteUpdateAsync` (`SetProperty(i =>
  i.Stock, i => i.Stock - 1)`) — no concurrency token needed, the database does the math.
- Test conflict handling end-to-end with **two concurrent integration tests** — surprisingly easy
  to ship a code path that never actually triggers.

## 🎯 Practice (with full solutions)

### 1. Add optimistic concurrency to `Blog` — `Easy`
**Task:** Add a `RowVersion` and a save loop that asks the database for current values on conflict.
**Solution:**
```csharp
public class Blog {
    public int Id { get; set; }
    public string Title { get; set; } = "";
    [Timestamp] public byte[] RowVersion { get; set; } = null!;
}

public async Task SaveAsync(BloggingContext ctx) {
    while (true) {
        try { await ctx.SaveChangesAsync(); return; }
        catch (DbUpdateConcurrencyException ex) {
            foreach (var entry in ex.Entries) {
                var dbValues = await entry.GetDatabaseValuesAsync();
                if (dbValues == null) throw;                                    // deleted
                entry.OriginalValues.SetValues(dbValues);                       // client-wins: keep my Title
            }
            // try again with the fresh OriginalValues
        }
    }
}
```
**Why it's better:** detects collisions, resolves with a clear policy, never silently loses
writes.

### 2. Counter without concurrency tokens — `Medium`
**Scenario:** `Inventory.Stock` decreases on every order. Conflicts under load would be constant
with optimistic concurrency.
**Solution:** atomic server-side update:
```csharp
var rows = await ctx.Inventory
    .Where(i => i.Sku == sku && i.Stock > 0)
    .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - 1));
if (rows == 0) throw new OutOfStockException();
```
**Why it's better:** the database does the read-modify-write atomically; no concurrency token,
no retries.

## ✅ Key Takeaways

- EF supports **optimistic concurrency** via **`RowVersion`** (auto-incremented) or
  **`[ConcurrencyCheck]`** (you manage the version).
- On conflict, EF throws **`DbUpdateConcurrencyException`** — handle it deliberately
  (client-wins / store-wins / merge / retry).
- For counters and atomic increments, prefer **`ExecuteUpdateAsync`** with server-side expressions.
- Test concurrency paths — they're easy to ship broken.
