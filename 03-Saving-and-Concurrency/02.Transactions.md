# Transactions

## 🧠 Intuition

A transaction groups multiple operations so they either **all succeed** or **all fail** — no
half-written state. EF wraps every `SaveChangesAsync` in an implicit transaction automatically.
You only need to manage transactions yourself when:
- Multiple `SaveChangesAsync` calls must commit together.
- You mix EF with raw SQL (`ExecuteSqlAsync`, `ExecuteUpdateAsync`) and need them in one trip.
- You want **savepoints** to roll back part of a long operation.

> 💡 The default is right 90% of the time. Reach for explicit transactions when EF's per-`Save`
> transaction doesn't span enough work.

## 💻 The default — implicit, per SaveChanges

```csharp
ctx.Blogs.Add(blog);
ctx.Posts.AddRange(posts);
await ctx.SaveChangesAsync();   // entire batch wrapped in one transaction automatically
```

If anything fails, nothing is saved. No code needed.

## 💻 Explicit transaction across multiple operations

```csharp
using var tx = await ctx.Database.BeginTransactionAsync();
try {
    ctx.Orders.Add(order);
    await ctx.SaveChangesAsync();

    await ctx.Inventory.Where(i => i.Sku == sku)
        .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - 1));

    await ctx.AuditLog.AddAsync(new Audit("OrderPlaced"));
    await ctx.SaveChangesAsync();

    await tx.CommitAsync();
} catch {
    await tx.RollbackAsync();   // explicit; `using` would also dispose without commit
    throw;
}
```

Everything inside the `try` either commits together or rolls back together.

## 💻 Savepoints — partial rollback inside a transaction

```csharp
using var tx = await ctx.Database.BeginTransactionAsync();

await ctx.Orders.AddAsync(order);
await ctx.SaveChangesAsync();

await tx.CreateSavepointAsync("Order");

try {
    await ctx.Audits.AddAsync(new Audit("OrderPlaced"));
    await ctx.SaveChangesAsync();
} catch {
    await tx.RollbackToSavepointAsync("Order");   // keep the order, drop the audit attempt
}

await tx.CommitAsync();
```

Savepoints are great for "try this optional sub-step; on failure, keep what's already done."

## 💻 Sharing a transaction across two `DbContext`s

```csharp
using var tx = await ctxA.Database.BeginTransactionAsync();
ctxB.Database.UseTransaction(tx.GetDbTransaction());

// changes in both contexts now share the same transaction
await ctxA.SaveChangesAsync();
await ctxB.SaveChangesAsync();
await tx.CommitAsync();
```

Useful when two bounded contexts share a database and a unit of work crosses both.

## 💻 `TransactionScope`

```csharp
using var scope = new TransactionScope(
    TransactionScopeOption.Required,
    new TransactionOptions { IsolationLevel = IsolationLevel.ReadCommitted },
    TransactionScopeAsyncFlowOption.Enabled);

await ctx.SaveChangesAsync();
scope.Complete();
```

Less common in EF Core, useful when integrating with legacy code or distributed transactions
(MSDTC). Note `TransactionScopeAsyncFlowOption.Enabled` — without it, async + scope breaks.

## ⚖️ Isolation levels (the short version)

| Level | Risks accepted |
|-------|----------------|
| `ReadCommitted` (SQL Server default) | Non-repeatable reads, phantom reads |
| `RepeatableRead` | Phantom reads |
| `Serializable` | None (but locks more) |
| `Snapshot` (SQL Server) | Optimistic; needs `ALLOW_SNAPSHOT_ISOLATION ON` |

Most apps live with `ReadCommitted` and use **optimistic concurrency** (next file) to handle
conflicts. Choose stricter levels only when you have a documented reason.

## 🚫 Common mistakes

```csharp
// ❌ Forgetting to commit
using var tx = await ctx.Database.BeginTransactionAsync();
ctx.Blogs.Add(blog);
await ctx.SaveChangesAsync();
// tx goes out of scope WITHOUT commit → rollback. Silent data loss.

// ❌ Long-running transactions
// holds locks; blocks other writers; deadlocks. Keep transactions short.

// ❌ TransactionScope without async flow
using var scope = new TransactionScope();   // BROKEN with async
// ✅ TransactionScopeAsyncFlowOption.Enabled
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 9** bundled all pending migrations into **one transaction by default**; **EF 10 reverted
  this** because it caused issues in various deployment scenarios — migrations are now per-step
  again (which is the historical behavior).
- All explicit transaction APIs stable across EF 8/9/10.

## 🌍 Real-world production tips

- **Keep transactions short.** Open → do the minimum → commit. Long transactions cause lock
  waits, retries, and deadlocks.
- For **idempotent workflows** (`Place order` should be safe to retry), pair the explicit
  transaction with an idempotency key check at the start.
- **Avoid distributed transactions** (MSDTC) unless absolutely necessary — they're slow and
  fragile. Outbox pattern is usually a better answer.
- Combine with **`EnableRetryOnFailure`** carefully — retries restart the transaction from the
  beginning, so make the body idempotent.

## 🎯 Practice (with full solutions)

### 1. Wrap an order + inventory update — `Medium`
**Scenario:** Placing an order must insert an `Order`, decrement `Inventory.Stock`, and write an
`Audit` record — atomically.
**Solution:**
```csharp
public async Task PlaceOrderAsync(Order order, BloggingContext ctx) {
    using var tx = await ctx.Database.BeginTransactionAsync();
    ctx.Orders.Add(order);
    await ctx.SaveChangesAsync();

    var updated = await ctx.Inventory
        .Where(i => i.Sku == order.Sku && i.Stock > 0)
        .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - 1));
    if (updated == 0) throw new OutOfStockException();

    ctx.AuditLog.Add(new Audit("OrderPlaced", order.Id));
    await ctx.SaveChangesAsync();

    await tx.CommitAsync();
}
```
**Why it's better:** all-or-nothing across two `SaveChangesAsync` calls plus a raw `ExecuteUpdate`
inside the same transaction. Failure anywhere rolls everything back.

### 2. Use a savepoint for an optional step — `Medium`
**Scenario:** After saving an order, try to call an external notification audit log; if it
fails, keep the order but skip the audit row.
**Solution:**
```csharp
using var tx = await ctx.Database.BeginTransactionAsync();
ctx.Orders.Add(order);
await ctx.SaveChangesAsync();
await tx.CreateSavepointAsync("AfterOrder");
try {
    await TrySendAuditAsync();
} catch {
    await tx.RollbackToSavepointAsync("AfterOrder");
}
await tx.CommitAsync();
```
**Why it's better:** the order is preserved; the optional step rolls back independently.

## ✅ Key Takeaways

- `SaveChangesAsync` runs in an **implicit transaction** — usually all you need.
- Open an **explicit transaction** when multiple operations must commit together.
- **Savepoints** allow partial rollback within a transaction.
- Keep transactions **short** and pair them with **idempotency** for safe retries.
- Avoid `TransactionScope` without `AsyncFlowOption.Enabled`.
