# Bulk Operations: ExecuteUpdate & ExecuteDelete

> **EF 7** introduced `ExecuteUpdateAsync` / `ExecuteDeleteAsync`. **EF 9** added complex-type
> support. **EF 10** added **non-expression lambdas** and **JSON-mapped property** support — the
> two biggest quality-of-life wins.

## 🧠 Intuition

Mutating many rows with EF's classic tracked pattern — **load** entities, **mutate**, **save** —
costs one entity per row in memory and at least one round-trip per save. For "set the status to
'Archived' on every order older than a year," that's brutal. **`ExecuteUpdateAsync`** /
**`ExecuteDeleteAsync`** ship a single UPDATE / DELETE statement to the database, no entities
loaded, no change tracker involved.

> 💡 **The rule:** when you don't need to apply per-entity business rules in C#, **do it on the
> server**. EF gives you LINQ-shaped bulk operations now — use them.

## 🎯 The Problem

```csharp
// ❌ Before EF 7: load + mutate + save — millions of entities through the change tracker
var stale = await ctx.Orders.Where(o => o.PlacedUtc < cutoff).ToListAsync();
foreach (var o in stale) o.Status = "Archived";
await ctx.SaveChangesAsync();
```

For a million rows, that's a million tracked entities, a giant DetectChanges scan, and a giant
batch of `UPDATE` statements.

## 💻 `ExecuteUpdateAsync`

```csharp
var updated = await ctx.Orders
    .Where(o => o.PlacedUtc < cutoff)
    .ExecuteUpdateAsync(s => s
        .SetProperty(o => o.Status, "Archived")
        .SetProperty(o => o.UpdatedUtc, DateTime.UtcNow));
```

**⚡ Generated SQL (SQL Server):**
```sql
UPDATE [o] SET [Status] = N'Archived', [UpdatedUtc] = GETUTCDATE()
FROM [Orders] AS [o]
WHERE [o].[PlacedUtc] < @cutoff
```

One statement, parameterized, no entities materialized. Returns the row count.

### Server-side computations

```csharp
await ctx.Inventory
    .Where(i => i.Sku == sku)
    .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - 1));
```

The `i => i.Stock - 1` is evaluated **in SQL**. Atomic; no race condition; no need for an
optimistic-concurrency token.

## 💻 EF 10: non-expression lambdas 🆕

Pre-EF-10, `ExecuteUpdateAsync` took an **expression tree** — making conditional or dynamic
updates extremely painful:

```csharp
// ❌ Before EF 10: had to build an expression tree manually if some sets were conditional
```

**EF 10** accepts a regular lambda body, so this just works:

```csharp
await ctx.Blogs.ExecuteUpdateAsync(s => {
    s.SetProperty(b => b.Views, 0);
    if (resetName) {
        s.SetProperty(b => b.Title, "");   // conditional — no expression tree gymnastics
    }
});
```

## 💻 EF 10: ExecuteUpdate on JSON-mapped complex properties 🆕

For a complex type mapped to JSON (see [JSON Columns](../01-Modeling-Data/10.JSON-Columns-and-Primitive-Collections.md)):

```csharp
modelBuilder.Entity<Blog>().ComplexProperty(b => b.Details, d => d.ToJson());

await ctx.Blogs.ExecuteUpdateAsync(s =>
    s.SetProperty(b => b.Details.Views, b => b.Details.Views + 1));
```

**⚡ Generated SQL (SQL Server 2025):**
```sql
UPDATE [b] SET [Details].modify('$.Views', JSON_VALUE([b].[Details], '$.Views' RETURNING int) + 1)
FROM [Blogs] AS [b]
```

Efficient `JSON_MODIFY` rather than loading and rewriting the whole JSON document.

## 💻 `ExecuteDeleteAsync`

```csharp
var deleted = await ctx.Sessions
    .Where(s => s.ExpiresUtc < DateTime.UtcNow)
    .ExecuteDeleteAsync();
```

**⚡ Generated SQL:**
```sql
DELETE FROM [s] FROM [Sessions] AS [s] WHERE [s].[ExpiresUtc] < @now
```

Combine with the `Where` clause to scope the delete however you like.

## ⚖️ Trade-offs

**Pros:** one round-trip; no change-tracker overhead; uses the database optimizer; atomic;
LINQ-shaped + parameterized.
**Cons:** **change tracker is bypassed** — already-tracked entities won't know about the change;
no per-entity business logic in C#; **doesn't trigger SaveChanges interceptors / audit logic**
that runs through the change tracker (you may need to add audit columns in the same statement).

## 🚫 Common mistakes

```csharp
// ❌ Expecting tracked entities to reflect the bulk change
var blog = await ctx.Blogs.SingleAsync(b => b.Id == id);
await ctx.Blogs.Where(b => b.Id == id).ExecuteUpdateAsync(s => s.SetProperty(b => b.Title, "X"));
Console.WriteLine(blog.Title);   // STILL the old value — tracked entity is stale
// ✅ refresh: await ctx.Entry(blog).ReloadAsync();

// ❌ Forgetting that interceptors don't see ExecuteUpdate
// ✅ if you rely on a SaveChanges interceptor for audit columns, set them in the SetProperty list too

// ❌ ExecuteUpdate while inside a SaveChanges transaction without thinking
// ✅ generally fine; just be aware of the same-transaction visibility rules
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 7:** introduced `ExecuteUpdateAsync` / `ExecuteDeleteAsync`.
- **EF 8:** stable, primary-constructor friendly.
- **EF 9:** added support for **complex-type properties** (must specify each member explicitly).
- **EF 10:** **non-expression lambdas** ✨; **JSON-mapped complex properties** via efficient
  `JSON_MODIFY`; simpler parameter names in the emitted SQL.

## 🌍 Real-world production tips

- **Default to `ExecuteUpdate` / `ExecuteDelete`** for set-based maintenance jobs (cleanups,
  status toggles, counter increments).
- **Re-attach or reload** any in-memory entities that may now be stale.
- Combine with **transactions** when bulk operations cross multiple statements that must commit
  together.
- For huge inserts, `ExecuteUpdate` doesn't help — see
  [Bulk Operations Performance](../05-Performance/04.Bulk-Operations-Performance.md).

## 🎯 Practice (with full solutions)

### 1. Archive in one statement — `Easy`
**Smelly code:** the load-mutate-save loop from The Problem.
**Solution:**
```csharp
var rows = await ctx.Orders
    .Where(o => o.PlacedUtc < cutoff)
    .ExecuteUpdateAsync(s => s
        .SetProperty(o => o.Status, "Archived")
        .SetProperty(o => o.UpdatedUtc, DateTime.UtcNow));
```
**Why it's better:** zero entities materialized, one round-trip, one SQL statement, atomic.

### 2. Conditional bulk update (EF 10) — `Medium`
**Task:** Reset `Views` on every blog; *also* reset `Title` when the caller passes a flag.
**Solution (EF 10 non-expression lambda):**
```csharp
public async Task ResetAsync(BloggingContext ctx, bool resetName) {
    await ctx.Blogs.ExecuteUpdateAsync(s => {
        s.SetProperty(b => b.Views, 0);
        if (resetName) s.SetProperty(b => b.Title, "");
    });
}
```
**Why it's better:** no expression-tree gymnastics; the `if` is just a normal C# `if`.

### 3. Increment a JSON property — `Medium` (EF 10)
**Task:** Increment `Blog.Details.Views` (a JSON-mapped complex property).
**Solution:**
```csharp
await ctx.Blogs.ExecuteUpdateAsync(s =>
    s.SetProperty(b => b.Details.Views, b => b.Details.Views + 1));
```
**Why it's better:** uses `JSON_MODIFY` server-side — no read-modify-write of the whole document.

## ✅ Key Takeaways

- `ExecuteUpdateAsync` / `ExecuteDeleteAsync` ship **one server-side SQL statement** — no entity
  loaded, no change tracker.
- Computations like `Stock - 1` happen in **SQL**, atomically.
- **EF 10:** non-expression lambdas (conditional sets) and **JSON-mapped complex properties** via
  `JSON_MODIFY`.
- **Already-tracked entities won't reflect bulk changes** — reload if needed.
- For multi-step atomic work, combine with **explicit transactions**.
