# Setting Up EF Core (EF 10 / .NET 10)

## 🧠 Intuition

Three things make an EF Core project work: **a .NET project that targets .NET 10**, **the EF Core
runtime + provider NuGet packages**, and **the `dotnet ef` CLI tool** for migrations. Once those
are in place, you write a `DbContext`, register it in DI, and you're querying.

> 💡 Skip the IDE wizards once and do it from the command line — you only need this five-minute
> dance once per project, and after that you understand exactly which package does what.

## 📐 The package landscape

EF is split across several NuGet packages so you only depend on what you use:

| Package | What it gives you |
|---------|-------------------|
| `Microsoft.EntityFrameworkCore` | The core runtime, change tracker, LINQ provider |
| `Microsoft.EntityFrameworkCore.SqlServer` | The **SQL Server provider** (our default) |
| `Microsoft.EntityFrameworkCore.Design` | Design-time pieces that `dotnet ef` calls into |
| `Microsoft.EntityFrameworkCore.Tools` | PowerShell cmdlets if you use Package Manager Console (optional) |
| `Microsoft.EntityFrameworkCore.Sqlite` | SQLite provider — handy for tests |
| `Npgsql.EntityFrameworkCore.PostgreSQL` | PostgreSQL provider |
| `Microsoft.EntityFrameworkCore.Cosmos` | Azure Cosmos DB provider |

You install **core + one provider + Design**, and add **Tools** as a global CLI tool.

## 💻 Setting up a fresh project

### 1. Create the project (.NET 10)

```bash
dotnet new console -n MyApp -f net10.0
cd MyApp
```

For a web app: `dotnet new web` or `dotnet new webapi`. The EF setup is identical.

### 2. Install the EF Core 10 packages

```bash
dotnet add package Microsoft.EntityFrameworkCore --version 10.0.*
dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 10.0.*
dotnet add package Microsoft.EntityFrameworkCore.Design --version 10.0.*
```

> ℹ️ Use `10.0.*` to float to the latest patch on EF Core 10. If you're targeting EF 8 LTS, swap
> the version range — same package names.

### 3. Install the `dotnet ef` CLI globally (once per machine)

```bash
dotnet tool install --global dotnet-ef
# or update an existing one:
dotnet tool update --global dotnet-ef
```

Verify:
```bash
dotnet ef --version
```
You should see `Entity Framework Core .NET Command-line Tools 10.x.x`.

## 💻 Your first `DbContext`

A `DbContext` is your handle to the database. The minimum:

```csharp
using Microsoft.EntityFrameworkCore;

public class Blog {
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public int Views { get; set; }
}

public class BloggingContext : DbContext {
    public DbSet<Blog> Blogs => Set<Blog>();

    public BloggingContext(DbContextOptions<BloggingContext> options) : base(options) { }
}
```

A few choices worth pointing out:
- **`DbSet<Blog>` via `Set<Blog>()`** — avoids the nullability warning you'd get on `public DbSet<Blog> Blogs { get; set; }`.
- **Constructor takes `DbContextOptions<T>`** — so the provider, connection string, and other
  options can be injected from the host. This is the modern, DI-friendly pattern.

## 💻 Registering it in DI (the standard host)

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var builder = Host.CreateApplicationBuilder(args);
builder.Services.AddDbContext<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
using var host = builder.Build();
```

Connection string in `appsettings.json`:

```json
{
  "ConnectionStrings": {
    "Default": "Server=(localdb)\\mssqllocaldb;Database=Blogging;Trusted_Connection=True;TrustServerCertificate=True"
  }
}
```

> 🔐 Real connection strings shouldn't live in committed files. Use **user secrets in dev**
> (`dotnet user-secrets`) and **Key Vault / app config in production** — see
> [Configuration & Connection Strings](../06-Production/02.Configuration-and-Connection-Strings.md).

## 💻 First migration + database

```bash
dotnet ef migrations add InitialCreate
dotnet ef database update
```

`migrations add` generates a class describing the schema delta; `database update` applies it. You
now have a `Blogs` table with `Id` (identity PK) and `Title` / `Views` columns.

## ⚖️ Common setup mistakes

```csharp
// ❌ Wiring options inside the context — works, but bypasses DI and complicates testing/multi-env
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder) {
    optionsBuilder.UseSqlServer("hardcoded-connection-string");
}

// ✅ Inject options via constructor; the host owns the connection string
public BloggingContext(DbContextOptions<BloggingContext> options) : base(options) { }
```

Other classics:
- Forgetting to install `Microsoft.EntityFrameworkCore.Design` — you'll see *"Your startup project
  doesn't reference Microsoft.EntityFrameworkCore.Design"* when running `dotnet ef`.
- Mixing major EF versions across packages — keep `EntityFrameworkCore`, the provider, and `Design`
  on the **same major.minor**.
- Treating the `DbContext` as a singleton — it's designed to be **scoped** (one per request/unit of
  work). See [DI](../06-Production/01.Dependency-Injection.md).

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8 (LTS, Nov 2023 → Nov 2026):** the first version with **complex types** and **primitive
  collections**; introduced `Database.SqlQuery<T>` for raw-SQL primitive results.
- **EF 9 (STS, Nov 2024 → Nov 2026):** added **MSBuild integration** to compile your model at build
  time (`<EFOptimizeContext>true</EFOptimizeContext>` in your `.csproj`) for faster startup.
- **EF 10 (LTS, Nov 2025 → Nov 2028):** requires **.NET 10**; introduces **vector data**, **SQL
  Server 2025 JSON type**, **LeftJoin/RightJoin** LINQ operators, **named query filters**, and
  many more (see [What's New in EF 10](../08-Whats-New/01.EF-Core-10.md)).

## 🎯 Practice (with full solutions)

### 1. Spot the wiring bug — `Easy`
**Smelly code:**
```csharp
public class BloggingContext : DbContext {
    public DbSet<Blog> Blogs { get; set; }
    protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder) {
        optionsBuilder.UseSqlServer("Server=...;Password=hunter2;...");
    }
}
```
**Task:** explain the two problems and rewrite cleanly.
**Solution:** (a) connection string hard-coded in source (leak risk + can't vary per environment);
(b) `OnConfiguring` bypasses DI, so this context can't take options from the host. Rewrite:
```csharp
public class BloggingContext : DbContext {
    public DbSet<Blog> Blogs => Set<Blog>();
    public BloggingContext(DbContextOptions<BloggingContext> options) : base(options) { }
}
// in Program.cs:
builder.Services.AddDbContext<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
```
**Why it's better:** secrets live in config (user secrets / Key Vault), and the host controls the
provider, connection, and lifetime.

### 2. Build it from scratch — `Easy`
**Task:** From an empty folder, produce a console app that connects to LocalDB, creates a `Blog`
table via migration, and prints `"Tables created"`.
**Solution sketch:**
```bash
dotnet new console -n DemoEF -f net10.0
cd DemoEF
dotnet add package Microsoft.EntityFrameworkCore --version 10.0.*
dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 10.0.*
dotnet add package Microsoft.EntityFrameworkCore.Design --version 10.0.*
dotnet tool install --global dotnet-ef   # if not already
```
```csharp
// Program.cs
using Microsoft.EntityFrameworkCore;

using var ctx = new DemoContext();
ctx.Database.EnsureCreated();   // OK for the demo; use migrations in real projects
Console.WriteLine("Tables created");

public class Blog { public int Id { get; set; } public string Title { get; set; } = ""; }
public class DemoContext : DbContext {
    public DbSet<Blog> Blogs => Set<Blog>();
    protected override void OnConfiguring(DbContextOptionsBuilder o) =>
        o.UseSqlServer(@"Server=(localdb)\mssqllocaldb;Database=Demo;Trusted_Connection=True;TrustServerCertificate=True");
}
```
Run with `dotnet run`. `EnsureCreated()` is for tiny demos only — switch to
`dotnet ef migrations add ...` for any real project.

## ✅ Key Takeaways

- Setup = **.NET 10 project + EF Core 10 + a provider + Design + `dotnet ef` CLI**.
- Define a `DbContext`, take `DbContextOptions<T>` in the constructor, register it in DI.
- Keep **connection strings out of source** — config, user secrets, Key Vault.
- Use **migrations** for real projects; `EnsureCreated()` is demo-only.
- Don't mix EF major.minor versions across packages.
