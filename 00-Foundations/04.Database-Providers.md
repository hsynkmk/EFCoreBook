# Database Providers

## 🧠 Intuition

EF Core's core is provider-agnostic — it doesn't know SQL Server from PostgreSQL. The **provider**
package is what teaches it the specific dialect: which functions exist, how identity columns work,
how JSON is stored, which LINQ operators it can translate. You pick one provider per `DbContext`
(plus the in-memory ones for tests).

> 💡 **Analogy — adapters in a power strip.** The same `DbContext` "plugs into" different
> databases by swapping the adapter. Your LINQ stays the same; the emitted SQL changes.

This page is a tour of the providers you'll actually meet. The course defaults to **SQL Server**.

## 📐 The major providers

| Provider | Package | Best for | Notes |
|----------|---------|----------|-------|
| **SQL Server / Azure SQL** | `Microsoft.EntityFrameworkCore.SqlServer` | Most .NET shops; this course's default | EF 10 unlocks **vector** + **SQL 2025 JSON type** on Azure SQL / SQL Server 2025 |
| **PostgreSQL** | `Npgsql.EntityFrameworkCore.PostgreSQL` | Open-source-first stacks, native `jsonb`/arrays | Excellent JSON support; native array/range types |
| **SQLite** | `Microsoft.EntityFrameworkCore.Sqlite` | Local dev, mobile, integration tests | Single file or in-memory; tiny |
| **Cosmos DB (NoSQL)** | `Microsoft.EntityFrameworkCore.Cosmos` | Document store, global distribution | Massively improved in EF 9; **full-text + vector** in EF 10 |
| **InMemory** | `Microsoft.EntityFrameworkCore.InMemory` | Unit tests **only** | Doesn't model SQL semantics (FKs, transactions, isolation). Don't trust it for real bugs |

There are community providers for MySQL/MariaDB (`Pomelo`), Oracle, Firebird, and more — same
`DbContext` pattern, different package.

## 💻 Switching providers

It's almost always **one line of configuration**:

```csharp
// SQL Server (course default)
opt.UseSqlServer(connectionString);

// Azure SQL — EF 9+ gives you SQL Server features tuned for Azure SQL
opt.UseAzureSql(connectionString);

// PostgreSQL
opt.UseNpgsql(connectionString);

// SQLite
opt.UseSqlite("Data Source=app.db");

// SQLite in-memory (for tests — keep the connection OPEN for the lifetime)
opt.UseSqlite("Filename=:memory:");

// Azure Cosmos DB
opt.UseCosmos("AccountEndpoint=...;AccountKey=...", databaseName: "MyDb");

// InMemory (tests only — see warnings below)
opt.UseInMemoryDatabase("test-db");
```

## ⚖️ Things providers differ on (the senior gotchas)

| Concept | SQL Server | PostgreSQL | SQLite |
|---------|-----------|------------|--------|
| Identity | `IDENTITY(1,1)` | `SERIAL` / `GENERATED IDENTITY` | `INTEGER PRIMARY KEY` |
| JSON | `nvarchar(max)` / **new `json` type** (SQL Server 2025) | Native `jsonb` (mature) | `text` with JSON funcs |
| Arrays | No (use JSON or `OPENJSON`) | **Native arrays** | No |
| Strings | `nvarchar(max)` | `text` | `text` |
| Booleans | `bit` | `boolean` | `0`/`1` |
| Case sensitivity | Case-insensitive by default | Case-sensitive | Configurable |
| `DateOnly` / `TimeOnly` | EF 8+ via `date` / `time` | EF 8+ via `date` / `time` | EF 8+ |
| HierarchyId | EF 8+ (SQL Server only) | n/a | n/a |
| Vector (AI) | EF 10 + SQL Server 2025 / Azure SQL | Use `pgvector` extension (community) | n/a |
| Full-text search | Yes (CONTAINS/FREETEXT) | Yes (`tsvector`) | FTS5 |

> ⚠️ "Provider-agnostic code" is largely a myth past simple CRUD. The moment you use features above
> the lowest common denominator (JSON, arrays, HierarchyId, vector, FTS), your code becomes
> provider-specific. **Pick a primary provider** and keep alternatives only when there's a real
> reason.

## 🚫 The InMemory provider — what it is, why it lies

The InMemory provider stores data in a `Dictionary<TKey, TEntity>`. Tests are fast — but **it
doesn't model relational behavior**:

- No foreign-key enforcement (you can leave dangling references).
- No transactions/isolation levels.
- No unique-constraint enforcement on multi-column keys in older versions.
- No real SQL — so LINQ that throws on a real database may silently succeed here.

> ✅ For unit tests of EF code, prefer **SQLite in-memory** — it's a real relational engine.
> See [Unit Testing DbContext](../07-Testing/02.Unit-Testing-DbContext.md).

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** introduced **complex types**, **JSON columns**, **primitive collections**,
  **HierarchyId** (SQL Server), and `DateOnly`/`TimeOnly` mapping across providers.
- **EF 9:** **Cosmos provider rewritten** (`$type` discriminator, simplified `id`, partition-key
  extraction, `ToPageAsync`); **`UseAzureSql`** / **`UseAzureSynapse`**; MSBuild-integrated
  compiled model for faster startup.
- **EF 10:** SQL Server 2025 **`json` data type** auto-used when targeting Azure SQL or
  compatibility ≥ 170; **vector** data type + `VECTOR_DISTANCE()` for SQL Server 2025 / Azure SQL;
  Cosmos **full-text search** + vector model API renamed (`IsVectorProperty`, `IsVectorIndex`).

## 🌍 Real-world picking guide

| Situation | Recommend |
|-----------|-----------|
| .NET shop, Microsoft stack, on-prem or Azure | **SQL Server / Azure SQL** |
| Open-source-first stack, heavy JSON or arrays, cost-sensitive | **PostgreSQL** |
| Local dev, mobile/desktop apps, deterministic CI tests | **SQLite** |
| Massive-scale document store, geo distribution, AI/RAG | **Cosmos DB** |
| Real bugs from real SQL in unit tests | **SQLite in-memory** (not InMemory provider) |
| Integration tests against your prod engine | **Testcontainers** (see Module 07) |

## 🎯 Practice (with full solutions)

### 1. Match the provider — `Easy`
**Task:** Pick a provider for each: (a) team building an MVP for a SaaS dashboard on Azure;
(b) a mobile app that should work offline; (c) an AI semantic-search service over 10M product
descriptions; (d) the test suite for that AI service.
**Solution:**
(a) **Azure SQL** via `UseAzureSql` — EF 9+ gives Azure-tuned SQL out of the box.
(b) **SQLite** — single file, runs anywhere, ships with the app.
(c) **SQL Server 2025 / Azure SQL with EF 10 vector** (or Cosmos if you also need global
   distribution) — vector data is now first-class in EF 10.
(d) **SQLite in-memory** for unit tests, **Testcontainers + the real provider** for integration
   tests. Don't unit-test vector code on InMemory.
**Why it matters:** the provider is a *load-bearing* decision — affects feature availability,
testing strategy, and cost.

### 2. Avoid the InMemory trap — `Medium`
**Smelly code:** Tests pass green using `UseInMemoryDatabase`, but production fails with
`FOREIGN KEY constraint failed` because a test creates a `Post` referencing a non-existent
`BlogId`.
**Task:** swap to a provider that catches the bug at test time.
**Solution:**
```csharp
var connection = new SqliteConnection("Filename=:memory:");
connection.Open();   // keep open for lifetime
var options = new DbContextOptionsBuilder<BloggingContext>()
    .UseSqlite(connection)
    .Options;

using var ctx = new BloggingContext(options);
ctx.Database.EnsureCreated();
// ... your test now runs against a real relational engine with FK enforcement
```
**Why it's better:** SQLite in-memory is **a real relational database** in 50ms. It catches FK,
unique-constraint, and SQL-syntax bugs the InMemory provider lets through.

## ✅ Key Takeaways

- The **provider** package is what teaches EF a specific dialect — pick one per `DbContext`.
- This course defaults to **SQL Server / Azure SQL**; PostgreSQL/SQLite/Cosmos are first-class
  alternatives with their own strengths.
- **Provider-agnostic code is a myth past simple CRUD** — feature availability varies (JSON,
  arrays, HierarchyId, vector, FTS).
- The **InMemory provider** is fast but lies — use **SQLite in-memory** for tests instead.
- EF 9 added `UseAzureSql`; EF 10 unlocked **vector** + **SQL 2025 JSON** + **Cosmos full-text**.
