# Your First CRUD with EF Core 10

> A complete end-to-end walkthrough. By the end you'll have inserted, queried, updated, and deleted
> data — and seen the SQL EF emits for each.

## 🧠 Intuition

CRUD = **Create, Read, Update, Delete** — the four basic data operations. EF Core makes each one
feel like working with C# collections (`Add`, query with LINQ, mutate, `Remove`), with one extra
step: **call `SaveChangesAsync()`** to flush pending changes to the database in one batched
transaction.

> 💡 Think of the `DbContext` as a *unit of work*. You stage all the changes you want, then commit
> them together. That's what `SaveChangesAsync` does.

## 📐 The Model We'll Use

```csharp
public class Blog {
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public int Views { get; set; }
    public List<Post> Posts { get; set; } = new();   // navigation to children
}

public class Post {
    public int Id { get; set; }
    public string Heading { get; set; } = "";
    public int BlogId { get; set; }                  // FK to Blog
    public Blog Blog { get; set; } = null!;          // navigation back
}

public class BloggingContext : DbContext {
    public DbSet<Blog> Blogs => Set<Blog>();
    public DbSet<Post> Posts => Set<Post>();
    public BloggingContext(DbContextOptions<BloggingContext> options) : base(options) { }
}
```

EF infers the relationship from the `BlogId` foreign key and the navigations — see
[Relationships](../01-Modeling-Data/03.Relationships.md) for the full story.

## 💻 Create

```csharp
public async Task AddBlogAsync(BloggingContext ctx) {
    var blog = new Blog {
        Title = ".NET News",
        Posts = { new Post { Heading = "EF 10 ships" } }   // child added in one shot
    };
    ctx.Blogs.Add(blog);                                   // staged, not yet in DB
    await ctx.SaveChangesAsync();                          // INSERT batch + transaction
    Console.WriteLine($"New blog id: {blog.Id}");          // EF fills in the identity
}
```

**⚡ SQL EF emits (SQL Server):**
```sql
SET IMPLICIT_TRANSACTIONS OFF; SET NOCOUNT ON;
INSERT INTO [Blogs] ([Title], [Views]) OUTPUT INSERTED.[Id] VALUES (@p0, @p1);
INSERT INTO [Posts] ([BlogId], [Heading]) OUTPUT INSERTED.[Id] VALUES (@p2, @p3);
```

> EF batches multiple inserts inside an automatic transaction and uses `OUTPUT INSERTED` (SQL
> Server's efficient "return the generated ID" mechanism). On PostgreSQL it uses `RETURNING`.

## 💻 Read

```csharp
// All blogs (read-only → no tracking)
var allBlogs = await ctx.Blogs.AsNoTracking().ToListAsync();

// Filter + project to a slim shape (only the columns you need leave the database)
var summaries = await ctx.Blogs
    .Where(b => b.Views > 1000)
    .OrderByDescending(b => b.Views)
    .Select(b => new { b.Id, b.Title })
    .ToListAsync();

// A single entity by primary key — convenience helper
var blog = await ctx.Blogs.FindAsync(42);

// With its posts (eager loading)
var withPosts = await ctx.Blogs
    .Include(b => b.Posts)
    .SingleAsync(b => b.Id == 42);
```

**⚡ SQL EF emits for the projection query:**
```sql
SELECT [b].[Id], [b].[Title]
FROM [Blogs] AS [b]
WHERE [b].[Views] > 1000
ORDER BY [b].[Views] DESC
```

Notice: only `Id` and `Title` come back — the projection lets EF emit a narrower `SELECT`. Read
[Basic Queries](../02-Querying/01.Basic-Queries.md) for the full set of LINQ tricks, and
[No-Tracking](../02-Querying/08.No-Tracking-and-Identity-Resolution.md) for when to use
`AsNoTracking()`.

## 💻 Update

```csharp
public async Task BumpViewsAsync(BloggingContext ctx, int blogId) {
    var blog = await ctx.Blogs.FirstAsync(b => b.Id == blogId);   // tracked
    blog.Views++;                                                  // mutate in memory
    await ctx.SaveChangesAsync();                                  // EF detects the change
}
```

**⚡ SQL EF emits:**
```sql
UPDATE [Blogs] SET [Views] = @p0 WHERE [Id] = @p1;
```

EF compared the original values it remembered (the "change tracker") with the new ones and emitted
**only the changed column**.

> 🚀 For "update many rows without loading them," prefer **`ExecuteUpdateAsync`** (EF 7+,
> dramatically improved in EF 10) — see [Bulk Operations](../03-Saving-and-Concurrency/05.Bulk-Operations.md).

## 💻 Delete

```csharp
public async Task DeleteBlogAsync(BloggingContext ctx, int blogId) {
    var blog = await ctx.Blogs.FindAsync(blogId);
    if (blog is null) return;
    ctx.Blogs.Remove(blog);
    await ctx.SaveChangesAsync();
}
```

**⚡ SQL:**
```sql
DELETE FROM [Blogs] WHERE [Id] = @p0;
```

If the relationship is configured for cascade delete (which EF infers for required relationships),
the dependent `Posts` rows are deleted by the database automatically — see
[Cascade Delete](../03-Saving-and-Concurrency/04.Cascade-Delete.md).

For "delete many without loading," use `ExecuteDeleteAsync`:
```csharp
await ctx.Blogs.Where(b => b.Views == 0).ExecuteDeleteAsync();
```
**⚡ SQL (one round-trip, no entities loaded):**
```sql
DELETE FROM [b] FROM [Blogs] AS [b] WHERE [b].[Views] = 0;
```

## ⚖️ Things to notice already

| Behavior | What it tells you |
|----------|-------------------|
| `SaveChangesAsync` batches & wraps in a transaction | You don't pay a round-trip per change |
| EF emitted `UPDATE … SET [Views] = …` for **just** the changed column | The change tracker is doing useful work |
| Querying `AsNoTracking()` skips that work | Free perf win for read-only paths |
| `Include` controlled what came back | Loading strategy is a deliberate choice, not magic |

These four observations are the seeds of the whole rest of the course.

## 🌍 Real-world production tips

- **Always use the `*Async` overloads** in server code. Sync calls block a thread per request.
- **Project to slim DTOs** when you don't need the whole entity (`Select(b => new BlogDto(...))`).
- **`AsNoTracking()` on read-only paths.** It's the most common one-line perf improvement.
- **Don't share a `DbContext` across requests/threads.** Scope it per request. EF's `DbContext` is
  *not* thread-safe.
- **Don't call `SaveChanges()` in a loop** — gather your changes, save once. Or use bulk operations.

## 🎯 Practice (with full solutions)

### 1. Add a blog and a post in one save — `Easy`
**Task:** Insert a blog with two posts in one round-trip and print the generated IDs.
**Solution:**
```csharp
var blog = new Blog {
    Title = "EF Diaries",
    Posts = {
        new Post { Heading = "Day one" },
        new Post { Heading = "Day two" },
    }
};
ctx.Blogs.Add(blog);
await ctx.SaveChangesAsync();
Console.WriteLine($"Blog {blog.Id}, posts: {string.Join(",", blog.Posts.Select(p => p.Id))}");
```
**Why it's better:** because the relationship is configured, EF inserts the blog first, captures
its generated `Id`, and uses it for the posts' `BlogId`. One `SaveChangesAsync` = one transaction.

### 2. Read efficiently — `Easy`
**Smelly code:**
```csharp
var blogs = await ctx.Blogs.ToListAsync();           // pulls EVERY column for EVERY blog
var titles = blogs.Select(b => b.Title).ToList();    // and we only wanted the titles
```
**Task:** rewrite to pull only what's needed.
**Solution:**
```csharp
var titles = await ctx.Blogs
    .Select(b => b.Title)
    .ToListAsync();
```
**Why it's better:** EF emits `SELECT [b].[Title] FROM [Blogs] AS [b]` — only one column over the
wire, no tracking overhead.

### 3. Delete without loading — `Medium`
**Task:** Delete all blogs whose `Views == 0` without instantiating them in memory.
**Solution:**
```csharp
var deleted = await ctx.Blogs.Where(b => b.Views == 0).ExecuteDeleteAsync();
Console.WriteLine($"Removed {deleted} blogs");
```
**Why it's better:** one `DELETE` statement, no change tracker, no entities materialized. Ideal
for "cleanup" jobs. (Full story in [Bulk Operations](../03-Saving-and-Concurrency/05.Bulk-Operations.md).)

## ✅ Key Takeaways

- CRUD = `Add` / LINQ query / mutate / `Remove`, then `SaveChangesAsync()`.
- `SaveChangesAsync` **batches** and wraps in a **transaction** automatically.
- EF only updates the **columns that changed** (thanks to the change tracker).
- For read-only paths: `AsNoTracking()` + projection.
- For "many rows" writes/deletes: `ExecuteUpdateAsync` / `ExecuteDeleteAsync`.

2. Why does the `UPDATE` emit only the columns that changed?
3. When should you reach for `ExecuteDeleteAsync` instead of `Remove`?
