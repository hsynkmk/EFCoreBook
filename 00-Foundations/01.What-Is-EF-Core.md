# What Is EF Core? The Big Picture

## 🧠 Intuition

Entity Framework Core (EF Core) is an **Object-Relational Mapper (ORM)**: it lets you work with
your database using **C# classes and LINQ** instead of writing SQL by hand. You declare what your
data looks like (entities and a `DbContext`); EF translates your queries into SQL, sends them to
the database, materializes results back into objects, and tracks the changes you make so it can
save them.

> 💡 **Analogy — a translator at a meeting.** You speak C#; the database speaks SQL. EF sits
> between them: you ask "give me all blogs where Views > 1000," it asks the database in SQL,
> brings back rows, and reconstructs them as `Blog` objects you can use. You never wrote a
> `SELECT`.

Two things follow from that analogy:
1. **EF is a leaky abstraction over SQL — in a good way.** You can ignore SQL until you can't.
   Senior EF developers can always read what EF emits and predict it from the LINQ.
2. **There's runtime work involved** — translation, change tracking, materialization. Some
   features (lazy loading, tracking) cost cycles. Knowing the costs is the rest of this course.

## 🧾 What you get with EF Core

| Feature | What it means |
|---------|---------------|
| **LINQ queries** | Query in C# (`context.Blogs.Where(b => b.Views > 1000)`) instead of strings |
| **Change tracking** | Modify objects in memory; call `SaveChanges()`; EF figures out the right INSERTs/UPDATEs/DELETEs |
| **Migrations** | Evolve the schema with versioned `dotnet ef migrations` scripts checked into source |
| **Provider model** | Same code over **SQL Server**, **PostgreSQL**, **SQLite**, **Cosmos**, and more |
| **Modern features** | JSON columns, complex types, primitive collections, HierarchyId, vector data (EF 8/9/10) |

## 🆚 EF Core vs Dapper vs Raw ADO.NET

A senior question: *"why would you use EF over Dapper?"* — and the inverse.

| | **EF Core** | **Dapper** | **Raw ADO.NET** |
|--|-------------|------------|-----------------|
| Style | LINQ + objects + tracking | "Micro-ORM": maps `SELECT` results to objects | You write everything by hand |
| You write | Entity classes + LINQ | SQL strings + small POCOs | SQL + `SqlCommand` + manual reading |
| Query translation | LINQ → SQL (you don't see it unless you log) | None — you write the SQL | None |
| Change tracking | Yes, automatic | No (you write the `UPDATE`) | No |
| Migrations | Built-in | None | None |
| Best for | Most line-of-business apps, complex domains, multi-DB targets | Hot read paths, dashboards, "give me the rows fast" | Niche perf, drivers, very simple tools |
| Trade-off | Magic + speed of development | Control + simplicity | Total control + total effort |

> 💡 You'll often **use both** in one app: EF for the domain model and most operations, Dapper for
> a few hand-tuned reporting queries. See [Module 09 — EF vs Dapper vs Raw](../09-Beyond/02.EF-vs-Dapper-vs-Raw.md).

## ✅ When EF Core is a great choice

- Line-of-business apps with a rich domain model.
- You want **migrations, change tracking, and DI** out of the box.
- You'll target multiple providers (e.g. SQL Server in prod, SQLite for tests).
- The team values **maintainability** over the last 10% of perf.

## 🚫 When EF Core is the *wrong* tool

- A **single hot query** that needs sub-millisecond latency on millions of rows — write it in
  Dapper or raw SQL.
- **Heavy reporting / OLAP**, especially complex pivots or window functions outside EF's translation
  set — go straight to SQL views, stored procedures, or a reporting tool.
- **Bulk data movement** (millions of rows per second) — use `SqlBulkCopy`, `COPY` (Postgres), or a
  dedicated ETL.
- An **ultra-simple** app where adding EF is more code than the queries themselves.

> ⚠️ The "EF Core is slow" complaint is usually one of: tracking when read-only, **N+1** with
> lazy/eager misuse, or doing in-memory filtering after `.ToList()`. Almost all of it is fixable —
> see [05 — Performance](../05-Performance/README.md).

## 🏷️ Concepts you'll meet (defined once, used everywhere)

- **Entity** — a C# class mapped to a table (or a JSON document, or a Cosmos container).
- **`DbContext`** — your session with the database. Holds the configuration, the **change tracker**,
  and `DbSet<T>` collections per entity type.
- **`DbSet<T>`** — the typed "table" you query against.
- **LINQ to entities** — LINQ queries EF translates to SQL.
- **Provider** — the package that knows how to talk to a specific database engine (SQL Server,
  PostgreSQL, SQLite, Cosmos…). You pick one per `DbContext`.
- **Migration** — a versioned schema change generated by `dotnet ef migrations add`.
- **Tracking** — EF watching an entity instance so it can detect changes for `SaveChanges()`.

You'll meet each of these in depth in later modules; this is just the vocabulary.

## 🌍 Where EF runs

EF Core targets the modern .NET runtime. **EF Core 10 (Nov 2025) is an LTS release supported until
November 2028 and requires the .NET 10 SDK and runtime.** EF 8 (also LTS, supported until Nov 2026)
remains a popular target for conservative teams. This course defaults to **EF Core 10**, and every
file calls out EF 8 / 9 differences explicitly so you can follow along on either version.

## 🎯 Practice (with full solutions)

### 1. Pick the right tool — `Easy`
**Scenario:** Decide EF / Dapper / raw SQL for each:
- (a) A B2B SaaS admin panel with ~30 CRUD screens.
- (b) A nightly report that aggregates 500M rows across 12 joins for a CSV export.
- (c) A read endpoint serving cached "trending products" hit 10,000×/sec.
**Solution:**
(a) **EF Core** — many entities, lots of CRUD, migrations and DI pay off immediately.
(b) **Raw SQL / a SQL view / a separate analytics tool.** EF will likely translate this query
   inefficiently or not at all; even if it does, you don't gain from change tracking on a one-shot
   export.
(c) **EF for the model + a Dapper/cached read path for this endpoint.** Most apps end up mixed —
   EF for write-side richness, hand-tuned read paths for hot endpoints.
**Why it matters:** "Which tool?" is a senior question. EF isn't always the answer.

### 2. Read the abstraction — `Easy`
**Task:** Without writing code, predict the SQL EF will emit for this LINQ query:
```csharp
var dotNetBlogs = await context.Blogs
    .Where(b => b.Title.StartsWith(".NET"))
    .OrderByDescending(b => b.Views)
    .Take(10)
    .Select(b => new { b.Id, b.Title })
    .ToListAsync();
```
**Solution:** roughly
```sql
SELECT TOP(10) [b].[Id], [b].[Title]
FROM [Blogs] AS [b]
WHERE [b].[Title] LIKE N'.NET%'
ORDER BY [b].[Views] DESC
```
EF translates `Where` → `WHERE`, `OrderByDescending` → `ORDER BY ... DESC`, `Take(10)` → `TOP(10)`
(SQL Server) or `LIMIT 10` (PostgreSQL/SQLite), and `Select` to a column list — so only `Id` and
`Title` come back over the wire, not the whole row.
**Why it matters:** thinking in *both* LINQ and SQL is the senior EF mindset — and it's the entire
point of [Module 02 — Querying](../02-Querying/README.md).

## ✅ Key Takeaways

- EF Core is an **ORM**: LINQ + objects + tracking + migrations + DI, on top of SQL.
- It's a **leaky abstraction over SQL on purpose** — you can ignore SQL until you can't.
- It's the right default for most line-of-business apps; reach for **Dapper or raw SQL** for hot
  paths, heavy reporting, and bulk movement.
- This course targets **EF Core 10 (LTS, requires .NET 10)** with EF 8/9 callouts.
- Vocabulary to memorize: **entity, `DbContext`, `DbSet<T>`, provider, migration, tracking.**
