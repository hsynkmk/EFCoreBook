# DbContext Pooling

## 🧠 Intuition

Creating a `DbContext` isn't free: EF wires up the change tracker, internal services, and state on
every `new`. Under high request rates, that allocation adds up. **DbContext pooling** keeps a pool
of pre-created context instances and **resets + reuses** them across requests instead of building
a fresh one each time — cutting allocations and improving throughput on hot APIs.

> 💡 **Analogy — a rental counter that resets cars between customers** instead of manufacturing a
> new car per rental. Same context object, wiped clean, handed to the next request.

## 💻 Enabling it

```csharp
// Instead of AddDbContext:
builder.Services.AddDbContextPool<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")),
    poolSize: 1024);   // default is 1024
```

That's it. The context is still **scoped** per request; behind the scenes EF leases one from the
pool and returns it (reset) when the scope ends.

## 📐 What "reset" means

When a context returns to the pool, EF resets:
- The change tracker (clears tracked entities).
- Internal query state.

What it does **not** reset is **your own state** — any private fields, injected per-request values
captured in the constructor, or event handlers you attached. That's the crux of pooling's rules.

## ⚖️ The constraints (read these before enabling)

Pooling reuses context instances, so the context must be **stateless across requests**:

1. **No constructor injection of scoped services that vary per request** into the pooled context.
   The pool reuses instances; a captured `ITenantProvider` from request A could serve request B.
   - ✅ The pooled context's constructor may take only `DbContextOptions<T>`.
   - ✅ If you need per-request state (tenant, user), use the **pooling factory overload** that
     supports it, or read it via an interceptor / `IHttpContextAccessor` at use time — not capture
     it in the constructor.
2. **No mutable instance state** that should differ per request.
3. **`OnConfiguring` is not used** — configuration must come through the options delegate.

If your context needs per-request dependencies, either don't pool it, or use the EF API designed
for that (`AddPooledDbContextFactory` + a small wrapper) so EF manages the reset correctly.

## 💻 Pooled factory (for background work / per-operation contexts)

```csharp
builder.Services.AddPooledDbContextFactory<BloggingContext>(opt =>
    opt.UseSqlServer(cs));

// In a service:
public class ReportService {
    private readonly IDbContextFactory<BloggingContext> _factory;
    public ReportService(IDbContextFactory<BloggingContext> factory) => _factory = factory;
    public async Task RunAsync() {
        await using var ctx = await _factory.CreateDbContextAsync();   // leased from pool, reset on dispose
        // ...
    }
}
```

Great for parallel work, background services, and Blazor Server (where the scoped-per-request
model doesn't fit).

## 🚫 Common mistakes

```csharp
// ❌ Pooled context capturing a per-request value in its constructor
public class BloggingContext : DbContext {
    private readonly int _tenantId;
    public BloggingContext(DbContextOptions<BloggingContext> o, ITenantProvider t) : base(o)
        => _tenantId = t.Current;   // captured ONCE; wrong tenant after reuse
}
// ✅ either don't pool, or read tenant at query time (interceptor / accessor)

// ❌ Pooling but still overriding OnConfiguring
// ✅ pooling requires all config via the options delegate

// ❌ Assuming pooling fixes a slow query — it reduces allocation overhead, not query cost
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- Pooling has existed since EF Core 2.0; `AddPooledDbContextFactory` since EF 6.
- **EF 9 compiled model** + pooling together give the best cold-start *and* per-request numbers.
- **EF 10:** no pooling-specific change; the broader perf improvements (plan caching) compound.

## 🌍 Real-world production tips

- Pooling shines on **high-throughput APIs** with simple, stateless contexts. Measure — the win is
  in allocations/GC pressure, which matters most under load.
- If your context legitimately needs per-request state, **prefer reading it at use time** (an
  interceptor or `IHttpContextAccessor`) over constructor capture, so pooling stays safe.
- Pool size default (1024) is generous; tune only with evidence.
- Pooling does **not** change correctness for well-behaved (stateless) contexts — but it will
  *surface* hidden per-request state bugs. Treat a "works without pooling, breaks with pooling"
  bug as "my context has illegal state."

## 🎯 Practice (with full solutions)

### 1. Turn on pooling safely — `Easy`
**Task:** A stateless `BloggingContext` (constructor takes only options) on a high-traffic API.
**Solution:**
```csharp
builder.Services.AddDbContextPool<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
```
Confirm the context's only constructor is `BloggingContext(DbContextOptions<BloggingContext>)`.
**Why it's better:** lower per-request allocation and GC pressure under load — measurable on hot
endpoints — with no code changes elsewhere.

### 2. Diagnose a pooling bug — `Medium`
**Scenario:** After enabling pooling, some requests see another tenant's data intermittently.
**Task:** find and fix the cause.
**Solution:** the context captured `ITenantProvider.Current` in its constructor; pooled reuse
served a stale tenant. Fix by reading tenant at query time:
```csharp
// Remove the captured field. Apply tenant via a named query filter that reads a scoped accessor:
modelBuilder.Entity<Blog>().HasQueryFilter("Tenant", b => b.TenantId == _tenantAccessor.Current);
// where _tenantAccessor reads IHttpContextAccessor each call, not once in the constructor
```
**Why it's better:** the context holds no per-request state, so pooled reuse is safe; tenant is
resolved fresh on every query.

## ✅ Key Takeaways

- **DbContext pooling** reuses reset context instances to cut allocation overhead on hot paths.
- The context must be **stateless across requests** — only `DbContextOptions<T>` in the
  constructor, no captured per-request values, no `OnConfiguring`.
- Use **`AddPooledDbContextFactory`** for background/parallel/Blazor scenarios.
- Pooling improves **throughput/GC**, not individual query cost.
- A "breaks only with pooling" bug means your context has illegal per-request state.
