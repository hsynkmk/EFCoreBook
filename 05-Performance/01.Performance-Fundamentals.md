# Performance Fundamentals

## 🧠 Intuition

"EF Core is slow" is almost always "I used EF Core in a slow way." A handful of patterns cause the
vast majority of EF performance problems, and a handful of habits fix them. Master these and EF
often matches hand-written Dapper for the workloads it's meant for.

> 💡 The five fundamentals, in priority order: **(1) don't track what you won't save, (2) project
> to only the columns you need, (3) kill N+1, (4) filter and paginate in the database, (5) batch
> writes.** Everything else is a footnote.

## 🎯 The Problem — every anti-pattern in one method

```csharp
// ❌ A greatest-hits compilation of EF perf sins
public async Task<List<BlogDto>> GetRecentBlogDtos() {
    var blogs = await _ctx.Blogs.ToListAsync();                       // (1) loads & tracks EVERY blog, all columns
    var result = new List<BlogDto>();
    foreach (var b in blogs.Where(b => b.Views > 1000)) {            // (4) filters in memory
        var postCount = _ctx.Posts.Count(p => p.BlogId == b.Id);    // (3) N+1: one query per blog
        result.Add(new BlogDto(b.Id, b.Title, postCount));          // (2) only needed Id, Title, count
    }
    return result;
}
```

Ten thousand blogs → one giant `SELECT *` + 10,000 `COUNT` queries + everything tracked. The fix
is one tidy server-side query.

## 💻 The fix — one query, no tracking, projected, server-filtered

```csharp
public async Task<List<BlogDto>> GetRecentBlogDtos() =>
    await _ctx.Blogs
        .AsNoTracking()                                              // (1) no snapshots
        .Where(b => b.Views > 1000)                                  // (4) filter in SQL
        .Select(b => new BlogDto(b.Id, b.Title, b.Posts.Count()))   // (2)(3) project + count in SQL
        .ToListAsync();
```

**⚡ Generated SQL:**
```sql
SELECT [b].[Id], [b].[Title], (
    SELECT COUNT(*) FROM [Posts] AS [p] WHERE [b].[Id] = [p].[BlogId]) AS [PostCount]
FROM [Blogs] AS [b]
WHERE [b].[Views] > 1000
```

One round-trip, only three values per row, nothing tracked.

## 📐 The five fundamentals

### 1. Don't track read-only data
`AsNoTracking()` — skips snapshots and the identity map. See
[No-Tracking](../02-Querying/08.No-Tracking-and-Identity-Resolution.md).

### 2. Project to slim DTOs
`Select(b => new BlogDto(...))` — fewer columns over the wire, no entity materialization. The
biggest single lever after tracking.

### 3. Kill N+1
Loading a parent then querying children per-row. Fix with `Include`, projection, or
`AsSplitQuery`. See [Loading Strategies](../02-Querying/03.Loading-Strategies.md).

### 4. Filter & paginate in the database
Never `.ToList()` then `.Where()`. Put `Where`, `OrderBy`, `Skip`/`Take` *before* materializing.
Use keyset pagination for deep pages.

### 5. Batch writes
Don't `SaveChanges()` in a loop. `AddRange` + one save, or `ExecuteUpdate`/`ExecuteDelete` for
set-based changes. See [Bulk Operations](../03-Saving-and-Concurrency/05.Bulk-Operations.md).

## 💻 Async + streaming for large results

```csharp
// Don't buffer a huge result set into memory — stream it
await foreach (var blog in _ctx.Blogs.AsNoTracking().AsAsyncEnumerable()) {
    await ProcessAsync(blog);
}
```

`AsAsyncEnumerable()` processes rows as they arrive instead of materializing the whole list.

## ⚖️ Measuring (don't guess)

| Tool | What it tells you |
|------|-------------------|
| `TagWith` + logs | Which LINQ emitted which SQL |
| `ToQueryString()` | The SQL without running it |
| `LogTo` + duration | How long each command took |
| SQL Server `SET STATISTICS IO, TIME ON` / PG `EXPLAIN ANALYZE` | Reads, scans, plan |
| BenchmarkDotNet | Apples-to-apples C# micro-benchmarks |

See [Diagnosing Slow Queries](05.Diagnosing-Slow-Queries.md).

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8/9:** continuous translation + materialization perf improvements; read-only collections.
- **EF 9:** **MSBuild compiled model** (faster cold start); inlined uncorrelated subqueries (fewer
  round-trips).
- **EF 10:** **parameterized collection padding** (better plan caching for `IN (...)` queries),
  cleaner SQL, continued AOT/precompiled-query work.

## 🌍 Real-world production tips

- Adopt **`AsNoTracking` by default** on read-side services (`QueryTrackingBehavior.NoTracking`).
- **Project** in every read path that doesn't need full entities.
- Watch for **N+1 in logs** — repeated near-identical SELECTs are the tell.
- **Index** the columns your hot queries filter and sort on
  ([Indexes](../01-Modeling-Data/07.Indexes-and-Constraints.md)).
- **Profile before optimizing.** The slow thing is rarely where you think.

## 🎯 Practice (with full solutions)

### 1. Fix the greatest-hits method — `Medium`
**Task:** Rewrite the Problem method to one efficient query.
**Solution:** the projected/no-tracking/server-filtered version above.
**Why it's better:** 10,001 queries → 1; full rows → 3 values; tracked → untracked. Often a
100×+ latency improvement.

### 2. Spot the N+1 in logs — `Easy`
**Scenario:** Your logs show, per page load:
```sql
SELECT * FROM Blogs;
SELECT * FROM Posts WHERE BlogId = 1;
SELECT * FROM Posts WHERE BlogId = 2;
... (one per blog)
```
**Task:** name the problem and fix it.
**Solution:** classic **N+1** from lazy/explicit loading per blog. Fix with eager loading or
projection:
```csharp
var blogs = await ctx.Blogs.Include(b => b.Posts).AsNoTracking().ToListAsync();
// or, if you only need counts:
var rows = await ctx.Blogs.Select(b => new { b.Title, Count = b.Posts.Count() }).ToListAsync();
```
**Why it's better:** one query instead of N+1.

## ✅ Key Takeaways

- The five fundamentals: **no-tracking reads, projection, kill N+1, DB-side filtering/paging,
  batched writes**.
- These fix the overwhelming majority of "EF is slow" cases.
- **Measure** with tags, logs, `ToQueryString`, and DB plans — never guess.
- EF 9/10 add **compiled models** and **better plan caching** on top.
