# Design-Time Configuration

## 🧠 Intuition

`dotnet ef` runs your code **at design time** — outside your normal app host — to discover the
`DbContext`, build the model, and generate migrations. If your context only gets its connection
string and provider from the running web host (via DI), the CLI has no idea how to construct it,
and you get the dreaded *"Unable to create a DbContext"*. **Design-time configuration** tells the
tooling how to build the context when the app isn't running.

> 💡 **Two worlds:** *runtime* (your app builds the context from DI/config) and *design time*
> (`dotnet ef` builds it on its own). They need to agree on provider + connection.

## 🎯 The Problem

```
dotnet ef migrations add Init
> Unable to create a 'BloggingContext'. ...
> No parameterless constructor was found ... or no design-time factory was registered.
```

This happens when the context constructor needs `DbContextOptions<T>` injected and there's no
parameterless path the tooling can use.

## 💻 Solution 1 — `IDesignTimeDbContextFactory<T>` (most explicit)

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Design;

public class BloggingContextFactory : IDesignTimeDbContextFactory<BloggingContext> {
    public BloggingContext CreateDbContext(string[] args) {
        var options = new DbContextOptionsBuilder<BloggingContext>()
            .UseSqlServer("Server=(localdb)\\mssqllocaldb;Database=Blogging;Trusted_Connection=True;TrustServerCertificate=True")
            .Options;
        return new BloggingContext(options);
    }
}
```

The CLI auto-discovers this factory and uses it. You can read the connection string from
`appsettings.json` or an environment variable instead of hard-coding:

```csharp
public BloggingContext CreateDbContext(string[] args) {
    var config = new ConfigurationBuilder()
        .SetBasePath(Directory.GetCurrentDirectory())
        .AddJsonFile("appsettings.json", optional: true)
        .AddEnvironmentVariables()
        .Build();
    var cs = config.GetConnectionString("Default")
             ?? "Server=(localdb)\\mssqllocaldb;Database=Blogging;Trusted_Connection=True;TrustServerCertificate=True";
    var options = new DbContextOptionsBuilder<BloggingContext>().UseSqlServer(cs).Options;
    return new BloggingContext(options);
}
```

## 💻 Solution 2 — the app host already exposes the context

If you use the generic host and register the context via `AddDbContext`, `dotnet ef` will use your
app's `CreateHostBuilder`/`Program` to resolve it — *as long as the project builds and the host
can start without side effects*. This "just works" for many ASP.NET Core apps without a factory.

```csharp
// Program.cs already does this; the EF tooling finds it:
builder.Services.AddDbContext<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
```

> ⚠️ If `Program.cs` does expensive or environment-specific work on startup (connects to a queue,
> needs prod secrets), the design-time factory (Solution 1) is cleaner and safer.

## 💻 Targeting a different project

When the `DbContext` lives in a class library and the startup project is the web app:

```bash
dotnet ef migrations add Init --project src/MyApp.Data --startup-project src/MyApp.Web
```

- `--project` — where migrations are written (the project with the context).
- `--startup-project` — the runnable project that wires up configuration.

## 💻 Multi-provider design time

For apps that target SQL Server in prod and SQLite in tests, you may keep **separate migrations
per provider**:

```bash
dotnet ef migrations add Init --context BloggingContext --output-dir Migrations/SqlServer -- --provider SqlServer
dotnet ef migrations add Init --context BloggingContext --output-dir Migrations/Sqlite    -- --provider Sqlite
```

The `--` passes args through to your `CreateDbContext(string[] args)`, which can switch providers
based on them. EF generates provider-specific SQL, so you genuinely need separate migration sets
if both providers manage real schemas.

## ⚖️ Trade-offs

**Factory (Solution 1):** explicit, independent of app startup, easy multi-provider — at the cost
of a small extra class and a connection string the tooling can reach.
**Host discovery (Solution 2):** no extra code when it works — but fragile if startup has
side effects or needs production secrets.

## 🚫 Common mistakes

```text
# ❌ Context in a class library, running dotnet ef from there with no startup project
# ✅ --startup-project pointing at the runnable app, or a design-time factory

# ❌ Design-time factory pointing at the PROD database
# → dotnet ef migrations add would connect to prod just to scaffold!
# ✅ point design time at localdb/dev; apply to prod via scripts (see Migrations in Production)

# ❌ Forgetting Microsoft.EntityFrameworkCore.Design package
# → "Your startup project doesn't reference Microsoft.EntityFrameworkCore.Design"
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- The design-time model is stable across EF 8/9/10.
- **EF 9 MSBuild compiled model** integrates with the build, complementing (not replacing)
  design-time configuration — see [Compiled Queries](../02-Querying/06.Compiled-and-Precompiled-Queries.md).

## 🌍 Real-world production tips

- Point the **design-time** connection at a **dev/local** database — `migrations add` shouldn't
  touch prod. Apply to prod via [scripts/bundles](02.Migrations-in-Production.md).
- Keep the design-time factory's connection string in **user secrets / env vars**, not hard-coded.
- For class-library contexts, always pass `--startup-project` (or add a factory) so the tooling
  finds configuration.

## 🎯 Practice (with full solutions)

### 1. Fix "Unable to create a DbContext" — `Easy`
**Scenario:** `BloggingContext` is in `MyApp.Data` (a class library). `dotnet ef migrations add`
fails to construct it.
**Solution:** add a design-time factory in `MyApp.Data`:
```csharp
public class BloggingContextFactory : IDesignTimeDbContextFactory<BloggingContext> {
    public BloggingContext CreateDbContext(string[] args) {
        var cs = Environment.GetEnvironmentVariable("EF_DESIGN_CONNECTION")
                 ?? "Server=(localdb)\\mssqllocaldb;Database=Blogging;Trusted_Connection=True;TrustServerCertificate=True";
        return new BloggingContext(new DbContextOptionsBuilder<BloggingContext>().UseSqlServer(cs).Options);
    }
}
```
**Why it's better:** the tooling can now build the context standalone, with a dev connection
string from an env var — no prod secrets, no startup side effects.

### 2. Generate migrations from a separate startup project — `Easy`
**Task:** Context in `src/MyApp.Data`, runnable web app in `src/MyApp.Web`.
**Solution:**
```bash
dotnet ef migrations add AddRating --project src/MyApp.Data --startup-project src/MyApp.Web
dotnet ef database update --project src/MyApp.Data --startup-project src/MyApp.Web
```
**Why it's better:** migrations land next to the context; configuration comes from the runnable
app — no duplicated wiring.

## ✅ Key Takeaways

- `dotnet ef` builds the context **at design time** — it needs a way to construct it.
- Use **`IDesignTimeDbContextFactory<T>`** for explicit, startup-independent construction.
- Or rely on **host discovery** via `--startup-project` when the app wires the context cleanly.
- Point design time at a **dev** database; apply to prod via scripts/bundles.
- Multi-provider apps keep **separate migration sets** per provider.

1. Why does `dotnet ef` sometimes fail to create your `DbContext`?
2. When do you need a design-time factory vs `--startup-project`?
3. Why should the design-time connection string never point at production?
