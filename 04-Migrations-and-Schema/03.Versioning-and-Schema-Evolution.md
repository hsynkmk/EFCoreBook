# Versioning & Schema Evolution

## 🧠 Intuition

Schemas live for years and change constantly. The senior skill isn't writing a migration — it's
making changes that are **backward-compatible** so deployments are safe, rollbacks are possible,
and old/new code can coexist during rolling deploys. The unifying technique is **expand-contract**
(parallel change): never break an existing contract in one step; add the new shape, migrate, then
remove the old shape later.

> 💡 **Mental model:** treat your database schema like a public API. You don't delete a public
> method and ship in one release — you deprecate, migrate callers, then remove. Same for columns
> and tables.

## 📐 Which changes are safe vs breaking

| Change | Safe in one step? | Notes |
|--------|-------------------|-------|
| Add a **nullable** column | ✅ | Old code ignores it |
| Add a column with a **default** | ✅ | Existing rows get the default |
| Add a table / index | ✅ | Nothing old breaks |
| Widen a column (`nvarchar(100)` → `(200)`) | ✅ | Strictly more permissive |
| Add a **non-nullable** column **without** default | ❌ | Fails if rows exist → add nullable + backfill first |
| **Rename** a column / table | ❌ | Old code references the old name → expand-contract |
| **Drop** a column / table | ❌ | Old code still reads it → contract *after* old code is gone |
| **Narrow** a column / add `NOT NULL` | ❌ | Existing data may violate → backfill + validate first |
| Change a column **type** | ❌ | Data conversion + old code → multi-step |

## 💻 Expand-contract, concretely

### Renaming `Name` → `Title`

```text
1. EXPAND   — migration adds `Title` (nullable). `Name` stays.
2. DEPLOY   — code writes BOTH Name and Title; reads Title (falls back to Name if null).
3. BACKFILL — UPDATE rows: Title = Name where Title IS NULL.
4. DEPLOY   — code stops touching Name entirely.
5. CONTRACT — later migration: Title NOT NULL; DROP Name.
```

Each step is independently deployable and reversible. At no point does live code reference a
column that doesn't exist.

### Splitting a column (`FullName` → `FirstName` + `LastName`)

```text
1. EXPAND   — add FirstName, LastName (nullable).
2. BACKFILL — populate from FullName with a script/ExecuteUpdate.
3. DEPLOY   — code reads/writes the new columns; keeps FullName in sync (or stops).
4. CONTRACT — drop FullName once nothing reads it.
```

## 💻 Backfilling at scale

A backfill that touches millions of rows in one statement can lock the table. Batch it:

```csharp
int batch;
do {
    batch = await ctx.Blogs
        .Where(b => b.Title == null)
        .Take(5000)
        .ExecuteUpdateAsync(s => s.SetProperty(b => b.Title, b => b.Name));
    await Task.Delay(50);   // breathe — let other transactions through
} while (batch > 0);
```

`ExecuteUpdateAsync` (see [Bulk Operations](../03-Saving-and-Concurrency/05.Bulk-Operations.md))
in bounded batches keeps locks short.

## 💻 Handling enum / lookup changes

Adding an enum value is safe if you store enums **as strings** (see
[Value Conversions](../01-Modeling-Data/05.Value-Conversions.md)) — old rows are unaffected.
Storing as `int` and reordering the enum silently changes the meaning of existing rows. Always
**append** new enum members; never reorder.

## ⚖️ Versioning the database itself

`__EFMigrationsHistory` already records which migrations are applied. For coarse "schema version"
needs (feature flags, compatibility gates), some teams add a `SchemaVersion` row in a metadata
table. Usually the migrations history is enough — don't over-engineer.

## 🚫 Common mistakes

```text
# ❌ Rename + drop in the same release that old instances still run → 500s during rollout
# ✅ expand-contract across releases

# ❌ Add NOT NULL column with no default to a populated table → migration fails
# ✅ add nullable → backfill → set NOT NULL later

# ❌ Reordering an int-backed enum → existing rows now mean something different
# ✅ store enums as strings; only ever APPEND members

# ❌ One giant backfill UPDATE on a hot table → lock storm
# ✅ batched ExecuteUpdate with small pauses
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8+** `ExecuteUpdateAsync` makes batched backfills clean and efficient.
- **EF 10** per-step migrations (not one big transaction) reduce the lock blast radius of a
  multi-operation migration.

## 🌍 Real-world production tips

- Treat the schema as a **versioned contract**: deprecate → migrate → remove.
- **Never** ship a breaking schema change in the same deploy as the code that depends on it.
- Keep migrations **small and named** so a bad one is easy to identify and revert.
- Document the **rollback** for every breaking change before you ship it.

## 🎯 Practice (with full solutions)

### 1. Make a column required safely — `Medium`
**Task:** `Blog.Slug` must become `NOT NULL`, but existing rows have nulls.
**Solution:**
```text
1. Migration: ensure Slug exists (nullable).
2. Backfill: batched ExecuteUpdate to set Slug from Title (slugified) where null.
3. Validate: confirm no nulls remain.
4. Migration: ALTER COLUMN Slug NOT NULL.
```
```csharp
int batch;
do {
    batch = await ctx.Blogs.Where(b => b.Slug == null).Take(5000)
        .ExecuteUpdateAsync(s => s.SetProperty(b => b.Slug, b => b.Title));   // simplistic
} while (batch > 0);
```
**Why it's better:** enforcing `NOT NULL` only after data is clean avoids a failed migration and
keeps locks short.

### 2. Add an enum value without risk — `Easy`
**Task:** Add `BlogStatus.Scheduled` to an existing enum.
**Solution:** ensure the enum is stored as a string, then simply append the member:
```csharp
public enum BlogStatus { Draft, Published, Archived, Scheduled }   // appended
modelBuilder.Entity<Blog>().Property(b => b.Status).HasConversion<string>().HasMaxLength(20);
```
**Why it's better:** string storage means existing `Draft`/`Published` rows are untouched, and
appending (not reordering) keeps every old value valid.

## ✅ Key Takeaways

- Make schema changes **backward-compatible**; use **expand-contract** for renames, splits, drops.
- **Add nullable → backfill (batched) → enforce constraint** — never add a `NOT NULL` column to a
  populated table in one step.
- Store enums **as strings** and only **append** members.
- Never ship a breaking schema change in the same release as the code depending on it.
