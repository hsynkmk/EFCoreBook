# Migrations Basics

## 🧠 Intuition

Your C# model is the *desired* schema; the database is the *current* schema. A **migration** is the
versioned, source-controlled diff between two model snapshots — the C# code (and SQL) that moves
the database from where it is to where your model says it should be. Migrations are how a schema
evolves in lockstep with your code, reviewably, across every environment.

> 💡 **Analogy — git for your database schema.** Each migration is a commit: a named, ordered,
> reversible change. `database update` is "check out the latest"; rolling back is "revert to an
> earlier commit."

## 💻 The core workflow

```bash
# 1. Change your model (add a property, an entity, an index…)
# 2. Generate a migration capturing the diff
dotnet ef migrations add AddBlogRating

# 3. Review the generated code (ALWAYS) — it's in Migrations/
# 4. Apply it to your database
dotnet ef database update
```

### What `migrations add` generates

```csharp
public partial class AddBlogRating : Migration {
    protected override void Up(MigrationBuilder migrationBuilder) {
        migrationBuilder.AddColumn<int>(
            name: "Rating", table: "Blogs", nullable: false, defaultValue: 0);
    }
    protected override void Down(MigrationBuilder migrationBuilder) {
        migrationBuilder.DropColumn(name: "Rating", table: "Blogs");
    }
}
```

`Up` applies the change; `Down` reverses it. EF also updates a model **snapshot**
(`Migrations/<Context>ModelSnapshot.cs`) so the next migration diffs against it.

## 💻 Essential commands

```bash
dotnet ef migrations add <Name>          # create a migration
dotnet ef migrations remove              # delete the LAST migration (if not yet applied)
dotnet ef migrations list                # see applied/pending
dotnet ef database update                # apply all pending
dotnet ef database update <MigrationName># migrate UP or DOWN to a specific point
dotnet ef database update 0              # revert ALL migrations (empty database schema)
dotnet ef migrations script              # generate idempotent SQL (for production — next file)
dotnet ef migrations has-pending-model-changes   # CI check: is a migration missing? (EF 8+)
```

## 💻 Applying migrations at runtime vs. via scripts

```csharp
// ❌ Convenient but risky in production: apply migrations on app startup
await ctx.Database.MigrateAsync();
```

`MigrateAsync()` is fine for dev and demos. In production it's risky: multiple instances racing
to migrate, no review of the SQL, no rollback plan, downtime if a migration locks a big table.

> ✅ For production, generate **idempotent SQL scripts** or **migration bundles** and apply them
> as a deliberate deployment step — see [Migrations in Production](02.Migrations-in-Production.md).

## ⚖️ The model snapshot — the thing people break

EF diffs your model against `<Context>ModelSnapshot.cs`, **not** against the live database. If you
hand-edit the database or delete a migration file without `migrations remove`, the snapshot and
reality drift, and the next migration generates wrong SQL.

**Rules:**
- Never hand-edit the snapshot.
- Use `dotnet ef migrations remove` (not file deletion) to drop the last *unapplied* migration.
- Commit the migration **and** the updated snapshot together.

## 🚫 Common mistakes

```bash
# ❌ Deleting a migration .cs file by hand
rm Migrations/20260101_AddRating.cs   # snapshot now out of sync
# ✅ dotnet ef migrations remove

# ❌ Editing the model and forgetting to add a migration → runtime "model changed" surprises
# ✅ in CI: dotnet ef migrations has-pending-model-changes (fails the build if a migration is missing)

# ❌ Running MigrateAsync() from three app instances at once → race / partial migration
# ✅ apply migrations as a single deployment step
```

```csharp
// ❌ Migrating with a non-default schema/connection but forgetting design-time config
// → "Unable to create a DbContext" — see Design-Time Configuration (04)
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** `dotnet ef migrations has-pending-model-changes` — a CI guard that fails if the model
  changed without a migration. Adopt it.
- **EF 9:** wrapped all pending migrations into **one transaction** during `database update`.
- **EF 10:** **reverted** the EF 9 single-transaction behavior — migrations apply per-step again,
  because the single transaction caused problems in several real deployment scenarios.

## 🌍 Real-world production tips

- **Always review the generated migration** before applying — especially column drops and type
  changes that can lose data.
- **One migration per logical change** with a descriptive name (`AddBlogRating`, not `Update1`).
- Add **`has-pending-model-changes`** to CI so nobody forgets a migration.
- Keep migrations **forward-compatible** during rolling deploys (expand-contract — see
  [Versioning & Schema Evolution](03.Versioning-and-Schema-Evolution.md)).

## 🎯 Practice (with full solutions)

### 1. Add a column safely — `Easy`
**Task:** Add a non-nullable `Rating` (default 0) to `Blog`.
**Solution:**
```csharp
public class Blog { public int Id { get; set; } public string Title { get; set; } = ""; public int Rating { get; set; } }
```
```bash
dotnet ef migrations add AddBlogRating
# review Migrations/..._AddBlogRating.cs — confirm defaultValue: 0
dotnet ef database update
```
**Why it's better:** the default value means existing rows get a valid `Rating` without a manual
backfill, and the migration is reviewable and reversible.

### 2. Roll back a bad migration — `Medium`
**Scenario:** You applied `AddWeirdColumn` to your dev DB and want it gone.
**Solution:**
```bash
# revert the database to the migration BEFORE the bad one
dotnet ef database update PreviousMigrationName
# then remove the bad migration from the project
dotnet ef migrations remove
```
**Why it's better:** `database update <target>` runs the `Down` methods to step back cleanly;
`migrations remove` keeps the snapshot consistent. No hand-editing.

## ✅ Key Takeaways

- A migration is a **versioned, reversible diff** between model snapshots — git for your schema.
- Workflow: change model → `migrations add` → **review** → `database update`.
- EF diffs against the **model snapshot**, not the live DB — never hand-edit it; use
  `migrations remove`.
- **Don't `MigrateAsync()` blindly in production** — use scripts/bundles (next file).
- Add **`has-pending-model-changes`** to CI.
