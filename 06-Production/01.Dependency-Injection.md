# Dependency Injection

## 🧠 Intuition

In a real app, you don't `new` a `DbContext` — you let the **DI container** create and dispose it
for you, scoped to the right lifetime, with the connection string and provider wired from config.
EF Core integrates natively with `Microsoft.Extensions.DependencyInjection`. Getting the
**lifetime** right is the whole game: a `DbContext` is meant to be **scoped** (one per request /
unit of work), never a singleton.

> 💡 **Analogy — a fresh notepad per meeting.** Each request gets its own `DbContext` (notepad),
> uses it, and throws it away. You never share one notepad across simultaneous meetings.

## 💻 The three registration methods

```csharp
// 1. Standard — scoped, one per request. The default for web apps.
builder.Services.AddDbContext<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

// 2. Pooled — scoped but reuses reset instances (perf). Context must be stateless.
builder.Services.AddDbContextPool<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

// 3. Factory — create short-lived contexts on demand (background work, Blazor Server, parallel work).
builder.Services.AddDbContextFactory<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
```

| Method | Lifetime | Use when |
|--------|----------|----------|
| `AddDbContext` | Scoped | Standard web request handling |
| `AddDbContextPool` | Scoped (pooled) | High-throughput APIs, stateless context ([pooling rules](../05-Performance/02.DbContext-Pooling.md)) |
| `AddDbContextFactory` | You control | Background services, parallelism, Blazor Server |

## 💻 Consuming it

```csharp
public class BlogService {
    private readonly BloggingContext _ctx;
    public BlogService(BloggingContext ctx) => _ctx = ctx;     // injected, scoped, auto-disposed
    public Task<Blog?> GetAsync(int id) => _ctx.Blogs.FindAsync(id).AsTask();
}
builder.Services.AddScoped<BlogService>();
```

With the factory, you create contexts per operation:

```csharp
public class NightlyReport {
    private readonly IDbContextFactory<BloggingContext> _factory;
    public NightlyReport(IDbContextFactory<BloggingContext> f) => _factory = f;
    public async Task RunAsync() {
        await using var ctx = await _factory.CreateDbContextAsync();   // your context, your dispose
        // ...
    }
}
```

## 🚫 The lifetime traps

### Captive dependency — the #1 EF DI bug

A **singleton** service that injects a **scoped** `DbContext` "captures" one context forever —
shared across all requests, across threads. `DbContext` is not thread-safe; chaos ensues.

```csharp
// ❌ Singleton holding a scoped DbContext
public class CacheWarmer {                      // registered as singleton
    private readonly BloggingContext _ctx;      // captured for the app's lifetime!
    public CacheWarmer(BloggingContext ctx) => _ctx = ctx;
}
builder.Services.AddSingleton<CacheWarmer>();   // 💥 captive dependency
```

**Fix:** inject the **factory** into the singleton and create a context per operation:

```csharp
public class CacheWarmer {
    private readonly IDbContextFactory<BloggingContext> _factory;
    public CacheWarmer(IDbContextFactory<BloggingContext> f) => _factory = f;
    public async Task WarmAsync() {
        await using var ctx = await _factory.CreateDbContextAsync();   // fresh, disposed per call
        // ...
    }
}
```

> The framework will actually **throw at startup** if a singleton directly depends on a scoped
> service — but it can't catch it when the singleton grabs the context via a service locator.

### Other traps

```csharp
// ❌ Injecting DbContext into a background IHostedService (singleton) directly
// ✅ use IDbContextFactory and create per unit of work

// ❌ Sharing one context across parallel tasks
await Task.WhenAll(ids.Select(id => _ctx.Blogs.FindAsync(id).AsTask()));   // DbContext not thread-safe!
// ✅ one context per task (via the factory), or run sequentially
```

## ⚖️ Lifetime quick reference

| Service kind | Lifetime | DbContext access |
|--------------|----------|------------------|
| Web request handler / scoped service | Scoped | Inject `DbContext` directly |
| Singleton (cache, hosted service) | Singleton | Inject `IDbContextFactory<T>`, create per op |
| Background worker | Singleton | Inject factory; one context per unit of work |
| Blazor Server component | (long-lived) | Inject factory; create per operation |

## 🆕 Latest EF Notes (8 / 9 / 10)

- `AddDbContext`, `AddDbContextPool`, `AddDbContextFactory`, and `AddPooledDbContextFactory` are
  all stable from EF 5/6 onward.
- **EF 9 compiled model** + DI pooling gives the best startup + per-request profile.
- **EF 10:** no DI-shape changes; the perf wins (plan caching) apply transparently.

## 🌍 Real-world production tips

- **Default to `AddDbContext` (scoped).** Reach for pooling only on hot APIs with stateless
  contexts; reach for the factory whenever you're outside the request scope.
- **Never inject a `DbContext` into a singleton.** Inject the **factory**.
- For **parallel** EF work, one context per parallel branch — `DbContext` is single-threaded.
- Keep services thin; the context is a unit of work, not a place for business logic.

## 🎯 Practice (with full solutions)

### 1. Fix the captive dependency — `Medium`
**Smelly code:** the singleton `CacheWarmer` holding a `BloggingContext`.
**Solution:** the factory-based `CacheWarmer` above; register the factory:
```csharp
builder.Services.AddDbContextFactory<BloggingContext>(opt =>
    opt.UseSqlServer(builder.Configuration.GetConnectionString("Default")));
builder.Services.AddSingleton<CacheWarmer>();
```
**Why it's better:** the singleton no longer captures a single context; each warm-up uses a fresh,
properly-disposed context — thread-safe and correct.

### 2. Parallel reads done right — `Medium`
**Task:** Fetch 10 blogs by id in parallel.
**Solution:**
```csharp
public async Task<Blog?[]> GetManyAsync(int[] ids, IDbContextFactory<BloggingContext> factory) =>
    await Task.WhenAll(ids.Select(async id => {
        await using var ctx = await factory.CreateDbContextAsync();   // one context per task
        return await ctx.Blogs.FindAsync(id).AsTask();
    }));
```
**Why it's better:** each parallel task gets its own context, so there's no shared-state /
thread-safety violation. (Often a single batched `WHERE Id IN (...)` query is better still — but
when you genuinely parallelize, this is the safe shape.)

## ✅ Key Takeaways

- Register EF with **`AddDbContext`** (scoped, default), **`AddDbContextPool`** (perf), or
  **`AddDbContextFactory`** (background/parallel/Blazor).
- `DbContext` is **scoped, short-lived, single-threaded** — never a singleton, never shared.
- The **captive dependency** bug (singleton holding a scoped context) is the classic EF DI mistake
  — inject the **factory** instead.
- One context per parallel branch.
