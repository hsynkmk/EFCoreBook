# Error Handling & Resilience

## 🧠 Intuition

Databases fail *transiently* all the time — a network blip, a failover, a momentary throttle on
Azure SQL, a deadlock. A naive app turns each blip into a 500. A resilient app **retries
transient failures automatically** and only surfaces the genuinely unrecoverable ones. EF Core has
built-in retry support (`EnableRetryOnFailure`); the skill is using it correctly with transactions
and idempotency.

> 💡 **Transient vs permanent.** "Connection reset" → retry. "Unique constraint violation" → don't
> retry, it'll fail forever. EF's retrying execution strategy knows the difference for known
> providers.

## 💻 Enable connection resiliency

```csharp
builder.Services.AddDbContext<BloggingContext>(opt =>
    opt.UseSqlServer(cs, sql => sql.EnableRetryOnFailure(
        maxRetryCount: 5,
        maxRetryDelay: TimeSpan.FromSeconds(10),
        errorNumbersToAdd: null)));     // provider's known-transient list + your extras
```

EF wraps each operation in a **retrying execution strategy** that catches known transient errors
and retries with exponential backoff. For Azure SQL, `UseAzureSql` (EF 9+) configures sensible
defaults automatically.

## 🚫 Retries + manual transactions = a sharp edge

A retrying strategy may re-run your operation — but it **can't blindly re-run a multi-statement
block you wrote by hand**, because it doesn't know how to roll the whole thing back and replay it.
If you open an explicit transaction, you must wrap it in the strategy's `ExecuteAsync`:

```csharp
var strategy = ctx.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () => {
    using var tx = await ctx.Database.BeginTransactionAsync();
    ctx.Orders.Add(order);
    await ctx.SaveChangesAsync();
    await ctx.Inventory.Where(i => i.Sku == sku)
        .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - 1));
    await tx.CommitAsync();
});
```

`strategy.ExecuteAsync` re-runs the **entire delegate** (transaction included) on a transient
failure — which is why the body must be **idempotent** (safe to run more than once).

> Without this wrapper, EF throws: *"The configured execution strategy 'SqlServerRetryingExecution­
> Strategy' does not support user-initiated transactions."*

## 💻 Handling specific exceptions

```csharp
try {
    await ctx.SaveChangesAsync();
} catch (DbUpdateConcurrencyException ex) {
    // optimistic concurrency conflict — resolve (see Concurrency Handling)
} catch (DbUpdateException ex) when (IsUniqueViolation(ex)) {
    // a unique constraint was violated — a real business error, surface it
    return Conflict("That slug is already taken.");
} catch (DbUpdateException ex) {
    // other persistence error — log and rethrow
    logger.LogError(ex, "Save failed");
    throw;
}
```

`DbUpdateException.InnerException` holds the provider's `SqlException` with the error number — use
it to distinguish unique-violation (don't retry) from deadlock (do retry).

## 💻 Deadlock retries

Deadlocks (SQL Server error 1205) are transient — the loser is chosen and rolled back. With
`EnableRetryOnFailure`, EF retries them automatically. For hand-rolled retry logic, only retry
**idempotent** work, with backoff and a cap. For richer policies (circuit breakers, jitter),
**Polly** complements EF's built-in strategy.

## ⚖️ What to retry vs not

| Error | Transient? | Action |
|-------|-----------|--------|
| Connection reset / timeout | ✅ | Retry (EF does it) |
| Azure SQL throttling (40501, 49918…) | ✅ | Retry with backoff |
| Deadlock (1205) | ✅ | Retry idempotent work |
| Unique constraint violation (2627/2601) | ❌ | Surface as a business error |
| FK violation | ❌ | Fix the data/logic |
| Concurrency conflict | ❌ (retry *after* resolving) | Resolve, then retry |

## 🚫 Common mistakes

```csharp
// ❌ Explicit transaction without the execution strategy under EnableRetryOnFailure → throws
using var tx = await ctx.Database.BeginTransactionAsync();   // 💥 with retries enabled
// ✅ wrap in strategy.ExecuteAsync (above)

// ❌ Retrying a non-idempotent operation → duplicate side effects on retry
// ✅ make the body idempotent (idempotency key, upsert) before enabling retries

// ❌ Catching all DbUpdateException and retrying → infinite loop on a unique violation
// ✅ classify the error number; only retry transient ones
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- `EnableRetryOnFailure` is stable across EF 8/9/10.
- **EF 9 `UseAzureSql`** sets Azure-appropriate transient-error handling out of the box.
- **EF 10:** migration application is **per-step** again (not one big transaction), which interacts
  more predictably with retries during deployment.

## 🌍 Real-world production tips

- **Turn on `EnableRetryOnFailure`** for any cloud database (Azure SQL especially).
- **Wrap explicit transactions** in `CreateExecutionStrategy().ExecuteAsync` and make them
  **idempotent**.
- **Classify exceptions** — retry transient, surface business errors (unique/FK) clearly to the
  caller.
- Add **Polly** for cross-cutting resilience (HTTP + DB) and circuit breakers when needed.
- Pair with **health checks** (previous file) so orchestrators route around sustained outages.

## 🎯 Practice (with full solutions)

### 1. Make a multi-step write resilient — `Medium`
**Task:** Order placement (insert order + decrement stock) must survive transient failures on
Azure SQL.
**Solution:**
```csharp
opt.UseAzureSql(cs, sql => sql.EnableRetryOnFailure());   // EF 9+ Azure defaults

var strategy = ctx.Database.CreateExecutionStrategy();
await strategy.ExecuteAsync(async () => {
    using var tx = await ctx.Database.BeginTransactionAsync();
    ctx.Orders.Add(order);
    await ctx.SaveChangesAsync();
    var ok = await ctx.Inventory.Where(i => i.Sku == sku && i.Stock > 0)
        .ExecuteUpdateAsync(s => s.SetProperty(i => i.Stock, i => i.Stock - 1));
    if (ok == 0) throw new OutOfStockException();        // non-transient → won't be retried into a loop
    await tx.CommitAsync();
});
```
**Why it's better:** transient blips replay the whole transaction; the out-of-stock case is a real
error that bubbles up. (Add an idempotency key so a replayed order isn't inserted twice.)

### 2. Classify a save error — `Easy`
**Task:** On a unique-slug violation, return 409; on anything else, log and rethrow.
**Solution:**
```csharp
try { await ctx.SaveChangesAsync(); }
catch (DbUpdateException ex) when (ex.InnerException is SqlException { Number: 2627 or 2601 }) {
    return Results.Conflict("Slug already taken.");
}
```
**Why it's better:** the genuinely-recoverable case becomes a clean 409; everything else follows
the normal error path. No blind retry on a permanent error.

## ✅ Key Takeaways

- Enable **`EnableRetryOnFailure`** for cloud databases — EF retries known transient errors with
  backoff.
- **Explicit transactions** under retries must be wrapped in **`CreateExecutionStrategy().ExecuteAsync`**
  and be **idempotent**.
- **Classify** exceptions: retry transient (timeouts, deadlocks, throttling); surface permanent
  (unique/FK) as business errors.
- Combine with **health checks** and optionally **Polly** for full resilience.
