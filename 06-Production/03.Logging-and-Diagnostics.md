# Logging & Diagnostics

> Consolidates what the old repo split across *Logging*, *Monitoring*, and *Query Tags*. The
> query-side detail lives in [Query Tags & Diagnostics](../02-Querying/07.Query-Tags-and-Diagnostics.md)
> and [Diagnosing Slow Queries](../05-Performance/05.Diagnosing-Slow-Queries.md); this is the
> production observability picture.

## 🧠 Intuition

In production you need to answer three questions fast: **What SQL is EF running? How long does it
take? Is the database healthy?** EF gives you logging (`LogTo`, categories, sensitive-data
toggles), diagnostic events (consumed by APM/OpenTelemetry), and metrics (EventCounters). Wired
correctly, a slow query or a failing connection shows up in your dashboards before users notice.

> 💡 **The two rails:** *logs* (what happened, with detail) and *metrics/traces* (aggregates and
> request-level spans). You want both, tuned differently for dev vs prod.

## 💻 Logging — dev vs prod

```csharp
// DEV: verbose, parameter values visible, detailed errors
opt.UseSqlServer(cs)
   .LogTo(Console.WriteLine, LogLevel.Information)
   .EnableSensitiveDataLogging()      // parameter VALUES — DEV ONLY
   .EnableDetailedErrors();

// PROD: structured logger, filtered to command category, no sensitive data
opt.UseSqlServer(cs)
   .LogTo(msg => logger.LogDebug("{EfSql}", msg),
          new[] { DbLoggerCategory.Database.Command.Name },
          LogLevel.Information);
```

> ⚠️ **`EnableSensitiveDataLogging()` writes parameter values** (often PII) into your logs. It is
> a **development-only** switch. Shipping it to prod is a data-leak incident waiting to happen.

### Log categories you'll filter on

| Category | What it covers |
|----------|----------------|
| `Database.Command` | SQL commands + durations |
| `Database.Connection` | Open/close |
| `Database.Transaction` | Begin/commit/rollback |
| `Update` | SaveChanges details |
| `Query` | Query compilation |
| `Migrations` | Migration application |

## 💻 Tag queries so logs are traceable

```csharp
var rows = await ctx.Orders
    .TagWith("Dashboard.OpenOrders")     // appears as a SQL comment in logs/profiler
    .Where(o => o.Status == "Open")
    .ToListAsync();
```

Now a slow line in your log carries `-- Dashboard.OpenOrders` → straight to source. This single
habit pays back enormously during incidents.

## 💻 OpenTelemetry — traces + metrics (the modern default)

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()     // EF queries become spans inside the request trace
        .AddSqlClientInstrumentation()
        .AddOtlpExporter())
    .WithMetrics(m => m
        .AddRuntimeInstrumentation()
        .AddOtlpExporter());
```

Now each request trace shows: controller → EF query span (with the SQL + duration) → SQL Client
span. Slow queries appear *inside* the request that triggered them. This is the gold standard for
"why was this request slow?".

## 💻 EventCounters / metrics

EF exposes counters (active DbContexts, queries executed, SaveChanges count, compiled-query cache
hits) via `dotnet-counters`:

```bash
dotnet-counters monitor --process-id <pid> Microsoft.EntityFrameworkCore
```

Or scrape them through OpenTelemetry metrics for dashboards and alerts.

## 💻 Health checks

```csharp
builder.Services.AddHealthChecks()
    .AddDbContextCheck<BloggingContext>("database");   // pings the DB via the context

app.MapHealthChecks("/health");
```

A load balancer / orchestrator hits `/health`; if the database is unreachable, the instance is
pulled from rotation. Pair with the **resilience** settings in
[Error Handling & Resilience](04.Error-Handling-and-Resilience.md).

## ⚖️ Dev vs prod settings

| Setting | Dev | Prod |
|---------|-----|------|
| `LogTo(Console...)` | ✅ | ❌ (structured logger) |
| `EnableSensitiveDataLogging` | ✅ | **❌ never** |
| `EnableDetailedErrors` | ✅ | optional (small perf cost) |
| Query tags | ✅ | ✅ |
| OpenTelemetry tracing | optional | ✅ |
| Health checks | optional | ✅ |
| Slow-query interceptor | ✅ | ✅ (alert) |

## 🚫 Common mistakes

```csharp
// ❌ EnableSensitiveDataLogging in production → PII in logs
// ❌ Logging every command at Information in prod → log volume explosion + cost
// ✅ filter to Warning, or sample, or rely on OpenTelemetry sampling

// ❌ No query tags → "which code emitted this SQL?" is a manual hunt
// ❌ No health check → orchestrator can't tell the DB is down
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 10** emits **human-readable parameter names** in logged SQL (`@orderId` vs `@__orderId_0`)
  — far easier to read and to paste into a query plan tool.
- **EF 10 Cosmos** logs **RU charge and partition key** per call — essential for cost monitoring.
- OpenTelemetry EF instrumentation is mature across EF 8/9/10.

## 🌍 Real-world production tips

- **Tag every important query.** It's free and saves you in every incident.
- **OpenTelemetry** as the backbone: traces tie EF queries to requests; metrics drive alerts.
- **Health check + resilience** so transient DB blips self-heal and orchestrators route around
  outages.
- **Never** ship `EnableSensitiveDataLogging`. Gate it behind `if (env.IsDevelopment())`.
- Watch **log volume/cost** — command-level logging at Information in prod is expensive; sample.

## 🎯 Practice (with full solutions)

### 1. Set up safe prod logging + tracing — `Medium`
**Task:** Production should: never log PII, surface EF queries in request traces, and expose a DB
health endpoint.
**Solution:**
```csharp
opt.UseSqlServer(cs)
   .LogTo(msg => logger.LogDebug("{EfSql}", msg),
          new[] { DbLoggerCategory.Database.Command.Name }, LogLevel.Warning);
// (no EnableSensitiveDataLogging)

builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddAspNetCoreInstrumentation().AddEntityFrameworkCoreInstrumentation().AddOtlpExporter());

builder.Services.AddHealthChecks().AddDbContextCheck<BloggingContext>();
app.MapHealthChecks("/health");
```
**Why it's better:** no PII leak; slow queries appear inside their request traces; the orchestrator
can detect DB outages.

### 2. Gate dev-only diagnostics — `Easy`
**Task:** Verbose logging + sensitive data only in Development.
**Solution:**
```csharp
builder.Services.AddDbContext<BloggingContext>((sp, opt) => {
    opt.UseSqlServer(cs);
    if (builder.Environment.IsDevelopment())
        opt.LogTo(Console.WriteLine, LogLevel.Information)
           .EnableSensitiveDataLogging()
           .EnableDetailedErrors();
});
```
**Why it's better:** the dangerous switches can't accidentally reach production.

## ✅ Key Takeaways

- Two rails: **logs** (`LogTo`, categories, tags) and **traces/metrics** (OpenTelemetry,
  EventCounters).
- **`EnableSensitiveDataLogging` is dev-only** — it logs parameter values (PII).
- **Tag queries** so logs and profiler output point back to source.
- Add **OpenTelemetry** tracing + **health checks** for real observability.
- EF 10 makes logged SQL more readable and logs Cosmos RU/partition info.

2. What does OpenTelemetry EF instrumentation give you that plain logs don't?
3. What does a `DbContext` health check protect against?
