# Security Best Practices

## 🧠 Intuition

EF Core gives you a lot of security for free — parameterized queries by default, no string-built
SQL unless you ask for it. But the database is where your most sensitive data lives, so the
remaining surface area matters: **injection** (only possible if you misuse raw SQL), **least
privilege** (the app's DB account shouldn't be `sa`), **encryption** (in transit and at rest),
**secret management**, and **not leaking data through logs or over-fetching**.

> 💡 EF's defaults are safe. Most EF security incidents come from *bypassing* those defaults —
> string-concatenated raw SQL, `sa` credentials, sensitive-data logging in prod.

## 💻 1. SQL injection — safe by default, dangerous when bypassed

LINQ and parameterized raw SQL are injection-safe:

```csharp
// ✅ LINQ — always parameterized
await ctx.Blogs.Where(b => b.Title == userInput).ToListAsync();

// ✅ FromSql / SqlQuery interpolation — parameterized
await ctx.Blogs.FromSql($"SELECT * FROM Blogs WHERE Title = {userInput}").ToListAsync();

// ❌ FromSqlRaw with string concatenation — INJECTION
await ctx.Blogs.FromSqlRaw("SELECT * FROM Blogs WHERE Title = '" + userInput + "'").ToListAsync();

// ✅ FromSqlRaw with explicit parameters
await ctx.Blogs.FromSqlRaw("SELECT * FROM Blogs WHERE Title = {0}", userInput).ToListAsync();
```

**Rule:** never build SQL with string concatenation/`$"..."` into `FromSqlRaw`/`ExecuteSqlRaw`.
Use interpolated `FromSql`/`ExecuteSql` (auto-parameterized) or explicit parameters.

## 💻 2. Least privilege

The app's database account should have **only** the permissions it needs — typically `SELECT`,
`INSERT`, `UPDATE`, `DELETE` on its tables, and execute on its procedures. Not `db_owner`, not
`sa`.

```sql
-- SQL Server example
CREATE USER app_user FOR LOGIN app_login;
ALTER ROLE db_datareader ADD MEMBER app_user;
ALTER ROLE db_datawriter ADD MEMBER app_user;
-- explicitly NOT db_owner / sysadmin
```

Run **migrations** under a higher-privilege account during deployment, but run the **app** under
the restricted one. A SQL-injection or app compromise is then bounded.

## 💻 3. Encryption

**In transit:** `Encrypt=True` with a valid certificate.
```text
Server=...;Database=...;Encrypt=True;   -- TrustServerCertificate=True is DEV ONLY
```

**At rest:** Transparent Data Encryption (TDE) at the database level (Azure SQL enables it by
default). For **column-level** secrets (SSNs, tokens), use **Always Encrypted** (SQL Server) or
encrypt in the app via a value converter backed by a KMS key — never store secrets in plaintext.

## 💻 4. Secret management

Covered in [Configuration & Connection Strings](02.Configuration-and-Connection-Strings.md):
**user secrets** (dev), **Key Vault / Secrets Manager** (prod), or **Managed Identity**
(passwordless — nothing to leak). Never commit credentials.

## 💻 5. Don't leak data through logs

```csharp
// ❌ EnableSensitiveDataLogging in prod → parameter values (emails, tokens, PII) in logs
// ✅ dev-only, gated behind env.IsDevelopment()
```

PII in logs is a breach. Keep sensitive-data logging out of production
([Logging & Diagnostics](03.Logging-and-Diagnostics.md)).

## 💻 6. Don't over-fetch / over-expose

```csharp
// ❌ Returning entities straight from an API — leaks columns the client shouldn't see
return await ctx.Users.ToListAsync();   // includes PasswordHash, internal flags...

// ✅ Project to a DTO with only the fields the client may see
return await ctx.Users
    .Select(u => new UserDto(u.Id, u.DisplayName))
    .ToListAsync();
```

Projection is a **security** control as much as a performance one — it's how you avoid leaking
`PasswordHash`, internal scores, soft-deleted rows, or other tenants' data.

## 💻 7. Multi-tenant isolation

Use **global / named query filters** ([Global & Named Query Filters](../01-Modeling-Data/08.Global-and-Named-Query-Filters.md))
so every query is automatically scoped to the current tenant — a forgotten `Where` can't leak
another tenant's rows.

```csharp
modelBuilder.Entity<Blog>().HasQueryFilter(b => b.TenantId == _tenant.Current);
```

## ⚖️ The security checklist

| Control | Do |
|---------|----|
| Injection | LINQ / interpolated `FromSql` / explicit params — never concatenate into `*Raw` |
| Privilege | App account = datareader + datawriter, **not** db_owner/sa |
| In transit | `Encrypt=True` + real cert |
| At rest | TDE; Always Encrypted / KMS for column secrets |
| Secrets | User secrets / Key Vault / Managed Identity — never in source |
| Logs | No `EnableSensitiveDataLogging` in prod |
| Over-fetch | Project to DTOs; never return raw entities to clients |
| Tenancy | Query filters enforce isolation automatically |

## 🚫 Common mistakes

```csharp
// ❌ FromSqlRaw with concatenation (injection)
// ❌ App connecting as sa / db_owner
// ❌ Returning User entities (with PasswordHash) from a controller
// ❌ EnableSensitiveDataLogging in production
// ❌ TrustServerCertificate=True in production
// ❌ Soft-delete without a query filter → "deleted" rows leak through APIs
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 9** added a safer **`FromSql`** to the **Cosmos** provider (parameterized) to replace
  injection-prone `FromSqlRaw`.
- **EF 10 named query filters** make robust multi-tenant isolation easier (disable only the
  soft-delete filter for admins, keep tenant scoping intact).
- Parameterization defaults are unchanged and safe across all versions.

## 🌍 Real-world production tips

- **Project to DTOs at the API boundary** — the simplest defense against data over-exposure.
- **Passwordless (Managed Identity)** removes the biggest secret-leak vector.
- **Query filters for tenancy** — never rely on every developer remembering to add `Where(TenantId
  == ...)`.
- Add EF security items to your **PR checklist**: any new `FromSqlRaw`? any entity returned from a
  controller? any new sensitive column?

## 🎯 Practice (with full solutions)

### 1. Close an injection hole — `Easy`
**Smelly code:**
```csharp
var blogs = await ctx.Blogs.FromSqlRaw("SELECT * FROM Blogs WHERE Title = '" + title + "'").ToListAsync();
```
**Solution:**
```csharp
var blogs = await ctx.Blogs.FromSql($"SELECT * FROM Blogs WHERE Title = {title}").ToListAsync();
// or: FromSqlRaw("SELECT * FROM Blogs WHERE Title = {0}", title)
```
**Why it's better:** `{title}` is sent as a parameter, not concatenated — injection-proof.

### 2. Stop leaking sensitive columns — `Easy`
**Smelly code:**
```csharp
[HttpGet] public Task<List<User>> GetAll() => ctx.Users.ToListAsync();   // returns PasswordHash etc.
```
**Solution:**
```csharp
public record UserDto(int Id, string DisplayName);
[HttpGet] public Task<List<UserDto>> GetAll() =>
    ctx.Users.Select(u => new UserDto(u.Id, u.DisplayName)).ToListAsync();
```
**Why it's better:** only safe fields leave the server; `PasswordHash` and internal columns never
hit the wire. Security + performance in one move.

## ✅ Key Takeaways

- EF is **injection-safe by default** — danger comes from concatenating into `FromSqlRaw`/`ExecuteSqlRaw`.
- Run the app under a **least-privilege** DB account; migrations under a separate elevated one.
- **Encrypt** in transit (`Encrypt=True`) and at rest (TDE / Always Encrypted); keep secrets in a
  vault or use **Managed Identity**.
- **Never** `EnableSensitiveDataLogging` in prod; **project to DTOs** to avoid over-exposure.
- Enforce **tenant isolation** with query filters, not developer discipline.

**Self-check:**
1. When is EF vulnerable to SQL injection, and how do you avoid it?
2. Why project to DTOs instead of returning entities from an API?
3. What database privileges should the running app actually have?
