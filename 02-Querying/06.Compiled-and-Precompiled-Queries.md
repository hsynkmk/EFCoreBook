# Compiled & Precompiled Queries

## 🧠 Intuition

EF Core caches the SQL it generates for a LINQ query — same query shape → reuse the plan, skip
translation. That's the plan cache. **Compiled queries** go further: you can pre-build a delegate
that captures EF's translation pipeline so subsequent executions skip most of the per-call work.
**EF 9 + 10 precompiled queries** push this further by doing model + query compilation at *build
time* for faster startup and AOT-friendly code.

> 💡 Most apps never need to compile a query manually — EF's plan cache is excellent. Reach for
> compiled queries when **a small set of queries runs millions of times** and you've already
> picked the obvious wins (no-tracking, projection, indexes).

## 💻 Manual compiled queries

```csharp
// Define once (typically at class level)
private static readonly Func<BloggingContext, int, Task<Blog?>> _byIdAsync =
    EF.CompileAsyncQuery((BloggingContext ctx, int id) =>
        ctx.Blogs.FirstOrDefault(b => b.Id == id));

// Use anywhere
var blog = await _byIdAsync(ctx, 42);
```

The compiled delegate caches:
- The translated SQL.
- The parameter binding.
- The result materializer.

For high-frequency endpoints this saves measurable CPU per call. **Profile first** — for typical
apps, the savings vs the plan cache aren't worth the indirection.

## 💻 The MSBuild compiled model (EF 9+)

For **large models** (hundreds of entities), building the model on first use is slow. EF 9
introduced MSBuild integration so the model is compiled at build time:

In your `.csproj`:
```xml
<PropertyGroup>
  <EFOptimizeContext>true</EFOptimizeContext>
  <EFScaffoldModelStage>build</EFScaffoldModelStage>
</PropertyGroup>
```

EF generates a model assembly during `dotnet build`. At runtime the context loads it instantly —
no model discovery, much faster cold start.

```text
Starting application...
Model loaded with 273 entity types.
```

You can verify in the build output:
```
Generating EF Core compiled model for BloggingContext
```

Whenever you change the model, the next build re-generates the compiled model automatically.

## 💻 Precompiled queries (EF 10 — the AOT story)

EF 10 continues the precompilation push: queries themselves can be pre-translated and integrated
with **Native AOT** compilation. The combination of a compiled model + precompiled queries means
EF doesn't need expression-tree compilation at runtime, which is the main blocker for AOT
deployment.

> 🆕 Status & exact APIs evolve per release. Check the [EF 10 What's New](../08-Whats-New/01.EF-Core-10.md)
> page in this course (and the Microsoft docs) for the up-to-date wiring.

## ⚖️ Trade-offs

**Pros:** lower per-call CPU; predictable performance on hot paths; AOT-friendly with the model
compiled at build time.
**Cons:** added build/setup complexity; manual `CompileAsyncQuery` adds static state you must
manage carefully; not all queries can be compiled (anything with closures over context state
won't).

## ✅ When to reach for it

- Cold-start latency matters (serverless, mobile, large models) → **MSBuild compiled model**.
- A specific endpoint is **CPU-bound on EF translation** under load → **`EF.CompileAsyncQuery`**.
- You're targeting **AOT** → use both, plus the EF 10 precompiled-query workflow.

## 🚫 Common mistakes

```csharp
// ❌ Compiled query that captures a request-scoped value via closure
var query = EF.CompileAsyncQuery((BloggingContext ctx, int id) =>
    ctx.Blogs.Where(b => b.TenantId == _currentTenant.Id && b.Id == id).FirstOrDefault());
// `_currentTenant.Id` is captured ONCE at compile time → wrong tenant served forever
// ✅ pass it as a parameter
var query = EF.CompileAsyncQuery((BloggingContext ctx, int tenantId, int id) =>
    ctx.Blogs.Where(b => b.TenantId == tenantId && b.Id == id).FirstOrDefault());

// ❌ Premature compilation
// The plan cache already serves identical-shaped LINQ queries fast. Profile first.
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** `EF.CompileQuery` / `EF.CompileAsyncQuery` mature.
- **EF 9:** **MSBuild integration** for the compiled model (`<EFOptimizeContext>`); read-only
  primitive collections; many translation improvements.
- **EF 10:** continued **precompiled query** investment toward AOT; cleaner emitted SQL with
  human-friendly parameter names.

## 🌍 Real-world production tips

- For 99% of apps, **the default plan cache + no-tracking + projection** beats any manual
  compilation.
- The biggest practical win is the **MSBuild compiled model** for large schemas — turn it on, see
  cold-start drop.
- Always **measure**: `BenchmarkDotNet`, real load tests, before and after.

## 🎯 Practice (with full solutions)

### 1. Cache a hot lookup — `Easy`
**Task:** `GET /blogs/{id}` is the most-hit endpoint. Compile its query once.
**Solution:**
```csharp
public static class BlogQueries {
    public static readonly Func<BloggingContext, int, Task<Blog?>> ByIdAsync =
        EF.CompileAsyncQuery((BloggingContext ctx, int id) =>
            ctx.Blogs.AsNoTracking().FirstOrDefault(b => b.Id == id));
}

// Usage
var blog = await BlogQueries.ByIdAsync(ctx, id);
```
**Why it's better:** translation runs once; subsequent calls only execute the delegate. Pair with
`AsNoTracking()` for full effect.

### 2. Turn on the EF 9 compiled model — `Easy`
**Task:** Reduce cold-start time on a project with ~200 entities.
**Solution:** add to the project's `.csproj`:
```xml
<PropertyGroup>
  <EFOptimizeContext>true</EFOptimizeContext>
  <EFScaffoldModelStage>build</EFScaffoldModelStage>
</PropertyGroup>
```
Rebuild — the model is generated and persisted. First-request latency drops noticeably.
**Why it's better:** model build moves from runtime to build time. Lower cold-start, no code
changes elsewhere.

## ✅ Key Takeaways

- EF's **plan cache** already saves you on repeated query shapes; compile manually only when
  needed.
- **`EF.CompileAsyncQuery`** caches translation/materialization for a known LINQ shape.
- **EF 9 MSBuild integration** moves model build to compile time — big cold-start wins.
- **EF 10** continues the precompilation push toward AOT.

1. What does EF's plan cache already give you for free?
2. What's the danger of closing over scoped state in a compiled query?
3. How does the MSBuild compiled model help startup?
