# No-Tracking & Identity Resolution

## 🧠 Intuition

By default, EF **tracks** every entity returned from a query — it snapshots the current values so
`SaveChangesAsync` knows what changed. Tracking costs memory and CPU. For **read-only paths**, you
don't need it; **`AsNoTracking()`** drops that work and is the single most common one-line perf
win in EF.

> 💡 If you'll never call `SaveChangesAsync` on what you queried, **don't track it.**

The catch: untracked queries return **fresh instances** for each row, even when two rows reference
the same entity. **`AsNoTrackingWithIdentityResolution()`** turns this off — same instance is
reused — at a small cost.

## 💻 The common pattern

```csharp
var dtos = await ctx.Blogs
    .AsNoTracking()                             // drop tracking — read-only
    .Where(b => b.Views > 1000)
    .Select(b => new BlogDto(b.Id, b.Title))   // projection — even better
    .ToListAsync();
```

Pair `AsNoTracking()` with projection to a DTO for the biggest single wins:
- No snapshots in memory.
- No identity map.
- Only the columns you projected come back from the database.

## 💻 When you need identity resolution

```csharp
// Without identity resolution, blog rows in this result may be DIFFERENT instances even when they're the same Id
var posts = await ctx.Posts
    .AsNoTracking()
    .Include(p => p.Blog)
    .Where(p => p.PublishedUtc > someDate)
    .ToListAsync();

// posts[0].Blog and posts[1].Blog might be two distinct Blog instances with the same Id
```

To force "one C# instance per DB row," use **`AsNoTrackingWithIdentityResolution()`** (EF 5+):
```csharp
var posts = await ctx.Posts
    .AsNoTrackingWithIdentityResolution()
    .Include(p => p.Blog)
    .ToListAsync();
// posts[0].Blog and posts[1].Blog are the SAME instance when they share an Id
```

Useful when downstream code does reference equality checks or builds an in-memory graph from
the results.

## 💻 Setting no-tracking as the default

```csharp
opt.UseSqlServer(connectionString)
   .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
```

Now every query is no-tracking by default — opt back in with `.AsTracking()` when you need to
mutate-and-save. Many teams adopt this default in services where mutations are explicit.

## ⚖️ Trade-offs

**Pros of no-tracking:** lower memory; faster materialization; encourages clear separation between
read paths and write paths.
**Cons:** can't simply `SaveChangesAsync` on a no-tracking entity — you need to attach it first.
Identity resolution adds a small cost compared to plain `AsNoTracking`.

| | Tracking (default) | `AsNoTracking` | `AsNoTrackingWithIdentityResolution` |
|--|---------------------|----------------|--------------------------------------|
| Snapshots? | Yes | No | No |
| Same Id → same instance? | Yes (identity map) | **No** | Yes |
| Can update + Save? | Yes | Need `Attach` + `EntityState.Modified` | Same |
| Cost | Memory + CPU | Lowest | Low + small dictionary |

## 🚫 Common mistakes

```csharp
// ❌ AsNoTracking and then mutate and save
var blog = await ctx.Blogs.AsNoTracking().SingleAsync(b => b.Id == id);
blog.Title = "New";
await ctx.SaveChangesAsync();   // does nothing — entity isn't tracked
// ✅ either drop AsNoTracking, or attach and set state explicitly
ctx.Update(blog);
await ctx.SaveChangesAsync();

// ❌ AsNoTracking on writes — same trap

// ❌ AsTracking on huge read-only queries → memory waste
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- Stable since EF 5. EF 8/9 have ongoing perf improvements to no-tracking materialization.
- **EF 10**: no semantic change; combined with **`MSBuild compiled model`** + projection, the
  read-side perf story is excellent.

## 🌍 Real-world production tips

- **Default to no-tracking** on read-side services; opt into tracking in write-side command
  handlers. Makes intent unmistakable.
- Combine with **projections** — `Select(... new XxxDto(...))` removes most of the question.
- For pages that read the same `Blog` many times in one request, **identity resolution** or a
  small per-request cache prevents downstream surprises.

## 🎯 Practice (with full solutions)

### 1. Trim a read endpoint — `Easy`
**Smelly code:**
```csharp
var dtos = (await ctx.Blogs.ToListAsync())
    .Where(b => b.Views > 1000)
    .Select(b => new BlogDto(b.Id, b.Title))
    .ToList();
```
**Solution:**
```csharp
var dtos = await ctx.Blogs
    .AsNoTracking()
    .Where(b => b.Views > 1000)
    .Select(b => new BlogDto(b.Id, b.Title))
    .ToListAsync();
```
**Why it's better:** server-side filter, server-side projection, no tracking overhead. Memory and
CPU drop; SQL gets `WHERE` + narrow `SELECT`.

### 2. Force identity in a graph — `Medium`
**Task:** Build a flat list of posts with their blog, where downstream code groups posts by blog
using reference equality.
**Solution:**
```csharp
var posts = await ctx.Posts
    .AsNoTrackingWithIdentityResolution()
    .Include(p => p.Blog)
    .ToListAsync();

var byBlog = posts.GroupBy(p => p.Blog).ToList();   // groups correctly — same Blog instance
```
**Why it's better:** with plain `AsNoTracking()`, the same blog would appear as separate
instances and grouping would explode into singletons.

## ✅ Key Takeaways

- **`AsNoTracking()`** is the cheapest perf win in EF for read-only paths.
- Pair with **projections** for compound gains.
- Use **`AsNoTrackingWithIdentityResolution()`** when you need reference equality across rows.
- Consider **`QueryTrackingBehavior.NoTracking`** as the default on read-side services.
- Don't try to `SaveChanges` on no-tracking entities without attaching them first.
