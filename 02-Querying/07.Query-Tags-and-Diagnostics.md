# Query Tags & Diagnostics

## 🧠 Intuition

When SQL Profiler or your log aggregator shows a slow query, the first question is *"which LINQ
expression in our codebase emitted this?"*. **Query tags** prepend a comment to the SQL so you can
identify it instantly. Combined with **`LogTo`** for capturing all SQL and **`EnableSensitiveData­
Logging`** for full parameter values (dev only!), they're the "always-on" toolkit for diagnosing
EF in development and production.

> 💡 **`TagWith`** is the cheapest, highest-value habit in EF. Tag every important query and your
> incident response gets 10× faster.

## 💻 Tag a query

```csharp
var blogs = await ctx.Blogs
    .TagWith("HomePage.TrendingBlogs")
    .Where(b => b.Views > 1000)
    .OrderByDescending(b => b.Views)
    .Take(20)
    .ToListAsync();
```

**⚡ Generated SQL:**
```sql
-- HomePage.TrendingBlogs

SELECT TOP(20) [b].[Id], [b].[Title] ...
FROM [Blogs] AS [b]
WHERE [b].[Views] > 1000
ORDER BY [b].[Views] DESC
```

In SQL Profiler / Application Insights / Datadog, you'll see the tag in the query text. Searchable.

You can chain tags: `.TagWith("Layer.Service").TagWith("Operation.GetTrending")` — both comments
appear in the SQL.

## 💻 Capture SQL with `LogTo`

```csharp
opt.UseSqlServer(connectionString)
   .LogTo(Console.WriteLine, LogLevel.Information)
   .EnableSensitiveDataLogging();          // DEV ONLY — logs parameter values too
```

For production, log to your structured logger (Serilog / ILogger) at `LogLevel.Warning` only, and
**do not enable sensitive data logging** unless you've thought through what ends up in logs.

```csharp
// Production-safe shape
opt.UseSqlServer(cs)
   .LogTo(message => logger.LogDebug("{Sql}", message), new[] { DbLoggerCategory.Database.Command.Name }, LogLevel.Warning);
```

## 💻 Get the SQL from an `IQueryable`

```csharp
var query = ctx.Blogs.Where(b => b.Views > 1000).OrderBy(b => b.Id);
var sql = query.ToQueryString();   // EF 5+
Console.WriteLine(sql);
```

`ToQueryString()` shows EF's generated SQL without executing it. Great for diagnosing translation
issues *before* hitting the database.

## 💻 EF events / `DiagnosticListener`

For deeper integration (APM tools, custom telemetry), EF emits diagnostic events:
- `Microsoft.EntityFrameworkCore.Database.Command.CommandExecuting`
- `Microsoft.EntityFrameworkCore.Database.Command.CommandExecuted`
- `Microsoft.EntityFrameworkCore.Database.Command.CommandError`

Application Insights, OpenTelemetry, Datadog, etc., pick these up automatically once their EF
instrumentation is wired in.

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8 / 9 / 10:** all support `TagWith`, `LogTo`, `ToQueryString`, and the diagnostic
  listeners. EF 10 cleaned up parameter names (`@blogId` vs `@__blogId_0`) so logged SQL is much
  more readable.
- **EF 10** Cosmos provider logs the partition key and RU charge per call — extremely helpful for
  cost diagnosis.

## 🌍 Real-world production tips

- **Tag everywhere**: `service.method.purpose` — searchable, traceable, zero perf cost.
- **`EnableSensitiveDataLogging` is OFF in prod.** It writes parameter values to your logs, which
  often includes PII.
- Pair with **OpenTelemetry** EF instrumentation for end-to-end traces (controller → EF query →
  database).
- Build an "EF slow query" alert by filtering tagged commands above a duration threshold.

## 🎯 Practice (with full solutions)

### 1. Identify a mystery query — `Easy`
**Scenario:** the DBA pings you about a slow query they see hit production at 3 AM:
```sql
SELECT TOP(20) [b].[Id], [b].[Title] FROM [Blogs] AS [b] WHERE ...
```
**Task:** make it instantly identifiable.
**Solution:** tag the relevant LINQ call:
```csharp
var blogs = await ctx.Blogs
    .TagWith("Reports.NightlyDigest")
    .Where(...)
    .Take(20)
    .ToListAsync();
```
The next run shows the tag in the SQL. Search the codebase for `Reports.NightlyDigest` →
straight to the source.
**Why it's better:** zero-cost annotation that survives every layer between LINQ and the DB.

### 2. Inspect SQL without executing — `Easy`
**Task:** A teammate's LINQ expression is producing surprising results. Find out what SQL EF
generates without running it.
**Solution:**
```csharp
var sql = ctx.Blogs
    .Where(b => b.Views > 1000)
    .Select(b => new { b.Id, b.Title })
    .ToQueryString();
Console.WriteLine(sql);
```
**Why it's better:** instant feedback, no DB round-trip, perfect for pull-request review.

## ✅ Key Takeaways

- **`TagWith("...")`** is the single highest-value habit: SQL annotations that survive into prod.
- **`LogTo` + structured logger** captures EF SQL safely; keep **`EnableSensitiveDataLogging` off
  in prod**.
- **`ToQueryString()`** inspects SQL without executing.
- EF emits **diagnostic events** that APM tools consume automatically.

**Self-check:**
1. What does `TagWith` add to the emitted SQL?
2. Why is `EnableSensitiveDataLogging` a production no-go by default?
3. What does `ToQueryString()` give you that running the query doesn't?
