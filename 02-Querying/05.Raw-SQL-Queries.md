# Raw SQL Queries

## 🧠 Intuition

EF translates a lot of LINQ, but **not everything**. For provider-specific tricks, very complex
aggregations, or hand-tuned queries the LINQ translator won't hit, you can drop straight to SQL —
and still benefit from EF's parameterization, result mapping, and integration with the rest of
the query pipeline.

> 💡 **Three flavors:**
> - **`FromSql`** — write SQL that returns rows for an existing entity type. Still queryable in LINQ.
> - **`SqlQuery<T>`** (EF 8+) — write SQL that returns rows for a **primitive or unmapped type**.
> - **`ExecuteSql`** — fire a non-query (INSERT/UPDATE/DELETE/DDL) and get a row count.

All three **parameterize** when you use interpolated strings — that's how they're safe.

## 🎯 The Problem

```csharp
// ❌ Before: building SQL with string concatenation — SQL injection waiting to happen
var sql = $"SELECT * FROM Blogs WHERE Title = '{userInput}'";
var rows = await ctx.Database.GetDbConnection().QueryAsync(sql);   // 💥
```

A user input of `' OR 1=1 --` is now an authentication bypass.

## 💻 `FromSql` (for entity types)

```csharp
var name = userInput;
var blogs = await ctx.Blogs
    .FromSql($"SELECT * FROM Blogs WHERE Title LIKE {name}")     // interpolation is safe
    .Where(b => b.Views > 100)                                   // composes with LINQ
    .ToListAsync();
```

Interpolation in `FromSql` is **automatically parameterized** — the `{name}` becomes `@p0` in the
emitted SQL, with the value bound separately. Safe.

```csharp
// You can also pass parameters explicitly
var blogs = await ctx.Blogs
    .FromSql($"EXEC GetActiveBlogs @TenantId = {tenantId}")
    .ToListAsync();
```

Constraints:
- The result columns must match the entity's mapped columns (names, types).
- You can compose **`.Where()`**, `.OrderBy()`, `.Include()`, etc., over the result.
- For string-format strings (not interpolation), use **`FromSqlRaw`** with explicit parameters —
  don't concatenate.

## 💻 `SqlQuery<T>` for primitives / DTOs (EF 8+)

```csharp
// EF 8+: query into a primitive or an unmapped type without configuring it as an entity
var ids = await ctx.Database
    .SqlQuery<int>($"SELECT Id FROM Blogs WHERE Views > {threshold}")
    .ToListAsync();

public record BlogStat(int Id, string Title, int PostCount);

var stats = await ctx.Database
    .SqlQuery<BlogStat>($"""
        SELECT b.Id, b.Title, COUNT(p.Id) AS PostCount
        FROM Blogs b LEFT JOIN Posts p ON p.BlogId = b.Id
        WHERE b.Views > {threshold}
        GROUP BY b.Id, b.Title
        """)
    .ToListAsync();
```

Before EF 8 you had to register the result type in the model with `[Keyless]` (or `HasNoKey`).
EF 8+ `SqlQuery<T>` handles it on the fly — much cleaner for one-off reporting queries.

## 💻 `ExecuteSql` for commands

```csharp
var rowsAffected = await ctx.Database.ExecuteSqlAsync(
    $"UPDATE Blogs SET Views = Views + 1 WHERE Id = {blogId}");
```

Returns the number of affected rows. For most "bulk update" needs, prefer the higher-level
**`ExecuteUpdateAsync`** / **`ExecuteDeleteAsync`** (see
[Bulk Operations](../03-Saving-and-Concurrency/05.Bulk-Operations.md)) — they're parameterized,
LINQ-friendly, and provider-portable. Use `ExecuteSql` when you genuinely need SQL EF can't
emit (DDL, provider-specific commands).

## ⚖️ Trade-offs

**Pros:** access to anything the database supports; composes with LINQ (for `FromSql`); EF still
parameterizes when you interpolate.
**Cons:** provider-specific (`SELECT *` form varies); easy to break if columns are renamed in
migrations; LINQ refactors don't catch it.

## 🚫 Common mistakes

```csharp
// ❌ String concatenation = injection
ctx.Blogs.FromSqlRaw("SELECT * FROM Blogs WHERE Title = '" + userInput + "'");

// ✅ interpolation OR FromSqlRaw with explicit params
ctx.Blogs.FromSql($"SELECT * FROM Blogs WHERE Title = {userInput}");
ctx.Blogs.FromSqlRaw("SELECT * FROM Blogs WHERE Title = {0}", userInput);

// ❌ Forgetting that FromSql composes — running the inefficient SQL when you didn't need to
var sql = $"SELECT * FROM Blogs";              // returns everything
await ctx.Blogs.FromSql(sql).Where(b => b.Views > 100).ToListAsync();
// ✅ either filter in SQL, or trust EF's WHERE — but know the DB sees the whole SQL first
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** **`Database.SqlQuery<T>`** for raw-SQL primitive/unmapped results — the big quality-
  of-life addition. Also `SqlQuery<T>` on `IQueryable` for composing.
- **EF 9:** Cosmos provider got a safer **`FromSql`** (parameterized SQL) replacing `FromSqlRaw`.
- **EF 10:** consistent parameter naming (`@blogId` etc.) makes captured SQL much easier to read.

## 🌍 Real-world production tips

- For **read-only reporting**, `SqlQuery<DTO>` is often the cleanest path — no entity to maintain.
- Use **named parameters** when possible. Capture SQL via `LogTo` and verify the parameter
  binding is what you expect.
- Don't run **`SELECT *`** in `FromSql` — list the columns explicitly. Schemas change.
- For DDL / provider commands, you still need `ExecuteSql` (or migrations).

## 🎯 Practice (with full solutions)

### 1. Safe interpolated query — `Easy`
**Task:** Find blogs whose title matches a user-supplied pattern, *safely*.
**Solution:**
```csharp
var pattern = "%" + userInput + "%";
var blogs = await ctx.Blogs
    .FromSql($"SELECT * FROM Blogs WHERE Title LIKE {pattern}")
    .ToListAsync();
```
**Why it's better:** `{pattern}` is parameterized — injection-safe. (Better still: use
`EF.Functions.Like` instead of SQL.)

### 2. Reporting query into a DTO — `Medium`
**Task:** Top 10 blogs by post count, returned as a slim DTO.
**Solution:**
```csharp
public record BlogStat(int Id, string Title, int PostCount);

var top = await ctx.Database.SqlQuery<BlogStat>($"""
    SELECT TOP 10 b.Id, b.Title, COUNT(p.Id) AS PostCount
    FROM Blogs b LEFT JOIN Posts p ON p.BlogId = b.Id
    GROUP BY b.Id, b.Title
    ORDER BY COUNT(p.Id) DESC
""").ToListAsync();
```
**Why it's better:** no entity to model just for a report; results stream straight into the
record; parameterization still applies if you add inputs.

## ✅ Key Takeaways

- **Three flavors:** `FromSql` (entities), **`SqlQuery<T>`** (primitives/DTOs — EF 8+),
  `ExecuteSql` (commands).
- **Always parameterize.** Interpolation in `FromSql` / `SqlQuery` is safe by construction.
- `FromSql` **composes** with LINQ — but remember the DB still sees your raw SQL first.
- For bulk updates/deletes, prefer **`ExecuteUpdateAsync`** / **`ExecuteDeleteAsync`** over
  `ExecuteSql`.
