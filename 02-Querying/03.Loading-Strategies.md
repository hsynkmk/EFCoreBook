# Loading Strategies: Eager, Explicit, Lazy

## 🧠 Intuition

When you query `Blog`, do you also want its `Posts`? Sometimes yes (a page that lists posts under
a blog), sometimes no (a page that lists blog titles). EF gives you three loading strategies:
**eager** (fetch the related data in the same trip via `Include`), **explicit** (load it on
demand with a separate query you write), or **lazy** (EF loads navigations transparently the
first time you access them).

> 💡 **Lazy loading is the easiest to write and the easiest way to ship an N+1 problem.** Prefer
> eager or explicit and use lazy sparingly.

## 🎯 The Problem: the classic N+1

```csharp
// ❌ Lazy loading without realising it — one query for blogs, then ONE QUERY PER BLOG for posts
foreach (var b in await ctx.Blogs.ToListAsync()) {
    Console.WriteLine($"{b.Title}: {b.Posts.Count} posts");   // each .Posts triggers a SELECT
}
```

Ten blogs → 11 queries. Ten thousand blogs → 10,001. The database is fine; your latency isn't.

## 💻 Eager loading — `Include`

```csharp
var blogsWithPosts = await ctx.Blogs
    .Include(b => b.Posts)
    .Where(b => b.Views > 1000)
    .ToListAsync();

// Multi-level (Posts → Comments)
var deep = await ctx.Blogs
    .Include(b => b.Posts)
        .ThenInclude(p => p.Comments)
    .ToListAsync();

// Filtered Include (EF 5+)
var withRecentPosts = await ctx.Blogs
    .Include(b => b.Posts.Where(p => p.PublishedUtc > DateTime.UtcNow.AddDays(-30)))
    .ToListAsync();
```

`Include` emits a single query with `JOIN`s. For multiple collection includes, that JOIN can
**explode into a cartesian** — switch to `AsSplitQuery()` (see [Split Queries](04.Split-Queries.md)).

## 💻 Explicit loading

```csharp
var blog = await ctx.Blogs.SingleAsync(b => b.Id == 42);
// Later:
await ctx.Entry(blog).Collection(b => b.Posts).LoadAsync();
await ctx.Entry(blog).Reference(b => b.Author).LoadAsync();
```

Explicit loading is great when **whether to load** is decided at runtime — you don't always need
posts, but sometimes you do.

## 💻 Lazy loading (use sparingly)

```csharp
// Setup
dotnet add package Microsoft.EntityFrameworkCore.Proxies
opt.UseLazyLoadingProxies().UseSqlServer(...);

// Mark navigations virtual
public class Blog {
    public int Id { get; set; }
    public virtual List<Post> Posts { get; set; } = new();    // EF wraps this in a proxy
}

// Usage
var blog = await ctx.Blogs.SingleAsync(b => b.Id == 42);
foreach (var p in blog.Posts) { ... }   // first access triggers a SELECT
```

Or without proxies, inject `ILazyLoader` into entities. Either way, the cost is the same: each
navigation access may be a round-trip.

> ⚠️ Lazy loading is **disabled by default** in EF Core — and that's the right default. Turn it
> on knowingly, for short scripts or specific scenarios. Production apps almost always want
> eager/explicit.

## ⚖️ Choosing a strategy

| Question | Use |
|----------|-----|
| Do I always need the related data? | **Eager** (`Include`) |
| Do I sometimes need it, decided at runtime? | **Explicit** (`Entry().Collection().LoadAsync()`) |
| Do I want EF to do it transparently and I accept the risk of N+1? | **Lazy** (proxies) |
| Do I want only specific columns? | **Projection** with `Select` (often beats `Include`) |

## ⚡ Generated SQL

### `Include` (eager)
```sql
SELECT [b].[Id], [b].[Title], [p].[Id], [p].[BlogId], [p].[Heading]
FROM [Blogs] AS [b]
LEFT JOIN [Posts] AS [p] ON [b].[Id] = [p].[BlogId]
ORDER BY [b].[Id]
```

### `.AsSplitQuery()` (eager, no cartesian)
```sql
-- query 1
SELECT [b].[Id], [b].[Title] FROM [Blogs] AS [b] ORDER BY [b].[Id];
-- query 2 (joined back via FK)
SELECT [p].[Id], [p].[BlogId], [p].[Heading]
FROM [Blogs] AS [b]
INNER JOIN [Posts] AS [p] ON [b].[Id] = [p].[BlogId]
ORDER BY [b].[Id];
```

### Projection (often the best of all)
```csharp
var titlesAndCounts = await ctx.Blogs
    .Select(b => new { b.Title, PostCount = b.Posts.Count() })
    .ToListAsync();
```
emits a single query with `COUNT()` and pulls **only** the columns you asked for. No `Include`, no
N+1, no cartesian.

## 🚫 Common mistakes

```csharp
// ❌ Include + ToList, then projecting on the client → wasted work
var blogs = await ctx.Blogs.Include(b => b.Posts).ToListAsync();
var dtos = blogs.Select(b => new { b.Title, PostCount = b.Posts.Count }).ToList();
// ✅ project on the SERVER
var dtos = await ctx.Blogs.Select(b => new { b.Title, PostCount = b.Posts.Count() }).ToListAsync();

// ❌ Lazy loading inside a loop after the context is gone
// → ObjectDisposedException, or a half-disposed context if you got lucky
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** lazy-loading proxies got assorted improvements; filtered `Include` is solid.
- **EF 9:** lazy-loading internals tuned; `AsyncLocal` changes for better lazy-load perf.
- **EF 10:** no big strategic change here; the bigger win is **`LeftJoin`/`RightJoin`** for cases
  you previously hand-wrote.

## 🌍 Real-world production tips

- **Project to DTOs** rather than including everything when you only need a few fields. It's the
  single biggest perf lever in EF.
- **Filtered `Include`** is excellent: `Include(b => b.Posts.Where(...))` keeps payload bounded.
- **Two `Include`s of collections** → use `AsSplitQuery()` (next file).
- Lazy loading proxies + DI-scoped DbContext + background work = **classic disposed-context bug**.

## 🎯 Practice (with full solutions)

### 1. Defuse an N+1 — `Easy`
**Smelly code:** the loop in The Problem.
**Solution (two equally valid approaches):**
```csharp
// (a) eager loading
foreach (var b in await ctx.Blogs.Include(b => b.Posts).ToListAsync()) { ... }

// (b) projection — usually cheaper
var rows = await ctx.Blogs
    .Select(b => new { b.Title, Count = b.Posts.Count() })
    .ToListAsync();
foreach (var r in rows) Console.WriteLine($"{r.Title}: {r.Count} posts");
```
**Why it's better:** one round-trip instead of N+1. Projection wins when you don't need the
posts themselves.

### 2. Load on demand — `Medium`
**Task:** A details endpoint loads a blog, and *conditionally* loads its posts only when a
`?includePosts=true` query parameter is set.
**Solution:**
```csharp
var blog = await ctx.Blogs.SingleAsync(b => b.Id == id);
if (includePosts) await ctx.Entry(blog).Collection(b => b.Posts).LoadAsync();
```
**Why it's better:** when posts aren't needed, you save a query (and the rows over the wire).
Explicit loading turns runtime decisions into clean code.

## ✅ Key Takeaways

- **Eager** (`Include`) for "I always need it"; **explicit** for "sometimes"; **lazy** as a last
  resort.
- **Projection beats `Include`** when you don't need full entities — it's faster *and* clearer.
- Multiple collection includes → **`AsSplitQuery()`** to avoid cartesian explosion.
- Lazy loading + scoped context + async = footgun magnet.
