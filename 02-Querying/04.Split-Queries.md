# Split Queries

## 🧠 Intuition

When you `Include` **two or more collection navigations**, EF emits a single SQL query with
multiple `JOIN`s — which can produce a **cartesian product** (every blog row × every post row ×
every comment row). For wide aggregates with deep nesting, the row count explodes and pulls way
more data than you actually need.

> 💡 **`AsSplitQuery()`** tells EF to emit **one query per collection** instead. You pay for
> several round-trips, but each one returns just the rows it needs. For deep includes, that's
> dramatically less data over the wire.

## 🎯 The Problem

```csharp
// ❌ Before: single query, cartesian explosion
var blogs = await ctx.Blogs
    .Include(b => b.Posts)
        .ThenInclude(p => p.Comments)
    .Include(b => b.Tags)
    .ToListAsync();
```

If a blog has 100 posts × 10 comments × 5 tags, you can get **50,000 rows in the result set** for
*one* blog. The per-row data is repeated heavily, and parsing it client-side takes time.

## 💻 The fix

```csharp
var blogs = await ctx.Blogs
    .Include(b => b.Posts).ThenInclude(p => p.Comments)
    .Include(b => b.Tags)
    .AsSplitQuery()                                  // separate query per collection
    .ToListAsync();
```

EF now emits **three queries** instead of one: blogs, posts/comments, tags — each carrying just
its rows. EF stitches them together by FK.

## ⚡ Generated SQL — single vs split

### Single (default)
```sql
SELECT [b].*, [p].*, [c].*, [t].*
FROM [Blogs] AS [b]
LEFT JOIN [Posts] AS [p] ON [b].[Id] = [p].[BlogId]
LEFT JOIN [Comments] AS [c] ON [p].[Id] = [c].[PostId]
LEFT JOIN [Tags] AS [t] ON [b].[Id] = [t].[BlogId]
ORDER BY [b].[Id], [p].[Id], [c].[Id]
```

### Split
```sql
-- 1. Blogs
SELECT [b].[Id], [b].[Title] FROM [Blogs] AS [b] ORDER BY [b].[Id];
-- 2. Posts + Comments joined to the same blog ids
SELECT [p].*, [c].*
FROM [Blogs] AS [b]
INNER JOIN [Posts] AS [p] ON [b].[Id] = [p].[BlogId]
LEFT JOIN [Comments] AS [c] ON [p].[Id] = [c].[PostId]
ORDER BY [b].[Id], [p].[Id];
-- 3. Tags
SELECT [t].* FROM [Blogs] AS [b]
INNER JOIN [Tags] AS [t] ON [b].[Id] = [t].[BlogId]
ORDER BY [b].[Id];
```

## ⚖️ Trade-offs

**Single query (default):**
- ✅ One round-trip.
- ❌ Cartesian risk with multiple collections — payload explodes.
- ❌ More CPU on the client to materialize from the wide result.

**Split query (`AsSplitQuery`):**
- ✅ Each query carries only its own rows — far less data.
- ❌ Multiple round-trips (latency adds up over the network).
- ❌ The result sees a **point-in-time per query** — across queries, the database state could
  change. Wrap critical paths in a serializable transaction if exact consistency matters.

## 💻 Make it the default for a `DbContext`

```csharp
opt.UseSqlServer(connectionString, sql => sql.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));
```

Then opt back into single queries case-by-case with `.AsSingleQuery()`.

## 🚫 Common mistakes

```csharp
// ❌ Including two collections without thinking
.Include(b => b.Posts).Include(b => b.Comments).ToListAsync()
// On medium data, this can produce millions of redundant rows.

// ❌ AsSplitQuery on a path with just ONE collection
// Pointless — single is already fine. AsSplitQuery shines when you have ≥ 2 collections.

// ❌ Expecting consistent point-in-time across split queries
// Use a transaction (Serializable) if cross-query consistency matters.
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- Available since EF Core 5. Stable across EF 8/9/10; no behavior changes worth noting.
- EF logs a **warning** in dev when it detects an `Include` likely to cause cartesian explosion —
  watch for it.

## 🌍 Real-world production tips

- For pages that show a header + several nested lists (a blog with posts and tags), `AsSplitQuery`
  almost always wins.
- For **single-collection** includes or single-row-per-blog payloads, the default single query is
  best.
- If you find yourself sprinkling `AsSplitQuery` everywhere, configure it as the **default** and
  opt out where you need consistency.

## 🎯 Practice (with full solutions)

### 1. Spot the cartesian — `Easy`
**Smelly code:** "blog details" endpoint loads blog + posts + tags via two `Include`s and serves
~5MB JSON to the client because the result set is millions of duplicated rows.
**Solution:**
```csharp
var blog = await ctx.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Tags)
    .AsSplitQuery()
    .SingleAsync(b => b.Id == id);
```
**Why it's better:** three small queries vs one giant cartesian. Bandwidth and CPU collapse.

### 2. Default on, opt out — `Medium`
**Task:** Set the entire `DbContext` to default to split queries; keep the legacy `GetSummary`
endpoint using a single query because it's read inside a transaction.
**Solution:**
```csharp
opt.UseSqlServer(cs, sql => sql.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));

var legacy = await ctx.Blogs
    .Include(b => b.Author)
    .AsSingleQuery()
    .ToListAsync();
```
**Why it's better:** safe default for the team; explicit opt-out where you need it.

## ✅ Key Takeaways

- `Include`ing multiple collections can cause a **cartesian explosion** — wide rows, slow parse.
- **`AsSplitQuery()`** turns it into one query per collection — usually a big win.
- Trade-off: **multiple round-trips** and **per-query snapshot** (no cross-query consistency).
- You can set split queries as the **default** for the context.
