# Advanced Querying

## 🧠 Intuition

Past basic CRUD, real queries combine **joins**, **groupings**, **set operations**, and **function
translation**. EF translates more than you'd expect — including, in **EF Core 10**, first-class
**`LeftJoin`** and **`RightJoin`** LINQ operators that match the .NET 10 LINQ improvements. The
remaining art is knowing what EF *can't* translate (and what to do then).

## 💻 `EF.Functions` — database functions in LINQ

```csharp
var likeMatch = await ctx.Blogs
    .Where(b => EF.Functions.Like(b.Title, "%EF Core%"))
    .ToListAsync();

var soundsLike = await ctx.Users
    .Where(u => EF.Functions.Soundex(u.LastName) == EF.Functions.Soundex("Smyth"))
    .ToListAsync();

// SQL Server full-text
var matches = await ctx.Documents
    .Where(d => EF.Functions.Contains(d.Body, "RAG OR embeddings"))
    .ToListAsync();
```

`EF.Functions` is the bridge to provider-specific SQL functions (`LIKE`, `Soundex`,
`PATINDEX`, `FullTextContains`, ...). They translate; methods you write yourself don't.

## 💻 Joins (and EF 10's `LeftJoin`/`RightJoin`)

```csharp
// Inner join (classic)
var query = from b in ctx.Blogs
            join p in ctx.Posts on b.Id equals p.BlogId
            select new { b.Title, p.Heading };

// EF 10: first-class LeftJoin
var withMaybeAuthor = await ctx.Posts
    .LeftJoin(ctx.Users, p => p.AuthorId, u => u.Id, (p, u) => new { p.Heading, AuthorName = u != null ? u.Name : "(unknown)" })
    .ToListAsync();
```

**⚡ Generated SQL** for the EF 10 `LeftJoin`:
```sql
SELECT [p].[Heading], CASE WHEN [u].[Id] IS NULL THEN N'(unknown)' ELSE [u].[Name] END AS [AuthorName]
FROM [Posts] AS [p]
LEFT JOIN [Users] AS [u] ON [p].[AuthorId] = [u].[Id]
```

Before EF 10, you wrote `GroupJoin + SelectMany + DefaultIfEmpty`. The new operators are the same
SQL, far cleaner C#.

## 💻 Grouping

```csharp
var perTenant = await ctx.Orders
    .GroupBy(o => o.TenantId)
    .Select(g => new { TenantId = g.Key, Total = g.Sum(o => o.Amount), Count = g.Count() })
    .ToListAsync();
```

**⚡ Generated SQL:**
```sql
SELECT [o].[TenantId], SUM([o].[Amount]) AS [Total], COUNT(*) AS [Count]
FROM [Orders] AS [o]
GROUP BY [o].[TenantId]
```

EF translates `GroupBy + aggregate Select` to `GROUP BY`. Grouping followed by **non-aggregate**
projection often forces materialization — refactor to two queries when EF complains.

## 💻 Set operations

```csharp
var unique = await ctx.Blogs.Select(b => b.Title)
    .Union(ctx.OldBlogs.Select(b => b.Title))   // UNION
    .ToListAsync();

var inBoth = await ctx.A.Intersect(ctx.B).ToListAsync();   // INTERSECT
var onlyInA = await ctx.A.Except(ctx.B).ToListAsync();     // EXCEPT
```

## 💻 Windowing-ish patterns (without `OVER`)

EF doesn't translate full SQL windowing yet, but two patterns cover most needs:

- **Top-N per group** — `GroupBy + Select(g => g.OrderBy(...).First())` (uses `OUTER APPLY` on SQL Server).
- **Running totals** — fall back to **raw SQL** (next file) when you genuinely need `SUM() OVER`.

## ⚖️ When EF can't translate — your options

1. **Refactor the LINQ.** Often a small change makes it translatable.
2. **Use `EF.Functions.*`** — covers `LIKE`, full-text, `Soundex`, `JsonValue`, etc.
3. **Drop to raw SQL** with `FromSql` (entities) or `SqlQuery<T>` (primitives/DTOs). See
   [Raw SQL Queries](05.Raw-SQL-Queries.md).
4. **Compute on the server with a SQL view or function** that EF maps to.

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** lots of LINQ translation improvements (incl. `string.Join`, enums to `ToString`).
- **EF 9:** **inlined uncorrelated subqueries** (fewer round-trips); read-only collection support;
  improved Cosmos LINQ; `EF.Constant` for opting *out* of collection parameterization.
- **EF 10:** **`LeftJoin`** / **`RightJoin`** operators; `MIN`/`MAX` over `DISTINCT` optimized;
  cleaner parameter names; **parameterized collection padding** (better plan caching).

## 🌍 Real-world production tips

- For complex aggregations, **read the SQL EF emits** and compare with the SQL you'd write by
  hand. Often EF is fine; sometimes it isn't — and a `FromSql` or SQL view is the right answer.
- `EF.Functions.Contains` (SQL Server full-text) is much faster than `Like('%term%')` for text
  search, *if* you have a full-text index.
- For "top-N per group," profile first; `OUTER APPLY` on SQL Server is sometimes slower than
  alternatives.

## 🎯 Practice (with full solutions)

### 1. Clean up a manual `GroupJoin` — `Easy` (EF 10)
**Smelly code:**
```csharp
var rows = await (
    from p in ctx.Posts
    join u in ctx.Users on p.AuthorId equals u.Id into gj
    from u in gj.DefaultIfEmpty()
    select new { p.Heading, AuthorName = u == null ? "(unknown)" : u.Name }
).ToListAsync();
```
**Solution (EF 10):**
```csharp
var rows = await ctx.Posts
    .LeftJoin(ctx.Users, p => p.AuthorId, u => u.Id,
              (p, u) => new { p.Heading, AuthorName = u != null ? u.Name : "(unknown)" })
    .ToListAsync();
```
**Why it's better:** intent is obvious; SQL is identical; no `into gj / DefaultIfEmpty` boilerplate.

### 2. Group with payload — `Medium`
**Task:** Return tenants with their open-order total and last order date.
**Solution:**
```csharp
var perTenant = await ctx.Orders
    .GroupBy(o => o.TenantId)
    .Select(g => new {
        TenantId = g.Key,
        OpenTotal = g.Where(o => o.Status == "Open").Sum(o => o.Amount),
        Last = g.Max(o => o.PlacedUtc)
    })
    .ToListAsync();
```
**Why it's better:** all aggregates in one `GROUP BY` query; no client-side reduction.

## ✅ Key Takeaways

- Use **`EF.Functions`** to reach provider-specific SQL (`Like`, full-text, `Soundex`, etc.).
- **EF 10** turns left/right joins into one-liners with `LeftJoin` / `RightJoin`.
- `GroupBy` translates to `GROUP BY` only when the projection is an aggregate.
- Anything you can't translate? Reach for `FromSql` / `SqlQuery<T>` or a SQL view.
- Always inspect generated SQL on hot queries.

3. When should you stop trying to express something in LINQ and use raw SQL?
