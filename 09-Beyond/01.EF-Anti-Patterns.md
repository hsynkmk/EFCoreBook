# EF Core Anti-Patterns

## 🧠 Intuition

Knowing EF's features is half the job; recognizing the **traps** is the other half. Most "EF is
slow / buggy / unmaintainable" stories trace back to a short list of anti-patterns. A senior
developer spots them in review and refactors away from them on sight.

> 💡 The meta-pattern behind most EF anti-patterns: **treating EF like an in-memory collection
> instead of a layer over SQL.** Once you remember there's a database and a change tracker on the
> other side, most of these disappear.

## 📐 The catalog

### 1. The captive DbContext
A singleton (cache, hosted service) holding a scoped `DbContext` — shared across requests and
threads, and `DbContext` isn't thread-safe.
- **Fix:** inject **`IDbContextFactory<T>`** and create a context per operation. See
  [Dependency Injection](../06-Production/01.Dependency-Injection.md).

### 2. N+1 queries
Loading a list, then triggering one query per item (lazy loading in a loop, or per-row
`Count`/`Load`).
- **Fix:** `Include`, projection, or `AsSplitQuery`. See
  [Loading Strategies](../02-Querying/03.Loading-Strategies.md).

### 3. Materialize-then-filter
`var all = await ctx.Blogs.ToListAsync(); var some = all.Where(...);` — the database returned
everything; you filtered in memory.
- **Fix:** put `Where`/`OrderBy`/`Skip`/`Take` **before** `ToListAsync`. See
  [Basic Queries](../02-Querying/01.Basic-Queries.md).

### 4. Tracking read-only queries
Tracking entities you'll never save — wasted snapshots and CPU.
- **Fix:** `AsNoTracking()` (or `QueryTrackingBehavior.NoTracking` by default) on read paths. See
  [No-Tracking](../02-Querying/08.No-Tracking-and-Identity-Resolution.md).

### 5. `SaveChanges` in a loop
One round-trip per entity.
- **Fix:** `AddRange` + one save, or `ExecuteUpdate`/`ExecuteDelete` for set-based changes. See
  [Bulk Operations](../03-Saving-and-Concurrency/05.Bulk-Operations.md).

### 6. The generic Repository<T> over EF
Wrapping `DbSet<T>` in `IRepository<T>` with `GetAll`/`Add`/`Find` — usually **redundant**: EF's
`DbContext` *is* a unit of work and `DbSet<T>` *is* a repository. The wrapper hides `IQueryable`
power (no projection, no `Include`, no `AsNoTracking`) and adds a leaky abstraction.
- **Fix:** inject the `DbContext` (or thin, **use-case-specific** query services) directly. Add a
  repository only when you genuinely need to swap the data store or isolate the domain for testing.

### 7. Returning entities from APIs
Serializing entities straight to clients — leaks columns (`PasswordHash`), causes lazy-loading
serialization loops, and over-fetches.
- **Fix:** project to **DTOs**. Security + performance. See
  [Security Best Practices](../06-Production/05.Security-Best-Practices.md).

### 8. `AutoDetectChangesEnabled = false` left off forever
A bulk-insert optimization that, if not restored, makes the rest of your code stop detecting
changes.
- **Fix:** wrap in `try/finally` and restore. See [Change Tracking](../03-Saving-and-Concurrency/01.Change-Tracking.md).

### 9. `EnableSensitiveDataLogging` in production
Parameter values (PII) written to logs — a data breach.
- **Fix:** gate behind `env.IsDevelopment()`. See [Logging & Diagnostics](../06-Production/03.Logging-and-Diagnostics.md).

### 10. String-concatenated raw SQL
`FromSqlRaw("... '" + input + "'")` — SQL injection.
- **Fix:** interpolated `FromSql`/`SqlQuery` (auto-parameterized) or explicit parameters. See
  [Raw SQL Queries](../02-Querying/05.Raw-SQL-Queries.md).

### 11. Migrate-on-startup in multi-instance prod
Replicas race to migrate; no review, no rollback.
- **Fix:** idempotent scripts / bundles applied as a gated deploy step. See
  [Migrations in Production](../04-Migrations-and-Schema/02.Migrations-in-Production.md).

### 12. Async-over-sync (and sync-over-async)
Calling `.Result`/`.Wait()` on async EF (deadlocks/thread starvation), or using sync EF in a web
request (blocks a thread per request).
- **Fix:** use the **`*Async`** methods all the way down, with `CancellationToken`.

## ⚖️ The Repository debate (nuance)

The generic Repository is the most *contested* item here. It's not always wrong:
- ✅ Reasonable when you must **swap the persistence technology**, or want a hard **domain/infra
  boundary** for testing without EF.
- ❌ Usually wrong when it's a thin pass-through over `DbSet` that strips away `IQueryable`,
  projection, `Include`, and `AsNoTracking` — you've added indirection and lost capability.

Senior default: **inject the `DbContext` or focused query/command services**; reach for a
repository only with a concrete reason.

## 🚫 The smell test (review checklist)

```text
[ ] Any singleton holding a DbContext?                 → captive dependency
[ ] Repeated near-identical SELECTs in logs?           → N+1
[ ] .ToList() followed by .Where()/.OrderBy()?         → materialize-then-filter
[ ] Read path without AsNoTracking/projection?         → tracking waste
[ ] SaveChanges inside a loop?                          → batch it
[ ] Entities returned from a controller?               → project to DTOs
[ ] FromSqlRaw with + concatenation?                   → injection
[ ] EnableSensitiveDataLogging without env guard?      → PII leak
[ ] MigrateAsync() in Main on a scaled service?        → migration race
[ ] .Result / .Wait() on EF calls?                     → async-over-sync
```

## 🎯 Practice (with full solutions)

### 1. Refactor a generic repository back to EF — `Medium`
**Smelly code:**
```csharp
public interface IRepository<T> { Task<List<T>> GetAllAsync(); Task<T?> FindAsync(int id); }
public class Repository<T> : IRepository<T> where T : class {
    private readonly DbContext _ctx;
    public Task<List<T>> GetAllAsync() => _ctx.Set<T>().ToListAsync();   // can't project, include, or no-track
    public ValueTask<T?> FindAsync(int id) => _ctx.Set<T>().FindAsync(id);
}
```
**Task:** a controller needs blog summaries (Id + Title + post count) — impossible to do
efficiently through `GetAllAsync`.
**Solution:** inject the context (or a focused query service) and write the real query:
```csharp
public class BlogQueries {
    private readonly BloggingContext _ctx;
    public BlogQueries(BloggingContext ctx) => _ctx = ctx;
    public Task<List<BlogSummary>> SummariesAsync() =>
        _ctx.Blogs.AsNoTracking()
            .Select(b => new BlogSummary(b.Id, b.Title, b.Posts.Count()))
            .ToListAsync();
}
```
**Why it's better:** projection + no-tracking + post count in **one** SQL query — none of which the
generic repository allowed.

### 2. Kill a captive dependency + N+1 in one review — `Medium`
**Smelly code:**
```csharp
public class StatsCache {                          // registered AddSingleton
    private readonly BloggingContext _ctx;         // captive!
    public StatsCache(BloggingContext ctx) => _ctx = ctx;
    public async Task<Dictionary<int,int>> PostCountsAsync() {
        var blogs = await _ctx.Blogs.ToListAsync();
        return blogs.ToDictionary(b => b.Id, b => _ctx.Posts.Count(p => p.BlogId == b.Id)); // N+1
    }
}
```
**Solution:**
```csharp
public class StatsCache {
    private readonly IDbContextFactory<BloggingContext> _factory;   // no captive context
    public StatsCache(IDbContextFactory<BloggingContext> f) => _factory = f;
    public async Task<Dictionary<int,int>> PostCountsAsync() {
        await using var ctx = await _factory.CreateDbContextAsync();
        return await ctx.Blogs
            .Select(b => new { b.Id, Count = b.Posts.Count() })     // one query, no N+1
            .ToDictionaryAsync(x => x.Id, x => x.Count);
    }
}
```
**Why it's better:** fresh per-operation context (no thread-safety violation) **and** one
aggregate query instead of N+1.

## ✅ Key Takeaways

- The big anti-patterns: **captive DbContext, N+1, materialize-then-filter, tracking read-only
  data, SaveChanges-in-a-loop, generic Repository-over-EF, returning entities from APIs,
  AutoDetect left off, sensitive-data logging in prod, string-concatenated SQL, migrate-on-startup,
  async-over-sync.**
- The root cause is usually **treating EF like an in-memory collection** instead of a SQL layer.
- The **generic Repository** is the contested one — justify it, don't cargo-cult it.
- Keep the **smell-test checklist** handy in code review.
