# Integration Testing with Testcontainers

## 🧠 Intuition

Some things only behave correctly against your **actual** database engine: SQL-Server-specific SQL,
JSON columns (the `json` type), temporal tables, HierarchyId, vector search, and **migrations**
themselves. [SQLite in-memory](02.Unit-Testing-DbContext.md) is a different dialect and can't
validate these. **Testcontainers** spins up a **real SQL Server in a Docker container** for your
test run — disposable, isolated, and only a few seconds of overhead.

> 💡 **The promise:** test against the same engine you deploy to, with zero shared state, fully
> automated in CI. No "works on my machine" database surprises.

## 💻 Setup

```bash
dotnet add package Testcontainers.MsSql
dotnet add package Microsoft.EntityFrameworkCore.SqlServer
```

A fixture that starts the container once per test class:

```csharp
using Testcontainers.MsSql;
using Microsoft.EntityFrameworkCore;

public class SqlServerFixture : IAsyncLifetime {
    public MsSqlContainer Container { get; } = new MsSqlBuilder()
        .WithImage("mcr.microsoft.com/mssql/server:2022-latest")   // or 2025 for json/vector tests
        .Build();

    public DbContextOptions<BloggingContext> Options { get; private set; } = null!;

    public async Task InitializeAsync() {
        await Container.StartAsync();                              // pulls + boots SQL Server
        Options = new DbContextOptionsBuilder<BloggingContext>()
            .UseSqlServer(Container.GetConnectionString())
            .Options;
        await using var ctx = new BloggingContext(Options);
        await ctx.Database.MigrateAsync();                        // run REAL migrations
    }

    public async Task DisposeAsync() => await Container.DisposeAsync();
}
```

## 💻 The test class

```csharp
public class BlogIntegrationTests : IClassFixture<SqlServerFixture> {
    private readonly SqlServerFixture _fx;
    public BlogIntegrationTests(SqlServerFixture fx) => _fx = fx;

    [Fact]
    public async Task Json_details_round_trip_on_sql_server() {
        await using (var ctx = new BloggingContext(_fx.Options)) {
            ctx.Blogs.Add(new Blog { Title = "T", Details = new BlogDetails { Views = 5 } });
            await ctx.SaveChangesAsync();
        }
        await using (var ctx = new BloggingContext(_fx.Options)) {
            var blog = await ctx.Blogs.SingleAsync();
            Assert.Equal(5, blog.Details.Views);   // verified against the REAL json column behavior
        }
    }
}
```

This actually exercises the SQL Server JSON mapping, `JSON_VALUE`, and the migration — none of
which SQLite could validate.

## 💻 Testing migrations apply cleanly

```csharp
[Fact]
public async Task All_migrations_apply_without_error() {
    await using var ctx = new BloggingContext(_fx.Options);
    // MigrateAsync already ran in the fixture; assert there's nothing pending
    var pending = await ctx.Database.GetPendingMigrationsAsync();
    Assert.Empty(pending);
}
```

A migration that generates invalid SQL fails *here*, in CI, instead of during a production deploy.

## 💻 End-to-end API tests (WebApplicationFactory + Testcontainers)

```csharp
public class ApiTests : IClassFixture<SqlServerFixture> {
    private readonly SqlServerFixture _fx;
    public ApiTests(SqlServerFixture fx) => _fx = fx;

    [Fact]
    public async Task Post_then_get_blog() {
        await using var factory = new WebApplicationFactory<Program>()
            .WithWebHostBuilder(b => b.ConfigureServices(s => {
                // swap the app's DbContext to point at the container
                s.RemoveAll<DbContextOptions<BloggingContext>>();
                s.AddDbContext<BloggingContext>(o => o.UseSqlServer(_fx.Container.GetConnectionString()));
            }));
        var client = factory.CreateClient();

        var created = await client.PostAsJsonAsync("/blogs", new { Title = "Hi" });
        created.EnsureSuccessStatusCode();
        var list = await client.GetFromJsonAsync<List<BlogDto>>("/blogs");
        Assert.Contains(list!, b => b.Title == "Hi");
    }
}
```

Full stack — HTTP → controller → EF → **real SQL Server** — verified.

## ⚖️ Trade-offs

**Pros:** tests the **real engine** and **real migrations**; isolated and disposable; catches
provider-specific bugs SQLite can't; runs in CI.
**Cons:** needs **Docker**; slower than SQLite (seconds to start the container — amortized across a
class via `IClassFixture`); a bit more setup.

## 🚫 Common mistakes

```csharp
// ❌ Starting a container per TEST (slow) instead of per class/collection
// ✅ IClassFixture (per class) or ICollectionFixture (shared across classes)

// ❌ Using the 2022 image to test SQL Server 2025 features (json type, vector)
// ✅ pin the image that supports the feature you're testing

// ❌ Tests that depend on each other's data in a shared container
// ✅ isolate: unique data per test, or reset between tests (respawn / transaction rollback)
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 10** features — the **`json` data type**, **vector** columns, **`VECTOR_DISTANCE`** — only
  exist on **SQL Server 2025 / Azure SQL**. To test them, pin a **2025** container image.
- `Testcontainers.MsSql` tracks current SQL Server images; bump the tag when you adopt new
  server-side features.

## 🌍 Real-world production tips

- **`IClassFixture` / `ICollectionFixture`** to start the container once and share it — keeps the
  suite fast.
- Use a **database reset** strategy between tests (e.g. **Respawn** to truncate tables, or a
  transaction-per-test that rolls back) so tests stay independent.
- Run Testcontainers tests in **CI with Docker available**; keep them as a separate, slightly
  slower test project from the SQLite unit tests.
- Pin the **image tag** to the server version whose features you rely on (2022 vs 2025).

## 🎯 Practice (with full solutions)

### 1. Verify a SQL-Server-only feature — `Medium`
**Task:** Prove the EF 10 `json`-mapped `Details` column round-trips and is queryable.
**Solution:** the `Json_details_round_trip_on_sql_server` test above, using a **2025** image so the
native `json` type is exercised:
```csharp
new MsSqlBuilder().WithImage("mcr.microsoft.com/mssql/server:2025-latest").Build();
```
**Why it's better:** SQLite/InMemory can't model the SQL Server `json` type; this verifies the
real behavior in CI.

### 2. Guard your migrations — `Easy`
**Task:** Fail the build if any migration generates invalid SQL.
**Solution:** the fixture runs `MigrateAsync()` against a real SQL Server; the
`All_migrations_apply_without_error` test asserts none are pending. A broken migration throws
during `InitializeAsync`.
**Why it's better:** migration bugs surface in CI, not during a production deploy window.

## ✅ Key Takeaways

- **Testcontainers** runs a **real SQL Server** in Docker — the only honest way to test
  provider-specific features and migrations.
- Start the container **once per class/collection** (`IClassFixture`) to stay fast.
- **Pin the image** to the server version (2025 for `json`/vector); reset data between tests.
- Use it for the handful of things **SQLite can't model**; keep most tests on SQLite for speed.
