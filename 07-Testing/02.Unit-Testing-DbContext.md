# Unit Testing the DbContext (SQLite In-Memory)

## 🧠 Intuition

You want EF tests that are **fast** (milliseconds, no Docker) but **honest** (catch FK violations,
unique constraints, real query translation). The sweet spot is **SQLite in-memory** — a genuine
relational engine that lives entirely in RAM, spins up instantly, and enforces the SQL semantics
the InMemory provider fakes.

> 💡 **The one trick that trips everyone up:** SQLite's in-memory database exists only while a
> connection to it is **open**. Close the connection and the database vanishes. So you open one
> connection and keep it open for the whole test.

## 💻 The setup that works

```csharp
using Microsoft.Data.Sqlite;
using Microsoft.EntityFrameworkCore;

public class BloggingTests : IDisposable {
    private readonly SqliteConnection _connection;
    private readonly DbContextOptions<BloggingContext> _options;

    public BloggingTests() {
        // 1. Open a connection — the in-memory DB lives as long as THIS is open
        _connection = new SqliteConnection("Filename=:memory:");
        _connection.Open();

        // 2. Build options against that open connection
        _options = new DbContextOptionsBuilder<BloggingContext>()
            .UseSqlite(_connection)
            .Options;

        // 3. Create the schema once
        using var ctx = new BloggingContext(_options);
        ctx.Database.EnsureCreated();
    }

    private BloggingContext NewContext() => new(_options);   // fresh context, same DB

    public void Dispose() => _connection.Dispose();          // DB disappears here
}
```

> **Use a fresh `DbContext` per logical operation** (`NewContext()`), but the **same connection**,
> so each "act" sees a clean change tracker while sharing the one in-memory database.

## 💻 A real test

```csharp
[Fact]
public async Task GetActiveBlogs_excludes_soft_deleted() {
    // Arrange — seed with one context
    using (var ctx = NewContext()) {
        ctx.Blogs.AddRange(
            new Blog { Title = "Live" },
            new Blog { Title = "Gone", IsDeleted = true });
        await ctx.SaveChangesAsync();
    }

    // Act — query with a fresh context (no leftover tracking)
    using (var ctx = NewContext()) {
        var result = await ctx.Blogs.ToListAsync();   // global query filter hides IsDeleted

        // Assert
        Assert.Single(result);
        Assert.Equal("Live", result[0].Title);
    }
}
```

This actually exercises the global query filter, the schema, and the round-trip — things a mock or
InMemory provider would not faithfully test.

## 💻 Testing constraint enforcement (the payoff over InMemory)

```csharp
[Fact]
public async Task Duplicate_url_violates_unique_index() {
    using var ctx = NewContext();
    ctx.Blogs.Add(new Blog { Title = "A", Url = "same" });
    ctx.Blogs.Add(new Blog { Title = "B", Url = "same" });

    // SQLite ENFORCES the unique index — InMemory would not
    await Assert.ThrowsAsync<DbUpdateException>(() => ctx.SaveChangesAsync());
}
```

SQLite catches this; the InMemory provider would let both rows save and your real database would
blow up in production instead of in the test. That's the whole reason to use SQLite.

## ⚖️ SQLite in-memory vs InMemory provider

| | SQLite in-memory | InMemory provider |
|--|------------------|-------------------|
| Real relational engine? | ✅ | ❌ (a dictionary) |
| FK enforcement | ✅ | ❌ |
| Unique constraints | ✅ | ❌ (historically) |
| Transactions | ✅ | ❌ |
| Catches bad LINQ translation | Mostly | ❌ |
| Speed | Very fast | Fastest |
| Provider-specific SQL (SQL Server JSON/temporal/vector) | ❌ (different dialect) | ❌ |

> SQLite is a different dialect from SQL Server, so it **won't** validate SQL-Server-only features
> (the `json` type, temporal tables, HierarchyId, vector). Those need
> [Testcontainers](03.Integration-Testing-with-Testcontainers.md).

## 🚫 Common mistakes

```csharp
// ❌ Not keeping the connection open → the in-memory DB vanishes mid-test
var options = new DbContextOptionsBuilder<BloggingContext>()
    .UseSqlite("Filename=:memory:")   // each new connection = a DIFFERENT empty DB
    .Options;
// ✅ open ONE SqliteConnection and pass the connection object (as above)

// ❌ Reusing one DbContext for arrange + act + assert → stale change-tracker state
// ✅ a fresh context per phase, same connection

// ❌ Expecting SQLite to validate SQL-Server-specific features
// ✅ those go to Testcontainers
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- SQLite in-memory testing is stable across EF 8/9/10. EF 8+ `DateOnly`/`TimeOnly` and primitive
  collections map on SQLite too, so most modeling tests work there.
- **EF 10** SQL-Server-only features (vector, `json` type, named-filter SQL nuances) still require
  the real provider.

## 🌍 Real-world production tips

- Make a small **test base class** (or fixture) with the connection + options + `NewContext()` so
  every test file gets the setup for free.
- **Seed deterministically** and keep tests independent — each test should create the rows it needs.
- For test data builders, lean on object initializers; keep seeds readable.
- Reserve **Testcontainers** for the handful of provider-specific behaviors SQLite can't model.

## 🎯 Practice (with full solutions)

### 1. Build the fixture — `Easy`
**Task:** Create a reusable base that gives each test a fresh context over a shared in-memory DB.
**Solution:** the `BloggingTests` class above, extracted to a base/fixture:
```csharp
public abstract class SqliteTestBase : IDisposable {
    private readonly SqliteConnection _conn;
    protected DbContextOptions<BloggingContext> Options { get; }
    protected SqliteTestBase() {
        _conn = new SqliteConnection("Filename=:memory:"); _conn.Open();
        Options = new DbContextOptionsBuilder<BloggingContext>().UseSqlite(_conn).Options;
        using var ctx = new BloggingContext(Options); ctx.Database.EnsureCreated();
    }
    protected BloggingContext NewContext() => new(Options);
    public void Dispose() => _conn.Dispose();
}
```
**Why it's better:** every test inherits a correct, fast, real-engine setup with no boilerplate.

### 2. Catch a constraint bug in a test — `Medium`
**Task:** Prove that saving two blogs with the same unique `Url` fails.
**Solution:** the `Duplicate_url_violates_unique_index` test above.
**Why it's better:** the bug surfaces in CI against a real relational engine, not in production —
exactly what the InMemory provider would have hidden.

## ✅ Key Takeaways

- Use **SQLite in-memory** for fast, honest `DbContext` tests — it enforces real relational
  semantics.
- **Keep one `SqliteConnection` open** for the test's lifetime; use a **fresh `DbContext` per
  phase**.
- It catches FK/unique/transaction bugs the **InMemory provider** silently ignores.
- It can't validate **SQL-Server-specific** features — those go to Testcontainers.

**Self-check:**
1. Why must you keep the `SqliteConnection` open?
2. Why use a fresh `DbContext` per arrange/act/assert phase?
3. What can't SQLite in-memory test, and where do those tests go?
