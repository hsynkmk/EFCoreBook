# Temporal Tables

> SQL Server feature (also supported on Azure SQL); not available on PostgreSQL/SQLite/Cosmos.

## 🧠 Intuition

A **system-versioned temporal table** keeps a complete history of every change automatically.
Every update or delete moves the previous row into a hidden history table with the time it was
valid. You can query any point in the past — *"what did this order look like last Tuesday at
3 PM?"* — without writing any audit code.

> 💡 **Analogy — a self-updating photo album.** Every time the data changes, the database snaps a
> photo first and files it by timestamp. You can flip back to any moment.

## 🎯 The Problem

```csharp
// ❌ Before: hand-rolled audit table that drifts out of sync with schema, missed by raw SQL writers
public class BlogAudit { public int BlogId { get; set; } public string Title { get; set; } public DateTime ChangedAtUtc { get; set; } }
// Every UPDATE you write must also write to BlogAudit. Forget once → silent gap.
```

Compliance, debugging, and "when did this change?" investigations all want a reliable history.
Hand-built audit tables drift and break.

## 💻 Enabling temporal tables in EF

```csharp
modelBuilder.Entity<Blog>()
    .ToTable("Blogs", t => t.IsTemporal());
```

EF generates a migration that turns the table into a temporal table:

```sql
ALTER TABLE [Blogs] ADD
    [PeriodStart] datetime2 GENERATED ALWAYS AS ROW START HIDDEN
        CONSTRAINT [DF_Blogs_PeriodStart] DEFAULT (SYSUTCDATETIME()),
    [PeriodEnd]   datetime2 GENERATED ALWAYS AS ROW END   HIDDEN
        CONSTRAINT [DF_Blogs_PeriodEnd]   DEFAULT (CONVERT(datetime2, '9999-12-31 23:59:59.9999999')),
    PERIOD FOR SYSTEM_TIME ([PeriodStart], [PeriodEnd]);

ALTER TABLE [Blogs] SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = [dbo].[BlogsHistory]));
```

Now every `UPDATE` and `DELETE` against `Blogs` also writes a row to `BlogsHistory` with the
previous values and the time window during which they were current.

## 💻 Querying history

```csharp
// All historical versions of this blog
var allVersions = await ctx.Blogs
    .TemporalAll()
    .Where(b => b.Id == 42)
    .ToListAsync();

// As of a specific moment
var snapshot = await ctx.Blogs
    .TemporalAsOf(new DateTime(2026, 1, 15, 9, 0, 0))
    .ToListAsync();

// Changed between two timestamps
var changes = await ctx.Blogs
    .TemporalBetween(start, end)
    .Where(b => b.Id == 42)
    .ToListAsync();
```

The `Temporal*` methods are added by the SQL Server provider and translate to `FOR SYSTEM_TIME`
clauses in the SQL.

## ⚡ Generated SQL

```csharp
ctx.Blogs.TemporalAsOf(when).ToListAsync()
```
emits:
```sql
SELECT * FROM [Blogs] FOR SYSTEM_TIME AS OF @when;
```

## ⚖️ Trade-offs

**Pros:** complete history with zero application code; survives raw SQL writers; queryable from
LINQ; compliance- and audit-friendly.
**Cons:** storage cost grows with change volume; schema changes need care (the history table must
keep up); SQL Server / Azure SQL only — not portable.

## 🚫 Common mistakes

```csharp
// ❌ Temporal-izing huge, frequently-updated tables without retention — disk explodes
// ✅ Configure a HISTORY_RETENTION_PERIOD (SQL Server feature) or use SYSTEM_VERSIONING with a custom history table you prune

// ❌ Storing PII in a temporal table without a deletion plan
// ✅ Either don't temporal-ize PII tables, or build a redaction job; GDPR right-to-erasure is harder with temporal history

// ❌ Expecting a portable migration — temporal SQL is SQL Server specific
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- EF 6+ has had `IsTemporal()` and `Temporal*` query operators. Behavior is stable across EF 8 / 9
  / 10; nothing dramatically new here.

## 🌍 Real-world production tips

- Set a **retention period** on the history table to bound storage:
  `SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = [...], HISTORY_RETENTION_PERIOD = 7 YEAR))`.
- For **PII**, prefer event-sourcing or app-level audit you can redact, rather than temporal
  tables you can't easily forget.
- For **compliance trails**, temporal is the easiest reliable answer: untouched by application
  code, hard to forget.

## 🎯 Practice (with full solutions)

### 1. Add history to an existing table — `Easy`
**Task:** Turn `Blog` into a temporal table.
**Solution:**
```csharp
modelBuilder.Entity<Blog>().ToTable("Blogs", t => t.IsTemporal());
// dotnet ef migrations add MakeBlogsTemporal
// dotnet ef database update
```
**Why it's better:** every future change to `Blog` is recorded — for free. Audit code can be
deleted.

### 2. "What did this look like last week?" — `Medium`
**Task:** Implement an endpoint that returns the state of `Blog` 42 as of seven days ago.
**Solution:**
```csharp
public async Task<Blog?> GetSnapshotAsync(int id, BloggingContext ctx) {
    var when = DateTime.UtcNow.AddDays(-7);
    return await ctx.Blogs.TemporalAsOf(when).FirstOrDefaultAsync(b => b.Id == id);
}
```
**Why it's better:** uses the database's built-in time-travel; no per-entity audit code; works
with the regular EF model.

## ✅ Key Takeaways

- **Temporal tables** give you automatic, complete history of every row.
- Enable with **`ToTable("Name", t => t.IsTemporal())`**.
- Query with **`TemporalAll`**, **`TemporalAsOf`**, **`TemporalBetween`**.
- SQL Server / Azure SQL only — not portable.
- Mind **storage cost** and **PII retention** rules.
