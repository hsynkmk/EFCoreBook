# HierarchyId & Tree Data

> SQL Server / Azure SQL only. Requires `Microsoft.EntityFrameworkCore.SqlServer.HierarchyId`
> (EF 8+).

## 🧠 Intuition

Hierarchical data (org charts, file systems, comment threads, BOM trees) is hard to model
elegantly with plain relational columns. You either pay for **recursive CTEs** every query
(*adjacency list*) or maintain a denormalized **materialized path** by hand. SQL Server's
**`hierarchyid`** is a built-in column type designed for trees: comparisons, ancestors,
descendants, depth — all native.

> 💡 Think of `hierarchyid` as a magic string like `/2/3/1/` (with proper ordering and pack
> efficiency). The database knows how to compare them, find ancestors, and so on.

## 💻 Setup

Install the package:
```bash
dotnet add package Microsoft.EntityFrameworkCore.SqlServer.HierarchyId --version 10.0.*
```

Enable on the context:
```csharp
opt.UseSqlServer(connectionString, sql => sql.UseHierarchyId());
```

Model:
```csharp
using Microsoft.EntityFrameworkCore;
public class Employee {
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public HierarchyId Path { get; set; } = HierarchyId.GetRoot();   // /
}
```

## 💻 Querying with HierarchyId

```csharp
// Direct ancestors of an employee
var ancestors = await ctx.Employees
    .Where(e => e.Path.IsDescendantOf(target.Path) && e.Path != target.Path)
    .ToListAsync();

// All descendants of a manager
var subtree = await ctx.Employees
    .Where(e => e.Path.IsDescendantOf(manager.Path))
    .ToListAsync();

// Direct reports (one level down)
var directReports = await ctx.Employees
    .Where(e => e.Path.GetLevel() == manager.Path.GetLevel() + 1
             && e.Path.IsDescendantOf(manager.Path))
    .ToListAsync();
```

**⚡ Generated SQL** uses native `hierarchyid` operators:
```sql
SELECT * FROM [Employees]
WHERE [Path].IsDescendantOf(@managerPath) = 1
  AND [Path] <> @managerPath
```

## 💻 Inserting children

```csharp
var newChildPath = manager.Path.GetDescendant(null, null);   // first child
ctx.Employees.Add(new Employee { Name = "Ana", Path = newChildPath });
```

`GetDescendant(left, right)` produces a new path that sits *between* its arguments — `null/null`
appends a first child; `lastChild/null` appends after the last existing child; `prev/next` slots
between them.

## ⚖️ Trade-offs

**Pros:** native operations are fast and index-friendly; no recursive CTEs in hot paths; depth and
descendant queries are one liner.
**Cons:** SQL Server only; reorganizing a tree means rewriting paths in every moved subtree
(SQL Server has `Reparent` to help); index strategy matters.

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** introduced first-class **HierarchyId** support via the dedicated package.
- **EF 9:** extended to **Azure SQL**, plus translation improvements.
- **EF 10:** stable; no major hierarchy-specific changes — the EF 10 LINQ improvements (Param
  collections, etc.) still apply.

## 🌍 Real-world production tips

- **Index** the `Path` column with a regular index for ancestor/descendant predicates; the
  built-in operators use it.
- Don't over-use HierarchyId — it's optimized for **read-heavy** trees that don't reshuffle
  constantly. For trees that reshape a lot, an adjacency list + materialized path may be simpler.
- Postgres users: equivalent functionality with the `ltree` extension. EF + Npgsql don't have
  first-class support; you'd map it via a value converter.

## 🎯 Practice (with full solutions)

### 1. Org chart with descendants — `Medium`
**Task:** Given an employee, return every report (direct and indirect).
**Solution:**
```csharp
public async Task<List<Employee>> GetAllReportsAsync(int managerId, DbContext ctx) {
    var mgr = await ctx.Set<Employee>().SingleAsync(e => e.Id == managerId);
    return await ctx.Set<Employee>()
        .Where(e => e.Path.IsDescendantOf(mgr.Path) && e.Id != mgr.Id)
        .ToListAsync();
}
```
**Why it's better:** one query, no recursion, fast on indexed `Path`.

### 2. Get path as string for display — `Easy`
**Task:** Format an employee's path as `Root / VP / Director / Lead`.
**Solution:** join up to ancestors with one query, then format:
```csharp
var ancestors = await ctx.Employees
    .Where(e => target.Path.IsDescendantOf(e.Path))
    .OrderBy(e => e.Path.GetLevel())
    .Select(e => e.Name)
    .ToListAsync();
var breadcrumb = string.Join(" / ", ancestors);
```
**Why it's better:** no per-node round-trips; relies on the native operator the DB already uses
for the path semantics.

## ✅ Key Takeaways

- `hierarchyid` (SQL Server) gives **native tree operations** that beat recursive CTEs.
- Install **`Microsoft.EntityFrameworkCore.SqlServer.HierarchyId`** and call
  `UseHierarchyId()` on the provider.
- Use `IsDescendantOf`, `GetLevel`, `GetDescendant` for the common queries.
- Best for **read-heavy** trees; reshuffles can be expensive.
- Not available on PostgreSQL/SQLite/Cosmos — use `ltree` (Postgres) or materialized paths.
