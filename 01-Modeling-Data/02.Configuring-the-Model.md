# Configuring the Model: Conventions, Annotations, Fluent API

## 🧠 Intuition

EF Core builds a model from three sources, in order: **conventions** (defaults inferred from your
classes), **data annotations** (attributes on the entities), and **the Fluent API** (configuration
in C# code, in `OnModelCreating`). The later sources override the earlier ones. For anything past a
toy app, the Fluent API — organized into per-entity **`IEntityTypeConfiguration<T>`** classes — is
the senior default.

> 💡 **Annotations** are quick (`[Required]`, `[MaxLength(200)]`). **Fluent API** is powerful
> (composite keys, complex relationships, value conversions, indexes, JSON columns, owned types).
> Mixing is fine; defaulting to Fluent is cleaner.

## 🎯 The Problem

```csharp
// ❌ Before: 50 entities, all configured inside one giant OnModelCreating
protected override void OnModelCreating(ModelBuilder b) {
    b.Entity<Blog>().Property(x => x.Title).IsRequired().HasMaxLength(200);
    b.Entity<Blog>().HasIndex(x => x.Title);
    b.Entity<Post>().Property(x => x.Heading).IsRequired().HasMaxLength(500);
    // ... 1500 more lines
}
```

Predictably unmaintainable, hard to test, easy to merge-conflict. The fix: per-entity
configuration classes the model loads automatically.

## 📐 The three configuration sources

| Source | Looks like | Lives in | Use when |
|--------|-----------|----------|----------|
| **Conventions** | Inferred from class shape | EF Core itself | Defaults that are good enough |
| **Data annotations** | `[Required]`, `[MaxLength]`, `[Index]`, `[Table]` | On the entity class | Quick, simple constraints; you want the constraint visible next to the property |
| **Fluent API** | `entity.Property(x => x.Title).IsRequired()...` | `OnModelCreating` or `IEntityTypeConfiguration<T>` | Anything non-trivial; the senior default |

The later source wins, so you can use annotations for defaults and override with Fluent.

## 💻 Three equivalent ways to configure a column

```csharp
// (1) Conventions only — string property is mapped, nvarchar(max), nullable per nullable annotation
public string Title { get; set; } = "";

// (2) Data annotations
[Required, MaxLength(200), Column(TypeName = "nvarchar(200)")]
public string Title { get; set; } = "";

// (3) Fluent API in OnModelCreating
modelBuilder.Entity<Blog>()
    .Property(b => b.Title)
    .IsRequired()
    .HasMaxLength(200);
```

All three produce the same schema. Pick the one that scales with your codebase — Fluent API in
configuration classes scales best.

## 💻 The senior default: `IEntityTypeConfiguration<T>` classes

One file per entity, applied automatically:

```csharp
// Configurations/BlogConfiguration.cs
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

public class BlogConfiguration : IEntityTypeConfiguration<Blog> {
    public void Configure(EntityTypeBuilder<Blog> b) {
        b.ToTable("Blogs");
        b.HasKey(x => x.Id);
        b.Property(x => x.Title).IsRequired().HasMaxLength(200);
        b.Property(x => x.Views).HasDefaultValue(0);
        b.HasIndex(x => x.Title).IsUnique();

        b.HasMany(x => x.Posts)
         .WithOne(p => p.Blog)
         .HasForeignKey(p => p.BlogId)
         .OnDelete(DeleteBehavior.Cascade);
    }
}
```

```csharp
// BloggingContext.cs
protected override void OnModelCreating(ModelBuilder modelBuilder) {
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(BloggingContext).Assembly);
}
```

`ApplyConfigurationsFromAssembly` scans the assembly for `IEntityTypeConfiguration<T>` types and
runs them. `OnModelCreating` stays a one-liner regardless of model size.

## ⚖️ Annotations vs Fluent — what each is good at

| | Annotations | Fluent API |
|--|-------------|------------|
| Required / max length / column type | ✅ | ✅ |
| Default values | ⚠️ Limited | ✅ Full (incl. SQL expressions) |
| Indexes | ✅ `[Index]` (basic) | ✅ Full (filtered, composite, included columns) |
| Composite keys | ❌ | ✅ |
| Relationships | ⚠️ Some | ✅ Everything |
| Value conversions | ❌ | ✅ |
| Owned / complex types | ❌ | ✅ |
| JSON columns | ❌ | ✅ |
| Discriminators / inheritance | ❌ | ✅ |
| Splits into per-entity files | ❌ | ✅ |

**Rule of thumb:** annotations for simple constraints close to the property; Fluent for everything
else. Don't fight the API — if a feature only exists in Fluent, just use Fluent.

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** introduced the **`ComplexProperty`** API on `EntityTypeBuilder` — used for value-object
  mapping. See [Owned Entities & Complex Types](04.Owned-Entities-and-Complex-Types.md).
- **EF 9:** improvements to convention-based read-only primitive collections (no Fluent needed for
  basic cases).
- **EF 10:** **named query filters** (`HasQueryFilter("name", ...)`) are configured via Fluent only;
  complex types can be marked optional or mapped `.ToJson()`.

## 🌍 Real-world production tips

- **One file per entity** under a `Configurations/` folder. Code reviews love it.
- Keep `OnModelCreating` to **just** `ApplyConfigurationsFromAssembly(...)` plus truly model-wide
  things (default schema, conventions).
- **Conventions:** for repeated rules ("all decimal properties are (18,2)"), use
  `ConfigureConventions` (EF 6+) or post-process the model — far cleaner than repeating it in every
  configuration.

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder cfg) {
    cfg.Properties<decimal>().HavePrecision(18, 2);   // applies to every decimal everywhere
}
```

## 🎯 Practice (with full solutions)

### 1. Refactor a monster `OnModelCreating` — `Easy`
**Task:** Take the `OnModelCreating` from the Problem and split each entity's config into its own
file.
**Solution:** for each entity, create a `BlogConfiguration : IEntityTypeConfiguration<Blog>` with
a `Configure(EntityTypeBuilder<Blog>)` method, then collapse `OnModelCreating` to
`modelBuilder.ApplyConfigurationsFromAssembly(typeof(BloggingContext).Assembly);`.
**Why it's better:** clean files, fewer merge conflicts, easy to find "where is `Blog.Title`
configured?".

### 2. Use a model-wide convention — `Medium`
**Scenario:** Every `decimal` in your model should be `decimal(18, 2)`. Configuring it on every
property is tedious.
**Solution:**
```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder cfg) {
    cfg.Properties<decimal>().HavePrecision(18, 2);
}
```
**Why it's better:** one rule, applied everywhere. Migrations stay consistent, future entities are
covered automatically.

### 3. Mix annotations and Fluent — `Easy`
**Task:** Use `[Required, MaxLength(200)]` on `Title`, then override `MaxLength` to 500 for one
entity via Fluent. What does EF produce?
**Solution:**
```csharp
public class Blog { [Required, MaxLength(200)] public string Title { get; set; } = ""; }
// In BlogConfiguration.Configure:
b.Property(x => x.Title).HasMaxLength(500);
```
Fluent **wins** (it's the last source), so the column is `nvarchar(500) NOT NULL`. The annotation
contributed the `NOT NULL`.
**Why it matters:** annotations and Fluent can coexist; just know which one wins (Fluent).

## ✅ Key Takeaways

- EF reads model config from **conventions → annotations → Fluent**; later wins.
- For real projects, use **Fluent API in per-entity `IEntityTypeConfiguration<T>` classes** and
  one-line `ApplyConfigurationsFromAssembly` in `OnModelCreating`.
- Use **annotations** only for trivial, near-the-property constraints.
- Use **`ConfigureConventions`** for repeated rules ("all decimals are (18,2)").
- Some features (composite keys, value conversions, owned/complex/JSON types, named filters) are
  **Fluent-only**.

**Self-check:**
1. If a property has both `[MaxLength(100)]` and Fluent `HasMaxLength(200)`, which wins?
2. Why split configuration into `IEntityTypeConfiguration<T>` classes instead of one big method?
3. What is `ConfigureConventions` for?
