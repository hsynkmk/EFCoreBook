# Global & Named Query Filters

> **Named query filters** are an **EF 10 headline feature** — multiple filters per entity, each
> disable-able by name.

## 🧠 Intuition

Many apps need a filter applied to **every** query of an entity — automatic soft delete (hide
`IsDeleted = true` rows), multi-tenancy (only show rows for the current tenant), per-environment
visibility flags. Global query filters let you declare these once, and EF appends them to every
LINQ query for that entity. **EF 10** adds *named* filters so you can configure several and
selectively disable some.

> 💡 **Analogy — a pair of sunglasses your queries can't take off.** Every query sees the filtered
> view by default. With named filters (EF 10+), you can flip up just the soft-delete lens or just
> the tenant lens for a specific query.

## 🎯 The Problem

```csharp
// ❌ Before: every query repeats the same filters; one forgotten Where leaks deleted rows
var posts = await ctx.Posts.Where(p => !p.IsDeleted && p.TenantId == currentTenant).ToListAsync();
// 50 query sites later, you'll miss one. Production leak.
```

## 💻 Global query filter (EF 2+ — still the workhorse)

```csharp
modelBuilder.Entity<Blog>()
    .HasQueryFilter(b => !b.IsDeleted && b.TenantId == _tenantProvider.Current);
```

Every query against `ctx.Blogs` now silently appends `AND ([IsDeleted] = 0 AND [TenantId] = @p)`.
To bypass it deliberately:

```csharp
var includingDeleted = await ctx.Blogs.IgnoreQueryFilters().ToListAsync();
```

The classic problem: **one filter per entity**. If you want to *only* disable the soft-delete
check (an admin "show deleted" feature) while keeping the tenant filter, you can't — `IgnoreQuery­
Filters` drops them all.

## 💻 Named query filters (EF 10 — new) 🆕

```csharp
modelBuilder.Entity<Blog>()
    .HasQueryFilter("SoftDelete", b => !b.IsDeleted)
    .HasQueryFilter("Tenant",     b => b.TenantId == _tenantProvider.Current);
```

Now you can disable filters **by name**:

```csharp
// Disable ONLY soft-delete; the tenant filter still applies
var includingDeleted = await ctx.Blogs
    .IgnoreQueryFilters(["SoftDelete"])
    .ToListAsync();

// Disable both (old behavior)
var everything = await ctx.Blogs.IgnoreQueryFilters().ToListAsync();
```

Multiple filters compose with `AND`. Naming makes intent explicit and prevents accidentally
disabling tenant scoping when you only meant to surface deleted rows.

## ⚡ Generated SQL

```csharp
ctx.Blogs.ToListAsync()
```
emits something like:
```sql
SELECT [b].[Id], [b].[Title], ...
FROM [Blogs] AS [b]
WHERE [b].[IsDeleted] = 0 AND [b].[TenantId] = @p_tenant
```

The filter is part of every query — including those generated by `Include`, projections, etc.

## ⚖️ Trade-offs

**Pros:** one safe default for every query; impossible to forget; pairs beautifully with
**filtered indexes** (only index `IsDeleted = 0` rows for huge perf wins on soft-delete-heavy
apps).
**Cons:** can hide rows even when you want to see them (debugging trap — use `IgnoreQueryFilters`);
joins to filtered entities may behave subtly with `Include`; capturing tenant state requires care
(don't close over a singleton `_tenantProvider` from a non-scoped context).

## 🚫 Common mistakes

```csharp
// ❌ Closing over a request-scoped tenant in a singleton DbContext setup
modelBuilder.Entity<Blog>().HasQueryFilter(b => b.TenantId == _tenantProvider.Current);
// works in scoped contexts; if you ever pool/cache the model, this captures incorrectly
// ✅ pass tenant through DI to the DbContext constructor and reference it from there

// ❌ Trying to disable just one filter on EF 8/9 (you can't — only IgnoreQueryFilters wholesale)
// ✅ EF 10 named filters

// ❌ Forgetting that Include also applies filters
ctx.Authors.Include(a => a.Blogs).ToListAsync();
// Blogs collection respects the Blog filter — only non-deleted blogs are loaded
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8 / 9:** one filter per entity, all-or-nothing with `IgnoreQueryFilters()`.
- **EF 10:** **named query filters** — multiple per entity, individually disable-able via
  `IgnoreQueryFilters(["FilterName"])`. *This is the big quality-of-life win for multi-tenant
  apps.*

## 🌍 Real-world production tips

- For **soft delete**, pair a query filter with a **filtered index** on `IsDeleted = 0`. The
  index is tiny, the filter is enforced, you can't forget either.
- For **multi-tenancy**, inject the tenant provider into the `DbContext` and **don't reuse a
  context across tenants** — the filter captures the tenant at model build time (or per-instance
  with EF's parameterization, depending on how you write it).
- Always provide an **admin** code path that uses `IgnoreQueryFilters` (or
  `IgnoreQueryFilters(["SoftDelete"])` in EF 10) — support staff need to see deleted/foreign data.
- Document the filters on each entity — a reader of `ctx.Blogs.ToListAsync()` shouldn't be
  surprised by what comes back.

## 🎯 Practice (with full solutions)

### 1. Soft delete with a filtered index — `Medium`
**Task:** Soft-delete `Blog`s by `IsDeleted` flag. All queries should hide deleted rows by default.
Reads should be index-efficient.
**Solution:**
```csharp
public class Blog { public int Id { get; set; } public string Title { get; set; } = ""; public bool IsDeleted { get; set; } }

modelBuilder.Entity<Blog>().HasQueryFilter(b => !b.IsDeleted);
modelBuilder.Entity<Blog>()
    .HasIndex(b => b.Title)
    .HasFilter("[IsDeleted] = 0");   // index only the live rows
```
**Why it's better:** every query auto-filters; the index is small and only covers visible data.
Soft-delete an entity via `blog.IsDeleted = true; await ctx.SaveChangesAsync();` — no need for a
real DELETE.

### 2. Show deleted rows for an admin endpoint — `Easy` (EF 10)
**Task:** Surface deleted blogs **but keep the tenant filter applied**.
**Solution (EF 10 named filters):**
```csharp
modelBuilder.Entity<Blog>()
    .HasQueryFilter("SoftDelete", b => !b.IsDeleted)
    .HasQueryFilter("Tenant", b => b.TenantId == _tenant.Current);

// admin endpoint:
var deletedForTenant = await ctx.Blogs.IgnoreQueryFilters(["SoftDelete"]).ToListAsync();
```
**Why it's better:** in EF 8/9 you'd have to disable *all* filters and re-implement the tenant
check by hand (and probably forget once). Named filters keep the safety rail.

## ✅ Key Takeaways

- **Global query filters** apply a predicate to every query of an entity — one place to enforce
  soft delete, multi-tenancy, etc.
- **EF 10 named filters** allow **multiple per entity** and **selective bypass** —
  `IgnoreQueryFilters(["Name"])`.
- Pair filters with **filtered indexes** for big performance wins.
- Always provide an admin path that bypasses the right filter only.
