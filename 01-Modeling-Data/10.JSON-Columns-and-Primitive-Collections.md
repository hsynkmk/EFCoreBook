# JSON Columns & Primitive Collections

> EF 8 introduced both. EF 9 added read-only primitive collections. EF 10 adds **SQL Server 2025's
> native `json` data type** and **complex types as JSON**.

## 🧠 Intuition

Traditional relational modeling shreds every property into a column. That's overkill for two
common shapes:

- **Document-like nested data** — an `Order` has shipping info, line items as a list, and a
  flexible `Metadata` bag. JSON columns model this directly.
- **Lists of primitives** — a `Blog` has a `string[] Tags`. Modeling a separate table feels heavy
  for what's logically "a few strings."

Modern EF gives you both: **JSON columns** for nested documents inside relational tables, and
**primitive collections** for "an array of strings/ints/etc." as a single column you can still
query with LINQ.

## 🎯 The Problem

```csharp
// ❌ Before EF 8: a string[] forces an ugly separate table or a CSV column
public class Blog {
    public int Id { get; set; }
    public string TagsCsv { get; set; } = "";   // "ef,csharp,dotnet"
    // every search becomes LIKE '%ef%' — no indexes, no parameter safety, no LINQ
}
```

Or you build a `BlogTag` join table for what's logically just a few words per blog. Heavy.

## 💻 Primitive Collections (EF 8+) — value-type arrays as one column

```csharp
public class Blog {
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public List<string> Tags { get; set; } = new();        // EF 8: maps to a single JSON column
}
```

EF stores `Tags` as a JSON array in a single column. You can query it with LINQ:

```csharp
var efBlogs = await ctx.Blogs
    .Where(b => b.Tags.Contains("ef"))
    .ToListAsync();
```

**⚡ Generated SQL (SQL Server):**
```sql
SELECT [b].[Id], [b].[Title], [b].[Tags]
FROM [Blogs] AS [b]
WHERE EXISTS (SELECT 1 FROM OPENJSON([b].[Tags]) WITH ([value] nvarchar(max) '$') AS [t] WHERE [t].[value] = N'ef')
```

EF uses `OPENJSON` (SQL Server) or `jsonb_array_elements` (Postgres) to query into the array.
**Indexable** via a computed column on the JSON path if you need it hot.

### EF 9: read-only collections

```csharp
public class DogWalk {
    public int Id { get; set; }
    public ReadOnlyCollection<DateOnly> DaysVisited { get; set; } = null!;   // EF 9+
}
```

EF 9 extended primitive collections to `IReadOnlyList<T>`, `IReadOnlyCollection<T>`, and
`ReadOnlyCollection<T>`. Pairs nicely with DDD-style immutable entities.

## 💻 JSON Columns (EF 8+) — nested documents

```csharp
public class Order {
    public int Id { get; set; }
    public ShippingInfo Shipping { get; set; } = new();   // nested document
    public List<OrderLine> Lines { get; set; } = new();   // nested array
}
public class ShippingInfo { public string Street { get; set; } = ""; public string City { get; set; } = ""; }
public class OrderLine { public string Sku { get; set; } = ""; public int Quantity { get; set; } }

modelBuilder.Entity<Order>().OwnsOne(o => o.Shipping, b => b.ToJson());
modelBuilder.Entity<Order>().OwnsMany(o => o.Lines, b => b.ToJson());
```

EF stores `Shipping` and `Lines` as JSON columns. The full Order is one row.

```csharp
// LINQ into the JSON
var bigOrders = await ctx.Orders
    .Where(o => o.Lines.Any(l => l.Quantity > 10))
    .ToListAsync();
```

**⚡ Generated SQL:**
```sql
SELECT ... FROM [Orders] AS [o]
WHERE EXISTS (
  SELECT 1 FROM OPENJSON([o].[Lines]) WITH ([Quantity] int '$.Quantity') AS [l]
  WHERE [l].[Quantity] > 10)
```

### EF 10: complex types into JSON (the cleaner modeling story)

```csharp
modelBuilder.Entity<Customer>(c => {
    c.ComplexProperty(x => x.ShippingAddress, addr => addr.ToJson());   // EF 10
});
```

Complex types (no `OwnsOne` ceremony, no shadow FK) mapped to JSON — see
[Owned Entities & Complex Types](04.Owned-Entities-and-Complex-Types.md).

## 🆕 SQL Server 2025 `json` data type (EF 10)

Pre-2025, JSON in SQL Server was stored in `nvarchar(max)` columns. **SQL Server 2025 (and Azure
SQL)** introduces a native **`json`** type with better storage and indexing. EF 10 uses it
automatically when targeting SQL Server 2025 or via `UseAzureSql`:

```sql
CREATE TABLE [Customers] (
    [Id] int IDENTITY PRIMARY KEY,
    [Name] nvarchar(max) NOT NULL,
    [Tags] json NOT NULL,                -- native JSON type, not nvarchar(max)
    [ShippingAddress] json NOT NULL
);
```

And `ExecuteUpdate` of JSON-mapped properties translates to efficient `JSON_MODIFY`:

```csharp
await ctx.Blogs.ExecuteUpdateAsync(s =>
    s.SetProperty(b => b.Details.Views, b => b.Details.Views + 1));
```
emits:
```sql
UPDATE [b] SET [Details].modify('$.Views', JSON_VALUE([b].[Details], '$.Views' RETURNING int) + 1)
FROM [Blogs] AS [b]
```

> Existing apps using `nvarchar(max)` for JSON get **migrated to `json`** on the first migration
> after upgrade. Opt out by manually setting the column type if needed.

## ⚖️ Trade-offs

**Pros:** model documents naturally; one row per logical aggregate; fewer joins; flexible schemas;
EF 10 + SQL 2025 give native, indexed, efficient JSON.
**Cons:** JSON LINQ predicates are slower than column predicates on large tables without indexes
on JSON paths; some advanced queries don't translate; cross-row joins on JSON content are awkward.

## 🚫 Common mistakes

```csharp
// ❌ Throwing everything into JSON because it feels "modern"
// JSON for: nested arrays of value objects, flexible documents, "metadata" bags
// Normal columns for: queryable searchable fields, foreign keys, anything you'll JOIN on
// ✅ keep the searchable bits as columns, document the bits inside JSON

// ❌ Indexing JSON content by mistake — DB indexes the whole column, not just the path you care about
// ✅ create a computed column on the JSON path, then index THAT
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** primitive collections (mutable list/array); JSON columns via `OwnsOne(...).ToJson()`.
- **EF 9:** read-only primitive collections (`IReadOnlyList<T>`, etc.); `Parameter`/`Constant`
  control over parameterization of inline collections; significant Cosmos JSON improvements.
- **EF 10:** native SQL Server 2025 **`json`** type; **complex types mapped to JSON**;
  **`ExecuteUpdateAsync` of JSON-mapped properties** with efficient `JSON_MODIFY` SQL;
  parameterized-collection padding for better plan caching.

## 🌍 Real-world production tips

- Keep **search keys** out of JSON; keep **payload** inside. E.g. `OrderId`, `CustomerId`, `Status`
  as columns; `Lines`, `Metadata`, `ShippingInfo` as JSON.
- For SQL Server, **always test the execution plan** of JSON predicates on production-sized data.
  Computed-column-plus-index is the usual lever.
- For PostgreSQL, use `jsonb` (default for Npgsql), not `json` — `jsonb` is binary, indexable with
  `GIN`, and dramatically faster for queries.

## 🎯 Practice (with full solutions)

### 1. Replace a CSV with a primitive collection — `Easy`
**Task:** Migrate `Blog.TagsCsv` to a real `List<string> Tags`, queryable by LINQ.
**Solution:**
```csharp
public class Blog { public int Id { get; set; } public List<string> Tags { get; set; } = new(); }
// query
var efBlogs = await ctx.Blogs.Where(b => b.Tags.Contains("ef")).ToListAsync();
```
**Why it's better:** parameterized, indexable (via a computed column if hot), LINQ-friendly, no
string parsing.

### 2. Model an Order with nested lines as JSON — `Medium`
**Task:** Store the order's lines inside the order row, but support `WHERE any line quantity > 10`.
**Solution:**
```csharp
modelBuilder.Entity<Order>().OwnsMany(o => o.Lines, b => b.ToJson());
// query
var bigOrders = await ctx.Orders.Where(o => o.Lines.Any(l => l.Quantity > 10)).ToListAsync();
```
**Why it's better:** one row per order; no separate `OrderLines` table; predicates translate via
`OPENJSON`/`jsonb`; complex types in EF 10 make this even cleaner.

## ✅ Key Takeaways

- **Primitive collections** (EF 8+) store arrays of value types as one column, still queryable in
  LINQ.
- **JSON columns** (EF 8+) store nested documents/arrays as JSON; map them via
  `OwnsOne/OwnsMany(...).ToJson()` or **EF 10 complex types** with `.ToJson()`.
- **EF 10 + SQL 2025** gives you a **native `json` data type** with efficient `JSON_MODIFY`-based
  `ExecuteUpdate`.
- Keep search keys as columns, payload as JSON. Test execution plans.
