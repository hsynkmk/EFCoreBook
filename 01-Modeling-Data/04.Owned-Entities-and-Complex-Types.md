# Owned Entities & Complex Types

> **EF 8** introduced complex types; **EF 10** added optional and JSON-mapped complex types. This
> file covers both, and explains when to use owned entities vs complex types.

## 🧠 Intuition

Some things in your domain look like a *value*, not an entity — an `Address`, a `Money`, a
`GeoPoint`. They don't have an identity of their own (no `Id`); they belong inside another entity.
EF Core gives you two ways to model these:

- **Owned entities** (since EF Core 2): still EF entities under the hood; tracked by a hidden FK
  back to the owner. Useful, but came with quirks (can't be `null` cleanly, tricky queries).
- **Complex types** (EF 8+): proper value objects. No identity, no tracking — just composed of
  their properties. **EF 10** lets them be optional and mapped to JSON.

> 💡 If you find yourself writing `class Address { public int Id { get; set; } ... }` to satisfy
> EF, you don't have an entity — you have a value object. Reach for a complex type.

## 🎯 The Problem

```csharp
// ❌ Before: flat columns dumped on Customer
public class Customer {
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public string ShippingStreet { get; set; } = "";
    public string ShippingCity { get; set; } = "";
    public string ShippingPostalCode { get; set; } = "";
    public string BillingStreet { get; set; } = "";
    public string BillingCity { get; set; } = "";
    public string BillingPostalCode { get; set; } = "";
}
```

Twelve address-related properties, two address concepts. Logic that operates on an address ("is
this address complete?") has nothing to bind to. The domain is screaming "I have an `Address`
value object."

## 💻 Complex Types (EF 8+ — the modern choice)

```csharp
public class Address {                       // a value object — no Id
    public string Street { get; set; } = "";
    public string City { get; set; } = "";
    public string PostalCode { get; set; } = "";
}

public class Customer {
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public Address ShippingAddress { get; set; } = new();
    public Address? BillingAddress { get; set; }   // optional (requires EF 10+)
}

// Fluent
modelBuilder.Entity<Customer>(c => {
    c.ComplexProperty(x => x.ShippingAddress);
    c.ComplexProperty(x => x.BillingAddress);     // EF 10: optional supported (need at least one required member)
});
```

**Mapping (default: table splitting):** the address columns live in the `Customers` table:

```sql
CREATE TABLE [Customers] (
    [Id] int IDENTITY PRIMARY KEY,
    [Name] nvarchar(max) NOT NULL,
    [ShippingAddress_Street] nvarchar(max) NOT NULL,
    [ShippingAddress_City] nvarchar(max) NOT NULL,
    [ShippingAddress_PostalCode] nvarchar(max) NOT NULL,
    [BillingAddress_Street] nvarchar(max) NULL,
    [BillingAddress_City] nvarchar(max) NULL,
    [BillingAddress_PostalCode] nvarchar(max) NULL
);
```

You can also map a complex type to **JSON** (EF 10+):

```csharp
modelBuilder.Entity<Customer>(c => {
    c.ComplexProperty(x => x.ShippingAddress, addr => addr.ToJson());
    c.ComplexProperty(x => x.BillingAddress, addr => addr.ToJson());
});
```

Schema becomes:

```sql
CREATE TABLE [Customers] (
    [Id] int IDENTITY PRIMARY KEY,
    [Name] nvarchar(max) NOT NULL,
    [ShippingAddress] json NOT NULL,       -- EF 10 uses the new json type on SQL 2025 / Azure SQL
    [BillingAddress] json NULL
);
```

`ExecuteUpdate` against complex JSON columns is supported in EF 10:
```csharp
await ctx.Customers.ExecuteUpdateAsync(s =>
    s.SetProperty(c => c.ShippingAddress.City, "Berlin"));
```

## 💻 Owned Entities (the older approach — still useful)

```csharp
public class Address { public string Street { get; set; } = ""; public string City { get; set; } = ""; }

public class Order {
    public int Id { get; set; }
    public Address ShippingAddress { get; set; } = new();
}
modelBuilder.Entity<Order>()
    .OwnsOne(o => o.ShippingAddress);

// or with collection:
modelBuilder.Entity<Order>()
    .OwnsMany(o => o.Tags, b => b.ToTable("OrderTags"));
```

Owned entities are EF entities behind the scenes; they participate in change tracking and can have
their own queries. Use them when you need that richness (e.g. collections of value objects, deep
nesting, or JSON arrays).

## ⚖️ Owned vs Complex — when to pick which

| | **Complex types (EF 8+)** | **Owned entities** |
|--|---------------------------|---------------------|
| Identity | None | Hidden FK to owner |
| Tracking | Not tracked separately | Tracked as a related entity |
| Collections | EF 10: collections supported as complex types | Use `OwnsMany` |
| JSON mapping | Yes (EF 10) | Yes (EF 8) |
| Querying as a key | EF 9: `GroupBy` over complex type supported | Limited |
| Best for | True value objects (Address, Money, GeoPoint) | More entity-like nested things; collections (older EF) |

**Senior rule of thumb:** start with **complex types** for value objects on EF 8+. Use owned
entities only when you specifically need their entity-flavored behavior.

## 🚫 Common mistakes

```csharp
// ❌ Making a value object an entity just to please EF
public class Address {
    public int Id { get; set; }   // there's no real identity here
    ...
}
// ✅ Model as a complex type or owned type instead

// ❌ Sharing one Address instance across two Customers
var addr = new Address { Street = "Main St", City = "NYC" };
ctx.Customers.Add(new Customer { ShippingAddress = addr });
ctx.Customers.Add(new Customer { ShippingAddress = addr });   // both reference the SAME instance
// ✅ value-object semantics: clone or use a record so each customer has its own copy

// ❌ Assuming BillingAddress can be null on EF 8 complex types — it couldn't reliably
// ✅ EF 10 supports optional complex types (with at least one required member)
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** **complex types** introduced; mapped via table splitting (columns in the owner table).
- **EF 9:** complex types support **`GroupBy`** and **`ExecuteUpdate` per member**.
- **EF 10:**
  - **Optional complex types** (`Address?`) supported.
  - **Complex types mapped to JSON** with `.ToJson()`.
  - **`ExecuteUpdate` of complex JSON** (e.g. `s.SetProperty(c => c.Details.Views, ...)`)
    translates to efficient `JSON_VALUE`/`JSON_MODIFY` SQL.
  - **Complex type collections** supported (one of the bigger EF 10 modeling wins).

## 🌍 Real-world production tips

- Make value objects **immutable** — `record` types fit perfectly, and the EF 10 collection support
  pairs nicely with them.
- Don't share complex-type instances across entities (no identity = no surprises if you don't).
- For **multi-tenant addresses** that grow into "billing entities" with their own lifecycle, *do*
  promote them to a regular entity. Value objects are for things truly without identity.

## 🎯 Practice (with full solutions)

### 1. Refactor flat columns into a complex type — `Easy`
**Task:** Refactor the `Customer` from the Problem into one with `ShippingAddress` and (optional)
`BillingAddress` of type `Address`.
**Solution:** the complex-type version above. Migration adds nothing (column names stay the
same — EF maps `Address.Street` to `ShippingAddress_Street`).
**Why it's better:** address logic lives in one place; multi-tenant rules ("billing must equal
shipping for some tenants") become a method on `Address`.

### 2. Move to JSON — `Medium`
**Scenario:** Your reports rarely need address fields, but reads of `Customer` are a hot path.
Mapping address to a JSON column trims six columns down to one.
**Solution (EF 10):**
```csharp
modelBuilder.Entity<Customer>(c => {
    c.ComplexProperty(x => x.ShippingAddress, a => a.ToJson());
    c.ComplexProperty(x => x.BillingAddress, a => a.ToJson());
});
```
And to update a single nested property efficiently:
```csharp
await ctx.Customers
    .Where(c => c.Id == id)
    .ExecuteUpdateAsync(s => s.SetProperty(c => c.ShippingAddress.City, "Berlin"));
```
**Why it's better:** narrower row, faster reads when address fields aren't needed; updates on the
JSON path use `JSON_MODIFY` on SQL Server 2025 (one round-trip, no entity loaded).

## ✅ Key Takeaways

- Value objects (Address, Money, GeoPoint) → **complex types** (EF 8+).
- "Entity-flavored" nested things → **owned entities**.
- **EF 10** unlocks the modern shape: **optional** complex types, **JSON mapping**, and
  **`ExecuteUpdate` of JSON-mapped properties**.
- Don't give a value object an `Id` just to please EF.
- Prefer immutable `record` types for value objects.
