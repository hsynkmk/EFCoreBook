# Indexes & Constraints

## 🧠 Intuition

An index is a **lookup table** the database keeps to find rows fast without scanning. Constraints
(`UNIQUE`, `CHECK`, foreign keys) are **rules** the database enforces on your data. EF Core lets
you declare both in code — and they get migrated, versioned, and reviewed like the rest of your
schema. A query without an index is the #1 production performance trap; a missing constraint is
the #1 data-quality trap.

> 💡 **Analogy — a book.** A query without an index is reading every page to find a word; a query
> *with* a covering index is the back-of-book index — straight to the page.

## 💻 Declaring indexes

```csharp
modelBuilder.Entity<Blog>()
    .HasIndex(b => b.Url)
    .IsUnique();

// Composite index — column order matters!
modelBuilder.Entity<Post>()
    .HasIndex(p => new { p.BlogId, p.PublishedUtc });

// Named, with included columns and a filter (SQL Server)
modelBuilder.Entity<Order>()
    .HasIndex(o => o.CustomerId, "IX_Orders_OpenByCustomer")
    .IncludeProperties(o => new { o.Total, o.PlacedUtc })
    .HasFilter("[Status] = 'Open'");
```

**⚡ Generated SQL (SQL Server):**
```sql
CREATE UNIQUE INDEX [IX_Blogs_Url] ON [Blogs] ([Url]);
CREATE INDEX [IX_Posts_BlogId_PublishedUtc] ON [Posts] ([BlogId], [PublishedUtc]);
CREATE INDEX [IX_Orders_OpenByCustomer] ON [Orders] ([CustomerId]) INCLUDE ([Total], [PlacedUtc]) WHERE [Status] = 'Open';
```

### Composite index column order

`[BlogId, PublishedUtc]` accelerates queries with `WHERE BlogId = X` or `WHERE BlogId = X AND
PublishedUtc > Y`, but **not** `WHERE PublishedUtc > Y` alone. Order matters; pick it to match
your most common predicate, with the most selective column first.

### Filtered indexes

`HasFilter` builds a smaller index over only the rows that match the filter (e.g. open orders, not
all orders). Especially powerful for soft-delete and tenant scoping.

### Included columns (covering indexes)

`IncludeProperties` tells the index to **carry extra columns** so queries can be served entirely
from the index without going to the table. Great for read-heavy hot paths.

## 💻 Unique constraints (alternate keys)

```csharp
modelBuilder.Entity<User>()
    .HasAlternateKey(u => u.Email);          // becomes a UNIQUE constraint
```

The `HasIndex(...).IsUnique()` form is more common; alternate keys are useful when you need a
**referenceable** unique column (e.g. a FK can point to `Email` instead of `Id`).

## 💻 Check constraints

```csharp
modelBuilder.Entity<Order>()
    .ToTable("Orders", t => t.HasCheckConstraint("CK_Orders_Total_NonNegative", "[Total] >= 0"));
```

EF emits an `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)`. The database enforces the rule on
every insert/update.

## ⚖️ Trade-offs

**Pros:** indexes turn O(n) scans into O(log n) seeks; constraints catch bad data at write time.
**Cons:** indexes cost **space** and **write throughput** (every insert/update maintains every
index). Too many indexes can slow writes more than they speed reads.

## ✅ When to add an index / 🚫 when not to

- ✅ Foreign keys (EF adds these automatically by convention).
- ✅ Columns in `WHERE`, `JOIN ON`, and `ORDER BY` for hot queries.
- ✅ Unique business keys (email, slug, external IDs).
- 🚫 Tiny tables (the optimizer prefers a scan).
- 🚫 Wide columns or low-cardinality (boolean) — usually wasted.
- 🚫 "Just in case" — wait until a query needs it.

## 🚫 Common mistakes

```csharp
// ❌ Index on a value-converted column → the converter hides values from the index
b.Property(x => x.Tags).HasConversion(/* CSV */);
b.HasIndex(x => x.Tags);   // useless for "tag contains X"
// ✅ use primitive collections + native indexes (next file)

// ❌ Indexing every nullable foreign key with `IsUnique()` — breaks if more than one NULL
b.HasIndex(x => x.OptionalId).IsUnique();   // SQL Server allows multiple NULLs; PG doesn't
// ✅ filtered: .HasFilter("[OptionalId] IS NOT NULL")

// ❌ Skipping the migration after adding an index
// `dotnet ef migrations add AddBlogUrlIndex` → review the generated SQL!
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8+:** indexes on **primitive collections** are supported (with provider-specific syntax).
- **EF 9/10:** `HasIndex` syntax unchanged; **named query filters** (EF 10) interact with indexes —
  filtered indexes for soft-delete + filtered EF queries form a powerful combo (see
  [Global & Named Query Filters](08.Global-and-Named-Query-Filters.md)).

## 🌍 Real-world production tips

- **Always check the execution plan**, not just "is there an index?". Use `EnableSensitiveDataLogging`
  in dev and run `SET STATISTICS IO, TIME ON` (SQL Server) or `EXPLAIN ANALYZE` (Postgres).
- **Composite over single** indexes when queries always filter together. Two single-column indexes
  rarely beat one well-chosen composite.
- **Filtered indexes for soft delete:** if 99% of rows are `IsDeleted = 0`, a filtered index on
  active rows can be 100× smaller and faster.
- **Don't add an index without removing the next-least-useful one** if writes are bottlenecked.

## 🎯 Practice (with full solutions)

### 1. Choose the right composite — `Medium`
**Scenario:** Your most common query is `WHERE TenantId = X AND PublishedUtc > Y` and your
second-most-common is `WHERE TenantId = X ORDER BY PublishedUtc DESC LIMIT 50`. Which index?
**Solution:**
```csharp
modelBuilder.Entity<Post>()
    .HasIndex(p => new { p.TenantId, p.PublishedUtc });
```
**Why it's better:** both queries are accelerated. `TenantId` first because it's the **equality**
predicate; `PublishedUtc` second because it appears in **range** + ordering. Reverse the order and
the second query loses its sort.

### 2. Speed up a hot list — `Medium`
**Scenario:** A dashboard query is `SELECT Total, PlacedUtc FROM Orders WHERE CustomerId = X AND
Status = 'Open'` and it scans the table.
**Solution:** a filtered, covering index:
```csharp
modelBuilder.Entity<Order>()
    .HasIndex(o => o.CustomerId, "IX_Orders_OpenByCustomer")
    .IncludeProperties(o => new { o.Total, o.PlacedUtc })
    .HasFilter("[Status] = 'Open'");
```
**Why it's better:** filter shrinks the index to a fraction of the rows; included columns make the
query **covered** (no key lookup back to the table).

## ✅ Key Takeaways

- Indexes accelerate reads at the cost of space and write throughput.
- Composite index **column order matters** — put equality predicates first.
- **Filtered** indexes pair beautifully with **named query filters** (EF 10) for soft-delete and
  multi-tenant scenarios.
- **Covering** (`IncludeProperties`) indexes let hot read queries skip the table.
- Don't index "just in case" — measure first, then index.

2. When is a filtered index dramatically better than a regular one?
3. What's the cost EF/DB pays for every additional index?
