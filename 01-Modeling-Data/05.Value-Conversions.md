# Value Conversions

## 🧠 Intuition

Sometimes the C# type you want to use and the database column type don't match: an `enum` stored
as text, a `Uri` stored as a string, money stored as cents (long) instead of decimal, an encrypted
string-on-disk, a `DateOnly` stored as a `date` column. **Value conversions** let you declare both
sides — "this property in C# is `X`, in the column it's `Y`" — and EF handles the round-trip
automatically.

> 💡 **Analogy — currency exchange.** You think in euros; the database thinks in dollars. A value
> conversion is the FX rate that EF applies every read and write.

## 🎯 The Problem

```csharp
// ❌ Before: enums silently stored as integers — DBA opens the table, sees 0/1/2 and curses you
public enum BlogStatus { Draft, Published, Archived }
public class Blog { public BlogStatus Status { get; set; } }
// Migration creates: [Status] int NOT NULL
```

Compact, fast, and **unreadable** in any DB tool. Worse: reorder the enum and existing rows now
mean something different. Storing the string is often the senior move.

## 💻 Built-in conversions you'll actually use

### Enum → string

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Status)
    .HasConversion<string>()
    .HasMaxLength(20);
```

Column becomes `nvarchar(20)`. Rows are readable; safe against re-ordering enums.

### `Uri` ↔ `string`

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Url)
    .HasConversion(
        v => v.ToString(),
        v => new Uri(v));
```

### Money as cents (avoid decimal scale surprises across providers)

```csharp
public class Order { public decimal Total { get; set; } }

modelBuilder.Entity<Order>()
    .Property(o => o.Total)
    .HasConversion(
        v => (long)(v * 100),       // C# decimal → DB bigint
        v => v / 100m);              // DB bigint → C# decimal
```

### List or array → comma-separated string (last-resort case)

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Tags)
    .HasConversion(
        v => string.Join(',', v),
        v => v.Split(',', StringSplitOptions.RemoveEmptyEntries).ToList());
```

> 🆕 In modern EF (8+), prefer **[primitive collections](10.JSON-Columns-and-Primitive-Collections.md)**
> — a real column type, queryable via LINQ, no manual conversion.

### `DateOnly` / `TimeOnly` (EF 8+ — no conversion needed)

```csharp
public class Event {
    public DateOnly EventDate { get; set; }    // maps to `date`
    public TimeOnly EventTime { get; set; }    // maps to `time`
}
```

EF 8 and later map `DateOnly` and `TimeOnly` natively on SQL Server, PostgreSQL, and SQLite. No
value conversion required. Earlier versions needed a conversion; now you just use the types.

## 💻 Reusable converters via `ValueConverter`

```csharp
public class UriToStringConverter : ValueConverter<Uri, string> {
    public UriToStringConverter() : base(v => v.ToString(), v => new Uri(v)) { }
}

modelBuilder.Entity<Blog>()
    .Property(b => b.Url)
    .HasConversion<UriToStringConverter>();
```

Then via convention, apply it to every `Uri` property at once:

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder cfg) {
    cfg.Properties<Uri>().HaveConversion<UriToStringConverter>();
}
```

## ⚖️ Trade-offs

**Pros:** clean C# types (`Uri`, enums, value objects) with sane column types; one place to enforce
the round-trip; works with LINQ (EF applies the conversion when translating predicates).
**Cons:** *can defeat indexes* if the conversion isn't representable in SQL (e.g. a complex
encryption converter); operators like `Contains` over a comma-joined list become full table scans;
LINQ translation can be limited for non-trivial converters.

## 🚫 Common mistakes

```csharp
// ❌ Conversion on a property used in a WHERE clause that becomes a full scan
b.Property(x => x.Tags).HasConversion(/* comma-join */);   // ctx.Blogs.Where(b => b.Tags.Contains("ef")) → can't use an index
// ✅ use primitive collections (next file) — first-class column type, real LINQ translation

// ❌ Storing currency as decimal without setting precision
b.Property(o => o.Total).HasColumnType("decimal(18,2)");   // ✅ explicit; some providers default to (18,0)
// (Better: configure once via ConfigureConventions on Properties<decimal>())

// ❌ Storing DateTime in UTC but reading it back as Unspecified — silent timezone bugs
b.Property(x => x.CreatedUtc).HasConversion(
    v => DateTime.SpecifyKind(v, DateTimeKind.Utc),
    v => DateTime.SpecifyKind(v, DateTimeKind.Utc));
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8:** native `DateOnly` / `TimeOnly` mapping; the `ValueConverter`s for them are no longer
  needed.
- **EF 9:** improvements to LINQ translation through converters (more predicates supported).
- **EF 10:** value converters compose better with **complex types** — you can convert nested
  properties inside a JSON-mapped complex type.

## 🌍 Real-world production tips

- For currency: store in **smallest unit** (cents) as `long` to avoid decimal precision drift
  across providers — or, more pragmatically, set a precise SQL type (`decimal(18,2)`) globally via
  `ConfigureConventions`.
- For enums: prefer **string** for human-readability, but pin the `MaxLength` so the column isn't
  `nvarchar(max)`.
- Avoid "clever" converters that break LINQ translation — when in doubt, check the **Generated SQL**
  (see [Query Tags & Diagnostics](../02-Querying/07.Query-Tags-and-Diagnostics.md)).

## 🎯 Practice (with full solutions)

### 1. Make an enum readable in the DB — `Easy`
**Task:** Switch `BlogStatus` to a string column with max length 20, without changing the C# type.
**Solution:**
```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Status)
    .HasConversion<string>()
    .HasMaxLength(20);
```
Migration: column becomes `nvarchar(20)`. Existing data needs a one-time transform — `dotnet ef
migrations script` shows you the alter that EF will run.
**Why it's better:** DBAs and audit tools can read it; reordering the enum no longer changes
meaning.

### 2. Apply a converter globally — `Medium`
**Scenario:** Every `decimal` in your model should be `(18, 4)` to handle financial amounts.
**Solution:**
```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder cfg) {
    cfg.Properties<decimal>().HavePrecision(18, 4);
}
```
**Why it's better:** new entities are configured automatically; you can't forget. Use the same
trick to register a custom `Uri` or `DateTimeOffset` converter once and forget it.

### 3. Don't blow your indexes — `Medium`
**Scenario:** You converted `Tags` to a comma-joined string. Queries like
`ctx.Blogs.Where(b => b.Tags.Contains("ef"))` scan the entire table.
**Task:** propose two fixes.
**Solution:**
- **Best:** model `Tags` as a [primitive collection](10.JSON-Columns-and-Primitive-Collections.md)
  — EF emits proper JSON / array predicates, and you can index it.
- **If you can't:** keep the converter but expose a normalized `TagsCsv` table for searches
  (many-to-many) — store the CSV as a redundant convenience field if you really need it for reads.
**Why it matters:** value conversions are powerful but **don't beat indexes** — once they hide
data inside an expression the database can't use indexes against, you've created an O(n) scan.

## ✅ Key Takeaways

- Value conversions reconcile **C# types** with **column types** without leaking either across the
  boundary.
- Built-in: enums → string, `Uri`, `DateTimeOffset` kinds, lists → CSV (last resort).
- **EF 8+** maps **`DateOnly` / `TimeOnly` natively** — drop legacy converters.
- Apply converters globally with **`ConfigureConventions`**.
- Watch out for converters that **defeat indexes**; check the Generated SQL.
