# Field Mapping & Shadow Properties

## 🧠 Intuition

Sometimes the data EF needs to read or write doesn't live in a public property on your entity:
- The class exposes a **read-only collection**, but EF needs to mutate a private list.
- The class is a **DDD aggregate** whose state lives in private fields, with no public setters.
- You want to track an **audit timestamp** or **tenant ID** that has no business reason to be on
  the class.

EF Core supports both: **backing fields / field mapping** (EF reads from a field, not a property)
and **shadow properties** (a property that lives only in the EF model, not on the class).

> 💡 Think of it as "EF can talk to your entity in ways your callers can't." That's how you keep
> public APIs clean while still letting EF do its job.

## 💻 Backing fields

```csharp
public class Order {
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyCollection<OrderLine> Lines => _lines.AsReadOnly();
    public void Add(OrderLine line) {
        if (line.Quantity <= 0) throw new ArgumentException();
        _lines.Add(line);
    }
}
modelBuilder.Entity<Order>()
    .HasMany(o => o.Lines)
    .WithOne()
    .HasForeignKey("OrderId");
```

By convention, EF finds `_lines` because the field name matches the property's camel-prefixed name.
If not, configure it:

```csharp
modelBuilder.Entity<Order>()
    .Property("Total")                    // can use the shadow-property syntax
    .HasField("_total")
    .UsePropertyAccessMode(PropertyAccessMode.Field);
```

This lets you have a class with **no public setters at all** — EF still hydrates and persists it.

## 💻 Shadow properties

A shadow property is a property EF knows about and stores in the table, but **doesn't exist on the
class**. Useful for cross-cutting metadata (`CreatedUtc`, `TenantId`, `LastUpdatedBy`) that the
domain shouldn't care about.

```csharp
modelBuilder.Entity<Blog>().Property<DateTime>("CreatedUtc");
modelBuilder.Entity<Blog>().Property<DateTime>("UpdatedUtc");

// In code, read/write via the change tracker
var entry = ctx.Entry(blog);
entry.Property("CreatedUtc").CurrentValue = DateTime.UtcNow;
```

Pair with a [SaveChanges interceptor](../03-Saving-and-Concurrency/06.Interceptors-and-SaveChanges-Hooks.md)
to set timestamps automatically and keep entities clean.

## 💻 Querying shadow properties

```csharp
var recent = await ctx.Blogs
    .Where(b => EF.Property<DateTime>(b, "CreatedUtc") > DateTime.UtcNow.AddDays(-7))
    .ToListAsync();
```

`EF.Property<T>(entity, "Name")` is the in-LINQ way to reference shadow properties. EF translates
it to the appropriate column.

## ⚖️ Trade-offs

**Pros:** clean public APIs (DDD-friendly); cross-cutting columns without polluting domain types;
encapsulated invariants stay encapsulated.
**Cons:** the model isn't immediately visible from the entity class alone — readers have to look at
configuration to see all the "real" state. Use sparingly and document.

## 🚫 Common mistakes

```csharp
// ❌ Adding CreatedUtc/UpdatedUtc to every entity class for no reason — pollutes the domain
public class Blog : BaseEntity { /* base brings audit columns no business code cares about */ }
// ✅ shadow properties + an interceptor to set them — domain stays clean

// ❌ Expecting EF to write to a property with a private setter when access mode isn't configured
public string Title { get; private set; } = "";
// ✅ explicit: .UsePropertyAccessMode(PropertyAccessMode.Field) or use a settable backing field
```

## 🆕 Latest EF Notes (8 / 9 / 10)

- **EF 8+:** primary constructors on entity classes work seamlessly with backing-field mapping.
- **EF 9:** improved support for read-only collections (incl. `IReadOnlyList`, `ReadOnlyCollection`)
  with EF supplying a backing list internally.
- **EF 10:** no major changes here; field mapping is mature.

## 🌍 Real-world production tips

- Combine **shadow properties** with a **SaveChanges interceptor** for audit timestamps and tenant
  IDs. Domain entities stay free of audit noise.
- For DDD aggregates, set `UsePropertyAccessMode(PropertyAccessMode.Field)` globally so EF *never*
  needs public setters.
- Don't shadow business-meaningful state — if `Status` matters to behavior, it belongs on the class.

## 🎯 Practice (with full solutions)

### 1. Add audit columns without changing entities — `Medium`
**Task:** Add `CreatedUtc` and `UpdatedUtc` to every entity without touching their classes.
**Solution:**
```csharp
// In OnModelCreating, walk the model
foreach (var entityType in modelBuilder.Model.GetEntityTypes()) {
    modelBuilder.Entity(entityType.ClrType).Property<DateTime>("CreatedUtc");
    modelBuilder.Entity(entityType.ClrType).Property<DateTime>("UpdatedUtc");
}
// Then a SaveChanges interceptor (or override SaveChangesAsync) fills them in.
```
**Why it's better:** business code never sees these columns; you can swap them out (or off) per
context without changing entity classes.

### 2. Encapsulate a collection — `Easy`
**Task:** Make `Order.Lines` read-only externally but persistable by EF.
**Solution:** the `Order` class with `_lines` backing field above; EF discovers `_lines` by
convention.
**Why it's better:** callers can't bypass `Order.Add(line)` validation; EF still hydrates and
saves the collection.

## ✅ Key Takeaways

- **Field mapping** lets EF read/write through private fields — keeps public APIs clean.
- **Shadow properties** live in EF's model but not on your classes — perfect for audit/tenant
  metadata.
- Reference shadow properties in LINQ with **`EF.Property<T>(entity, "Name")`**.
- Use sparingly; the cost is reduced visibility into "what's actually stored."
